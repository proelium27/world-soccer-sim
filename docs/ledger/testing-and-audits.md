# Testing, audits, CI sharding and the two-Mac cluster

> Moved verbatim from CLAUDE.md on 2026-09-25 to keep session context small. This is the detailed ledger for this area: read it before touching the code it describes, and add new entries here, not to CLAUDE.md. References to "this file" below meant CLAUDE.md as a whole; the other sections now live alongside this one in `docs/ledger/`.

**Which to reach for when a run will be long.** There are two Macs available to this project (see `.test-cluster.example.json`), and the two `:cluster` commands use the second one. Measured 2026-08-29: the full suite is **1384s on one machine, 570s across two — 2.43x**. **Those two numbers predate the 626-club world and are low**: total CI work rose 49% with it (5615s → 8367s of runner time), so expect roughly half as long again on both until someone re-times them — the *ratio* is what the advice rests on and that is unaffected. So for a *full-suite* run or a *multi-seed audit*, prefer `npm run test:cluster` / `npm run audit:cluster` over the plain command. Both **fall back to a normal local run within ~2s** when the other machine is asleep, offline or unconfigured, so neither is a gamble. **`.test-cluster.json` is gitignored, and a git worktree only checks out TRACKED files, so it is never present in one** — which made "no config here" a guaranteed false negative for any session working in a worktree, and `testCluster.sh` compounded it by copying the blank example over the top and quietly running local (measured 2026-08-30: three full-suite runs at 1x while the other Mac sat idle). Both scripts now resolve the config from the **main checkout** via `git rev-parse --git-common-dir` when it is not beside them, and say so — plain `npm test` stays right for a scoped run of a few files, where the sync and startup cost more than they save. **Two caveats worth knowing before making it reflex.** (a) They `rsync --delete` the working tree onto the other machine, so **whichever machine you invoke from is the source of truth for that run**; the target is a scratch dir (`~/soccer-gm-testcluster`), never a real checkout, but do not treat this as two-way sync. (b) **The other Mac may have its own session running** — observed live on 2026-08-29, a full vitest run under way there, back when a second account worked this repo; one developer with two machines can do the same to themselves — so a cluster run can land on a machine that is already busy, and will both go slower and slow the other session down. Probing whether the other machine is idle is cheap; assuming it is, is not.
Audit scripts live in `scripts/` (e.g. `divisionAudit.ts`, `weakLeaguesAudit.ts`) — run with `tsx`.

**An audit's seeds can be split across two Macs (`npm run audit:cluster -- <auditName>`, `scripts/auditCluster.sh`, 2026-08-28).** Audits are the long pole — longer than the test suite: `weakLeaguesAudit` defaults to `SEASONS=20 × SEEDS=1,2,3,4`, i.e. 80 season-cycles at ~13s each (`scripts/worldGenSplitProbe.ts` measures that 13s), and this file refers to 30- and 100-season runs elsewhere. 13 scripts read `SEEDS` and loop them **serially**. Seeds split where test files often can't: a seed is an independent world, whereas the slow *test* files chain seasons (season N+1 starts from season N) and are serial by nature — the distinction to keep straight before trying to parallelise the wrong thing. Shares `.test-cluster.json` (host, capacities) with the test runner, and the same guards: login shell for the remote's PATH, tree-hash check after rsync so half your results can't come from different code, and fall back to running every seed locally when the other machine is unreachable. **The load-bearing part is that it REFUSES to split the six audits that aggregate across seeds** — `weakLeaguesAudit`, `leagueVolumeProbe`, `positionAwardAudit`, `midVsMidProbe`, `totsSlotProbe`, `totsWeightProbe`. Those don't just loop and print; they average over the seeds and gate on the mean, precisely because one seed is noisier than the effect (`weakLeaguesAudit`'s own header: adjacent rungs "coin-flip on seed noise", and it prints a NOTE that the mean gate is under-powered below 3 seeds). Split in half, each machine averages its own two seeds and prints a confident-looking number over a sample the script itself calls too small — a plausible wrong answer, not a crash, which is the same failure class as a distributed test run going green against stale code. `--per-seed-only` splits anyway when you want the per-seed sections and are ignoring the aggregate; `--local` runs every seed here with the aggregate intact. **`FORWARD_VARS` in the script is a hand-maintained list of the env knobs audits read** (`SEASONS`/`SEED`/`SHOW`/`RUN`/`RATE`/`N`/`ALL_N`) — a new audit reading a new variable silently won't have it reach the remote half until it is added there.

**Open work queue from real player saves: `docs/player-save-findings.md`.** Six saves sent in by players were audited 2026-08-17; that file is a *fix queue*, not a design doc — each item carries evidence, root cause with line refs, fix shape and gating, and they're independent of each other. Two things there generalize beyond the individual bugs: **(a) real players reach season 75**, roughly triple the 20-30 season horizon every dynasty audit in `scripts/` gates at, and at least one invariant (the country strength ladder) fails only out there while the 20-season gate stays green; **(b) `scripts/playerSaveAudit.ts`** audits any exported save for size/integrity/balance, and reads the **raw parsed file rather than going through `migrateLeague`** — migration repairs and culls, so a migrated league tells you what the game would fix, not what the player has. Player saves live in `leaguesaves/` (gitignored, other people's data, never committed) and exist only on the machine they were sent to.

The first `npm test` after any `src/core` change rebuilds the cached test worlds (see `test/` below); later runs reuse them. `SOCCER_GM_NO_FIXTURE_CACHE=1 npm test` skips the cache.

**A local `npm test` runs on half the cores, deliberately (`localMaxWorkers` in `vite.config.ts`, 2026-08-29).** Vitest defaults to about one worker per core and on this suite that is measurably too many: the work is sustained full-world multi-season sims and the machines are fanless laptops that throttle under exactly that. Measured on an 8-core Air, **6 workers over 6 heavy files took 2025s while the *sum* of per-test times hit 8476s against ~1038s uncontended — an ~8x inflation** — so past a low worker count this suite scales *negatively*: more workers make the wall-clock worse, not merely sub-linear. The same effect from the other side: capping workers was worth **1.96x on the full suite** (1117s → 570s) in the two-machine runner. **RAM was NOT the mechanism when this shipped and IS one now, and the flip is worth knowing about — the first full run after third divisions (#308) exhausted memory and took the host down (2026-09-02).** The original reading was right at the time: peak resident size was ~445MB per worker, so nine fit comfortably; the cost was memory bandwidth and thermals. Going from 420 clubs / 7,092 fixtures to **626 / 10,538** invalidated it. Measured in one process on a 16GB machine, 2-division → 3-division: `league.played` **129MB → 192MB** of JSON (1.49x, tracking the world) but **peak heap for a simmed season 471MB → 1082MB (2.30x)** — *superlinear*, because a matchday's box scores are all live at once. Nothing accumulates across seasons (the offseason clears `played` and live heap drops back to ~100MB) but **resident size never comes back**: across three seasons RSS ratcheted 1205 → 1393 → 1510MB against a ~100MB live heap, since V8 does not return freed pages to the OS. So a worker on a heavy file costs **~2-3GB and keeps it**, and locally the sequencer inherits vitest's slowest-first `sort()` (`shard()` is a no-op without `--shard`), so a run *starts* by putting the heaviest sim files on every worker at once — the worst case by construction. The cap is therefore now the **lower of a core limit and a memory limit** (`WORKER_PEAK_GB` 3, `HOST_RESERVE_GB` 4): 16GB/10-core lands on 4 workers, 8GB on 1. A per-worker `--max-old-space-size` ceiling is set from the same `WORKER_PEAK_GB`, so `maxWorkers × budget` is a real bound rather than an assumption — **Node's ~4.3GB default bounds one worker without bounding the run**, which is exactly how the machine died with no test reporting anything. Verified after the change: the six heaviest files together peak at **6.5GB** and the full suite at ****6.8GB** (202 files / 2093 tests green in 26.6 min, 4 workers)**. The thermal half of the story is unchanged and still applies — it *worsens as the machine heats*, with the same three files taking ~506s cool and 988s after six hours of back-to-back sims (the `shardPartition.ts` "234s and 557s an hour apart" warning, one level up). Half the cores is deliberately conservative rather than tuned — the true optimum is machine- and temperature-dependent and could not be pinned through that much drift. `VITEST_MAX_WORKERS=n` overrides (and throws on a non-positive value rather than silently ignoring it). **CI is deliberately untouched**: its runners are already core-poor, they are not thermally-limited laptops, and CI gates merges, so there is no upside and real downside if the guess is wrong for that hardware.

- `test/` — vitest. `test/validation/` holds the M1/M4 §8 gate tests.
  - **A world-wide `max` is not a league statistic, and the M3 top-scorer gate learned this the hard way (2026-08-11).** It asserted a Golden-Boot-shaped band (18–36) but measured the max goals over **every player in the world, second divisions included**. Both halves drift for reasons unrelated to scoring realism: a max rises with sample size (12 competitions → 16 raised it on its own), and tier-2 defences are weaker, so the world max was *set by a tier-2 player* and exceeded every top-flight leader that season (43 vs 32, 40 vs 34). It failed at a 36.2 mean while all 40 measured tier-1 Golden Boots sat between 23 and 34 — inside the band, never once above it. Now measures the **mean tier-1 top scorer** (27.7, per-season range 27.0–28.8), which is what the band describes and is invariant to both world size and tier-2 quirks. `scripts/topScorerProbe.ts` prints both side by side. **Widening the ceiling would have been the wrong fix** — it keeps a number that needs re-widening every time a country is added.
  - **The M1 mismatch gate had the same fault, third time in this file (2026-08-27).** "Strong home beats weak 70-80%" measured **one** league seed's strongest-vs-weakest pair. How far apart that pair lands is itself a draw — the OVR gap runs 16.9 to 18.8 across seeds — so the reading carries **±3.3pp of spread against a 10pp band**. Measured on **untouched `origin/main`**: `73.60 / 74.42 / 76.07 / 78.65 / 78.75 / 79.88 / 76.89 / 83.90` (mean 77.77, sd 3.30), i.e. **seed 71 already sat outside the band on main** and seed 1, the one the gate read, was passing by 0.12pp. A change worth **+0.23pp on the mean** then failed it. Now averages the same `LEAGUE_SEEDS` the mid-vs-mid gate already uses, band untouched, mean 78.0. **The recurring lesson: when a §8 gate fails, first measure its estimator across seeds on main — twice now the gate was reading one arbitrary sample, and both times widening the band would have hidden that.**
  - **"Average team" must mean the average team, not the middle array index — the M1 §8 benchmark gate (2026-08-13).** `averageMidVsMid` sampled one club per seed as `seedComps[len / 2]`. Strength targets are shuffled across tids at generation, so that is an arbitrary club, not the median one — the same file already sorts by `avgOvr` "rather than array position" to pick its strong/weak pair, and this function was simply never given the same treatment. The gate therefore reported the sampled club rather than the league, and it sat on its floor (goals/game **2.6019** against a 2.6 floor). A change that provably did not move scoring — **2.8566 → 2.8560 measured across all 100 teams, a difference of 0.0006** — failed it, purely because a different club landed at that index. It now averages **every** team's self-match, which lands all six metrics inside their **existing** bands on both the old commit and the change that exposed it. **No band was moved**, deliberately: the bands are the spec's realism targets and none of them was the problem. `scripts/midVsMidProbe.ts` prints both estimators side by side. Same lesson as the top-scorer gate above — fix the statistic, don't widen the band.
  - **A 5-season average is not precise enough to gate on — the M1 table-spread gate (2026-08-16).** It averaged **5** seasons of champion points against a 78-94 band. A single season's champion total has sd ≈ **5** points (`scripts/championPointsProbe.ts`, 20 seasons span 72-91), so that average carried ~**2.2 points of its own sampling error**, against a true mean of ~82 sitting only ~1.8 of those above the floor — i.e. **it could fail on seed luck with nothing wrong with the sim**, which is the precise sense in which CLAUDE.md already said it "sits near its floor by construction". Demonstrated: raising `YELLOW_GIVEN_FOUL` 0.11 → 0.18 read **75.8** here, a clean failure, while the *same change* over 20 seasons moved the champion mean **up** (81.75 → 82.20) and **reduced** its spread (sd 5.80 → 4.66). Now averages **20** seasons (~22s, against 13-minute gates elsewhere), which halves the estimator's error; **the band was deliberately not moved**, and the widened gate was verified green on **both** sides of the change so the fix can't be tuned to it. Third instance of the same lesson as the top-scorer and "average team" gates: **fix the statistic, don't widen the band** — and note the failing statistic here was the *sample size*, not the quantity.
  - **TWO ENGINE GATES WERE MEASURING A QUANTITY THAT LARGELY CANCELS, and both had been passing on luck (2026-09-10).** Fifth and sixth instances of the standing lesson, and the sharpest: in each case the *mechanism* was healthy and the *estimator* was near-null, so a routine rng-stream shift tipped them. Both were re-measured across sample sizes on both trees, rewritten to measure what they were reaching for, and **verified green on the merge base before being adopted** — which is what separates fixing a statistic from tuning a gate to the change that needed it.
    - **`fatigue.test.ts`'s stamina gate compared both sides tired against both sides fresh.** `chanceP` reads `off.attack - def.defense`, so fatigue applied equally to both sides cancels out of the difference and only the residual survives (attack and defense sit on slightly different fatigue curves). Worth **0.12%**, and `origin/main` passed it **by ONE SHOT IN 5052**. It had already been re-tuned once (40 → 200 trials) after an earlier stream shift tipped it, which was this same symptom read as a sampling problem. One tired side against one FRESH side, orientation flipped and summed so `HOME_ATTACK_BONUS` cancels, is worth **6.5-7.0%** on the identical fixture — ~50x the signal, because the fatigue gap now lands in the term that decides a chance. `scripts/staminaShotProbe.ts` prints both forms.
    - **`neutralVenue.test.ts` compared one noisy sum against HALF of another noisy sum**, and the residual it bounded is centred on zero, so its sampling error was most of its value. On one tree it passed at 400 matches, **FAILED at 1200 and passed again at 3000**, the residual wandering 15 → 103 → 8. The denominator is itself small (an 11-goal bonus gap over 400 matches on main), so the bar collapses toward zero exactly when the sample is unluckiest. Now a one-sided comparison of the home **SHARE** of goals, which moves both halves of the comparison together so the noise largely divides out: passes at 400/800/1200/2000 on both trees. `scripts/homeEdgeProbe.ts` prints both forms.
    - **The generalizable tell: a gate that passes by a hair on `origin/main` is not a tight gate, it is a null one.** Before relaxing or re-seeding an engine test, measure its effect size on the merge base — if the effect is a fraction of a percent, the quantity is probably cancelling and the fix is a different measurement, not more trials.
  - **A minimum over 320 clubs is not a safety invariant either — the offseason roster-floor test (2026-08-13).** It asserted every club sits at or above `ROSTER_SAFETY_FLOOR` (18) after one offseason. Nothing enforces that: retirement and contract expiry are not sales, so `runAITransferMarket`'s per-sale depth floor never sees them, and `ensureUserRosterSafety` can only promote academy players a club actually has. Measured over five seasons on the test's own seed, **`origin/main` itself dips to 16 — the user's own club, season 4** — and the test only ever looked at season 1, where it happened to land exactly on 18. It was passing by luck, and any change that perturbs match results can tip it (across 8 seeds at season 1: main `20 19 18 19 18 18 18 20`, i.e. sitting *on* the floor half the time). Now asserts the engine's real requirement as a hard floor (**11** fit players, below which `selectXI` silently leaves slots empty) plus the healthy-squad target on the **5th percentile**, which is 21 on every seed on both sides and doesn't move. Dips recover by the next offseason. If the floor should be a genuine guarantee for AI clubs, that needs a mechanism (AI free agency refilling to it), not a tighter assertion — see the lower-severity leftovers about squads dropping below 11.
- **CI shards are packed by cost, not by file count (`test/helpers/shardPartition.ts`, 2026-08-25).** Vitest's `--shard` hashes each path with sha1, sorts, and slices into equal *counts*, which is deterministic and cost-blind — a bad pair here, because the suite's work sits almost entirely in a few full-world sim files. Measured over three consecutive CI runs: slowest shard 1749/1765/1863s against a fastest of 40/41/47s, on ~75 minutes of total work, i.e. one runner carried the build while another idled for half an hour, the same way every run. A `CostAwareSequencer` (wired at `test.sequence.sequencer` in `vite.config.ts`) weights each file and greedily packs the shards instead. Three things to know: **(a)** the weights are a hand-maintained table of measured seconds, defaulting to 10s for anything unlisted — being wrong costs *balance only*, never correctness, since `partitionByCost` is total and disjoint whatever the weights say (`shardPartition.test.ts` pins that, and it is the point of the file: a partition bug drops a file from every shard and CI still reports green). Add an entry when a new file runs longer than ~30s. **(b)** **Balancing alone did NOT speed CI up, and the measurement is the point.** The floor is the slowest single *file*: on the first packed run shard 1 ran `offseason.test.ts` **alone** for 1933s, against a pre-balancing worst shard of 1749-1863s — i.e. the old worst shard was already essentially that one file, so there was never a wall-clock win to take (the estimate that there was assumed no single file exceeded an even share; this one is ~2.2x it). What balancing bought is the other five shards getting lighter — spare capacity, not a faster build. It also makes the floor *mechanical*: shard 1 is provably one file, so the next move is unambiguous. **(c)** **The giants have since been split, and that is what actually moved the number.** `offseason.test.ts` (23 tests, ~1933s CI) became `offseason` / `offseasonSquads` / `offseasonRetirement` / `offseasonFinance` / `offseasonSolvency`, and `international.test.ts` (25 tests, ~1082s) became `international` (the pure structural tests, which drop to ~7s once the sims leave) / `internationalCampaign` / `internationalPlayerRecord` / `internationalEquivalence` / `internationalConfederationCups`. Every test moved **byte-identically** — they were already independent, each building its own seeded rng — with the shared `playFullSeason` / `advance` helpers lifted into `test/helpers/offseasonLeague.ts` and `test/helpers/intlLeague.ts`. The packing is what then spreads the pieces; without it two halves land back on one shard. **Measured after the split: shards 603/639/666/685/698/725s against a 669s even share, i.e. within 8% of the best any partition could do, and CI wall-clock 1863s -> 725s (~31 min -> ~12 min).** Total work did not grow (4016s against a 4131-4922s baseline), so splitting a hot sim file across processes costs nothing measurable in re-JIT. **(d)** With no file dominating, the binding constraint is now **total work / shard count**, so the next lever is the shard count in `ci.yml` — but a shard is **not free**, and that is new (2026-08-29). GitHub Free allows **20 concurrent jobs per account**, so shards compete for slots across every branch running at once: at six shards, three active branches want 42 jobs and the repo sits pinned at exactly 20 in progress with the rest queued, which looks like a run creeping through its shards one at a time. Raising the count past what the ceiling can serve buys nothing and slows every *other* branch. The first thing to fix when CI feels slow is therefore demand, not the split: `ci.yml`'s `push` trigger is filtered to main precisely because an unfiltered `push` alongside `pull_request` ran the whole suite **twice on the same commit** (verified by run ids with `event=push` and `event=pull_request` on one sha), doubling demand for nothing. The same file also carries a `concurrency` group so a new push **supersedes** the branch's in-flight run rather than queueing behind it — the other half of that backlog was stale runs finishing six shards nobody would read. It is deliberately **not** applied to main (`cancel-in-progress` is conditioned on the ref): merging two PRs in quick succession would otherwise cancel the first commit's run and leave it permanently unverified, not more splitting — the packing test asserts against exactly that bound (`max(slowest file, total/shards)`) rather than a fixed number, so it stays honest in either regime. **(e)** CI runners are ~1.5x slower than a dev machine here, and a dev machine running full-world sims back to back **thermally throttles** — the same file measured 234s and 557s an hour apart — so treat the weights as an ordering, not as seconds, and don't chase a small discrepancy. **(f) A WORLD-SIZE CHANGE INVALIDATES THE WHOLE TABLE, and not in a way that still sorts correctly (2026-09-02).** The 626-club world (#308) grew total CI work **5615s → 8367s (+49%, tracking the club count almost exactly)**, but it grew it *unevenly*: a file that builds a world and sims seasons roughly tripled while a pure-derivation file did not move, so the packing — which only cares about relative cost — went genuinely wrong rather than merely scaling. Measured on run 33580546751: shards **870/1184/1306/1538/1558/1911s**, i.e. the slowest at **1.37x** the 1394s even share, while the model believed it had balanced them to within 1% (it predicted 1000-1009s each). **Fourteen files that had crossed the ~30s bar were still on the 10s default**, `cupIntegration.test.ts` at 743s of CI time against a weight of 10. The table was rebuilt from that one run's per-file `tests` durations ÷1.5 (its stated local-seconds basis), taking every number from **one** contended run so they are consistent with each other, where the old table mixed months and worlds; re-scored against the same measurements that lands **3105/3073/3138/3149/3117/3149 — max/even 1.01**. Refresh it the same way after the next world change, from a green run rather than file by file: `gh run view <id> --log | grep -oE '\S+\.test\.tsx? \([0-9]+ tests?\) [0-9]+ms'`. **But the wall clock did NOT follow, and that predicted 1.01 is the trap.** Measured after the refresh (run 33641959090): shards **1245/1304/1438/1531/1501/1802s**, so the slowest went 1911s → 1802s and CI ~32 → ~30 min, not the ~24 predicted. The *work* did even out (summed test-time 1.13x the even share, against 1.37x before) — **but summed test-time is not shard wall clock, and this table can only balance the former.** Two causes, both inside that single run: **effective parallelism varied 1.72–2.48x across the six runners** (shard 2 drew the slowest and finished last on the second-*lightest* load, which no packing can fix), and **per-file cost swings run to run** (`offseasonRetirement` 1359s → 1481s, `internationalConfederationCups` 813s → 574s — ordering survives, which is all packing needs). So refresh after a world change, but don't expect proportional wall-clock gains and never tune these against one run's wall clock. **The corollary is that (d) has expired:** the slowest single file now sits *inside* the range the shards actually finish in, so a seventh shard buys nothing and the lever is the heaviest file, not more runners. **(g) THE HEAVIEST FILE WAS REPEATING ONE WORLD, AND THE FIX WAS A SHARED FIXTURE RATHER THAN A SPLIT (2026-09-08).** `test/core/youthIntake.test.ts` measured **2,073s on CI** against its shard's total wall clock of **2,114s** — one file was 98% of a runner, which spent its last twenty-two minutes on it while the rest idled, and it was the slowest in the suite by **2.3x** over `offseasonRetirement` (907s on the same run — so (f)'s naming of that file as the slowest was already stale). The cause was not that it did too much: twelve of its fifteen tests each built and simmed **the identical 626-club world**, all off `mulberry32(4)`, to assert twelve different things about it. One `beforeAll` sharing one world (plus a second advance, which one test needs) replaced thirteen season+offseason runs with two, and **no test changed what it asserts**. **The generalizable rule, and it now precedes the split advice above: before splitting a heavy file, check whether it is repeating one fixture.** A split divides the same work and adds files to keep in step; sharing removes the work. The counter-case is `scoutDirections.test.ts` (860), whose three worlds differ in the directions they were built with — the thing under test — and which already memoises across the cases that do want the same one. Since the shared world is now read by twelve tests, `freezeFixture` shallow-freezes the teams and their pid arrays, so a future test that mutates it in place fails on the line that did it rather than in whichever test runs next; that is the same functional-core invariant `test/db/playerIdentity.test.ts` gates, asserted at the one place it newly matters. **Measured: the file went ~1382s → 186s locally, all 15 tests unchanged.** **Do NOT expect the shard to fall proportionally, for the reason (f) spells out — summed test time is not shard wall clock.** What moved is the *floor*: the worst shard was 40m17s set by that one 34.6-minute file, and the heaviest file is now `offseasonRetirement` at 907s CI, so the binding constraint goes back to total work over six shards — where the other five shards were already finishing in 19-32 minutes. Expect roughly **40 → 30 minutes**, not 40 → 20; total modelled work only falls ~7%, and re-scored packing lands **2263-2272s per shard, max/even 1.00**.
- **A local run can be split across two Macs (`npm run test:cluster`, `scripts/testCluster.sh`, 2026-08-28).** Same idea as the CI sharding above, pointed at hardware you own: it probes the other machine, rsyncs the working tree (so uncommitted work is tested), runs shard 1/2 here and 2/2 there in parallel, and merges the blob reports into one pass/fail. Unreachable machine (asleep, offline, no key) falls back to a normal local run after a 2s timeout; `-- --local` forces it. Config is `.test-cluster.json` (gitignored — it names *your* machine), seeded from `.test-cluster.example.json`. The split reuses `partitionByCost` with an optional `capacities` array, because two laptops are not two identical CI runners; **with uniform capacities it reduces to exactly the old least-loaded rule, so CI's split is byte-for-byte unchanged and a test pins that.** Gotchas, all found by running it against a real second machine rather than by reasoning: **(a) A file timed ALONE is not the number it costs during a full run, and the gap is large.** Measured on an 8GB MacBook, `offseasonFinance.test.ts` is 156s solo and 244s alongside three other heavy files — 1.57x at only *four* workers on *eight* cores, so it is memory bandwidth and thermals, not CPU contention; parallel efficiency across those four was ~55%. The `FILE_WEIGHTS_SECONDS` table holds full-run numbers, so a solo `npx vitest run <file>` reading far lower is expected — **do not paste it in**, since mixing a solo number into a table of contended ones reorders the packing on a measurement artefact. This is the same effect as the thermal caveat in (e) above, one level up. **(b) Hence a second machine is worth more than its core count**: it brings an independent memory subsystem and thermal budget, which is the part a small fanless machine is short of, and why the split is capacity-weighted at all. **(c) ~~Do NOT split more test files for this.~~ TRUE UNTIL 2026-09-02, FALSE NOW.** After the #278 splits the heaviest file was ~156s solo, well under a two-machine even share, so files had stopped being the ceiling and further splitting bought nothing but churn. The 626-club world undid that, and by 2026-09-08 the heaviest file was `youthIntake.test.ts` at ~2073s on CI — 98% of a whole shard, and a large fraction of a two-machine share. **It was fixed by sharing one world rather than splitting** (see (g) one bullet up), which is the move to check for first: a split still pays for the duplicated work, just on two machines at once. **(d) Two failure modes here report GREEN while being wrong, so both fail loudly instead.** Every shard computes the whole partition and keeps its own slice, so the machines agree only while they agree on the capacities — a malformed `VITEST_SHARD_CAPACITIES` therefore *throws* rather than falling back to an equal split, which would silently run some files twice and others never. And the runner hashes `src`/`test`/`scripts`/config on both sides after rsync and refuses to run on a mismatch, because a remote passing against stale code is a green that means nothing. **(e) `ssh host cmd` gets a non-login shell**, which on macOS never sources `/etc/zprofile` and so never runs `path_helper`, leaving PATH without `/usr/local/bin` — `npm ci` fails with "command not found" on a machine where node works perfectly in person. Remote commands go through a login shell so neither machine needs its dotfiles edited. **(f) `vitest --merge-reports` needs `run`** (without it vitest defaults to watch mode and merging is rejected), and it reads **every** file in `.vitest-reports/` as a blob and dies on anything else — so per-machine logs and exit codes live in `.test-cluster-run/`, never beside the blobs. **(g) Autotune only fires on a full run**, when both sides ran long enough that rsync/`npm ci`/startup isn't most of the elapsed time, damped halfway with a 4:1 clamp: bins hold whole files so a single run always over- or undershoots, and an early filtered run moved the remote from 2.0 to 8.86, which is not a 8.9x machine. **(h) `set -o pipefail` does NOT cross the ssh boundary, and that cost a whole run (2026-09-03).** It is set at the top of the script, but `rsh` opens a fresh login zsh, which reports only the last stage of a pipeline — so `npm ci --silent 2>&1 | tail -2 || exit 1` took its status from `tail` and could never fail. A half-finished remote install reported success, the suite ran against a `node_modules` with no vite in it, `npx` quietly fetched a *different major version* of vitest, and both shards died at startup about 20 minutes in. The rsync excludes `node_modules`, so nothing else would have noticed either. Fixed by setting the option inside the remote shell. **The general shape: any `set -o` in this script is local-only; a remote command needs its own.** **(i) The verdict is the two SHARD EXIT CODES, not the merged report, and it produces false REDs as well as the false greens (d) warns about.** It has to read exit codes — a shard that dies halfway writes a partial blob and the merge would call the files it did run green — but the converse happened on 2026-09-03: a shard exited 1 with **every test in its own blob passing, no unhandled errors, and the same shard exiting 0 on an immediate re-run against the same tree**. A full 204-file / 2165-test green suite was reported as a failure, and telling that from a real one meant reading both blobs by hand. The run now says so explicitly when the merged report shows no failing test and a shard still exited non-zero, and names the two possibilities. **Read the merged file count against a known-good run before believing a red**: short counts mean a shard really died, matching counts mean the runner failed after the tests passed.
- **Test worlds are cached on disk** (`test/helpers/worldCache.ts`, used by `makeLeague`). vitest gives every test file its own worker process, so an in-process memo died at each file boundary and the same world was regenerated in every one of the ~69 files that wanted one — the single dominant cost in the suite. Worlds are now generated once ever into `node_modules/.cache/soccer-gm-worlds/<hash>/` and parsed back on demand. **Re-measured 2026-09-03 on the shipped 626-club/15,650-player world, on an idle machine: generation 6.8s, a cached load 110ms, 66ms on an in-process memo hit, 25.7 MB per fixture — so a cached world is ~60x cheaper than generating one, not free.** (The figures here read "~4.1s / ~12ms / ~340x / 36 files" until then, from the 240-club/6,000-player world three expansions ago; they were what people budgeted against when deciding a per-test load was harmless, and a 2026-09-03 audit found ~70 scattered per-`it` loads plus files loading a world for code that never reads a player. Note also that generation measures 6.8s solo against the 12-20s a contended run implies — the same solo-vs-contended gap the cluster entry warns about.) **A call still allocates 15,650 player objects, so hoist it to one shared fixture when a file's tests only read, and prefer an existing seed to a new one: every distinct `(userTid, seed, genSeed)` is another 25.7 MB fixture to regenerate after any `src/core` change.** **Always build test worlds with `makeLeague(tid, seed)`, never `createLeagueState` directly** — the one exception is a test that *reuses its rng after generation* (threading it into a later `simThrough`/`simOffseason`), which needs the rng advanced by generation and so must keep generating; those live in `international.test.ts`, `offseason.test.ts`, `simThrough.test.ts`, `transfersRender.test.tsx`, the m3/m4 validation gates and one case in `loans.test.ts`. Gotchas: **(a)** the cache key is a content hash of **all of `src/core`** plus `src/engine/rng.ts` and the Node version — deliberately broad, because generation cannot then depend on anything unhashed. Narrowing it to generation's current import list reintroduces silent staleness; don't. A core edit costs one rebuild (~60s) and is free thereafter. **(b)** It is only sound because generation is deterministic apart from `meta.created` (a wall-clock stamp) — `fixtureFidelity.test.ts` asserts both that and cached-equals-fresh, and is what stops the cache drifting silently. **(c)** `SOCCER_GM_NO_FIXTURE_CACHE=1` bypasses disk entirely if you ever suspect the cache. **(d) Nothing prunes it, so it grows by one directory per source state the machine has ever tested — measured 3.6 GB across 20 hashes, the largest 720 MB.** `npm run test:clean-worlds` (`scripts/pruneWorldCache.ts`) keeps the current hash plus anything touched in the last 7 days; `--all` keeps only the current one. Deliberately a command rather than something `loadFixture` does on its own: several worktrees share one cache directory and each may sit on a different hash, so self-pruning would have them continually destroying each other's fixtures and paying full generation again.
