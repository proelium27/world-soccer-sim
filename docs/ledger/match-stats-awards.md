**Match data & stats**
- **Box scores** — `PlayerMatchLine`/`SeasonStats`. **Match Rating** (`engine/matchRating.ts`, FotMob-style 0-10, position-weighted, damped by minutes). `minutesPlayed` reconstructed from event clocks. `tackles`/`interceptions` split (`pickInterceptor`). Decorative `passes`/`crosses`/`foulsCommitted` attributed post-sim on a separate rng stream (scoreline-invariant). `avgRating` rolled into `SeasonStats`.
- **Assists key off `MatchPlayer.passing`, and event attribution is NOT scoreline-inert (2026-08-22).** The engine carried no passing attribute at all, so `pickAssister` had to weight its draw by `dribbling` — an assist was in effect a dribbling stat. Measured over a simmed league season, that left a creative midfielder's passing essentially unrelated to his assist count (**r = 0.077**, slope +0.005 per 10 points) while dribbling carried it (r = 0.32); keying off `passing` ((shortPass + longPass) / 2) lands **r = 0.307** and drops dribbling's spurious grip to 0.076. Volume is untouched by construction — `pickAssister`'s 25% no-assist roll means league assists are ~0.74x league goals either way (0.735 → 0.736), so this moved *who* is credited, not how much. `scripts/assistProbe.ts` measures it. **The gotcha that generalizes to any attribution change: assists feed `computeMatchRating`, match ratings feed `subPriority` and the bench-quality gate, and substitutions change who is on the pitch** — so "who gets the stat" is a real feedback path into results, and the `touchStats` scoreline hash was rebased for it even though the rng draw count is identical. Don't assume an attribution-only change is safe; `passes`/`crosses`/`foulsCommitted` are inert only because nothing reads them back.
  - **Related, unfixed: some attributes drive OVR (hence wages/value/team rating) but feed NOTHING on the pitch.** A full-back's `speed` (15% of his OVR) and `crosses` (12%) are both dead — `speed` is not on `MatchPlayer` at all, and `crosses` appears only in the `attack` composite, whose group is ST/W/AM/CM, so a full-back's never counts. Centre-back `speed` (6%) likewise. The check: an attribute is live only if it reaches `MatchPlayer` (`core/league/matchPlayers.ts`) or sits in a composite's skill list for a group that actually contains that position (`attack` = ST/W/AM/CM, `defense` = CB/DM/FB, `control` = every outfielder).
- **Suspensions** (`core/suspensions.ts`, 2026-08-16) — cards were simulated from M5 on but expired at the final whistle; `applySuspensions` turns them into league bans (`SUSPENSION_*` in `constants.ts`: 5 yellows → 1 match, second yellow → 1, straight red → 3, **longer-of not sum** when both land together). `SeasonStats` gained `yellowCards`/`redCards`, and `Player` gained optional `suspension` + `yellowCount` (running tally toward the next accumulation ban, distinct from the season total, `-= THRESHOLD` on trigger so a surplus booking carries). Structural notes: **(a)** it is the disciplinary twin of `applyInjuries` and is called beside it once per matchday — the global one-per-matchday tick is *exact* rather than approximate only because every competition is a 20-club round robin, so every club plays every matchday; a competition of another size would silently over-serve bans. **(b)** A ban earned by this matchday's cards skips this matchday's decrement, or the sending-off would partly serve itself. **(c)** **Bans are league-only by design**, which is both realistic and what keeps the blast radius small: `leagueMatchData` gained an optional `unavailable` predicate and *only* the per-competition league call passes `isSuspended` — `cupMatchData` and `nationMatchData` deliberately don't, so a banned player still plays the cup. Cup cards are aggregated onto `CupPlayerLine` as before and carry no ban. **(d)** Reads box-score *lines*, not events, because the line already separates a second yellow (`yellowCards >= 2` + a red) from a straight red. **(e)** **Zero rng draws** — cards are already rolled inside the match, so stream order is untouched. Availability does change who plays, hence composites, hence results, so a scoreline rebase was *expected* here — and **the `touchStats.test.ts` hash did not move, for a reason worth knowing**: that baseline runs `simSeason` (`core/season.ts`), a one-shot harness that computes `leagueMatchData` **once for the whole season** and never re-derives it per matchday, so it has never modelled injuries either and cannot see suspensions. The corollary is that **the scoreline baseline does not guard this path at all**; the gates that do are the `simThrough` ones (`m3-top-scorer`, `m4-multiseason` — which carries the pid/roster integrity gate too since 2026-09-03, its own file having folded in), all green with bans live, while `m1-table-spread` is on `simSeason` and is likewise blind to it. **(f)** Cleared every offseason alongside the injury heal (`clearSuspension`, step 2). **(g)** `suspension`/`yellowCount` are optional and deliberately **not** backfilled (absent = clean record); past seasons' `yellowCards`/`redCards` backfill to 0 rather than being reconstructed, since archived cups have discarded the box scores that would make it uneven. **Rate, measured, and then raised** (`scripts/suspensionProbe.ts` on a 16-competition season, `scripts/cardRateSweep.ts` for the fast single-league version). Nothing had ever checked the booking rate, because cards had no consequence to make it matter; measured, the engine booked **1.42 yellows / 0.098 reds per match** against a real top flight's ~3.5-4.5 / ~0.15-0.25. `YELLOW_GIVEN_FOUL` was therefore raised **0.11 → 0.18** (2026-08-16, user call), landing **2.28 yellows / 0.181 reds** — about half the gap closed, with reds now inside their real band. Four things to know before touching it again: **(a) reds rise with roughly the SQUARE of it**, since a second yellow needs two bookings on one player (second-yellow dismissals 68 → 166 in the sweep while straight reds held at ~40), which is why `RED_STRAIGHT_GIVEN_FOUL` was left alone — the real red band is reached on second yellows alone and raising both overshoots. **(b) Cards cost goals indirectly**: every card calls `bumpEvent()` and stoppage is `STOPPAGE_SECONDS_PER_EVENT` per event, so a busier card sheet lengthens matches — measured at **+0.0105 goals/match** (3.0132 → 3.0237), inside seed noise, but it is the channel that breaks a benchmark if this goes much higher. **(c) Ban load scales super-linearly**: 1102 → **2497** bans/season across 320 clubs (3.4 → 7.8 per club, 1.03% → **1.93%** of appearances missed), because accumulation bans need five hits on one player (485 → 1223). **(d) The remaining shortfall is in FOULS, not cards per foul** — at 13.0 fouls/match the engine already books a higher *share* of its fouls than referees do, so going further means `FOUL_BASE`, which also moves free kicks and penalties. Rebased the `touchStats.test.ts` scoreline hash (the draw *count* is unchanged — `cardRoll` is drawn on every foul either way — but the branch taken moves, so more men are sent off and matches run marginally longer). UI: Dashboard ban list, `SuspensionBadge` on Roster/PitchField, profile header + per-season YC/RC columns, Leaders boards, God Mode "clear suspension". Deliberately **not** added to `ALL_TIME_STAT_KEYS` — that set widens every `ArchivedPlayer` row and `RETIREE_ARCHIVE_LIMIT` has already been cut twice to pay for row width.
- **Foul VOLUME is now a real top flight's, with set pieces held level (`FOUL_RATE_MULTIPLIER` 1.7, `BOOKED_FOUL_WEIGHT` 0.3, 2026-09-22).** Point (d) above, done. `simMatchDetailed` rolls fouls at `FOUL_BASE_DETAILED` (= `FOUL_BASE` × the multiplier) and **divides the penalty and free-kick chance per foul by the same factor, clamps included**, so the expected set pieces per tick are unchanged: more whistles, not more chances. A player already on a yellow is picked as the fouler 0.3× as often (`pickFouler`'s `bookings`, still one draw), which is what keeps reds in band — without it the sweep read **0.43 reds a match**, second yellows piling on the same men with roughly the square of the booking rate. **`simMatch` (the M1 benchmark path) is untouched** and keeps `FOUL_BASE` and the undivided constants; its golden snapshot is the proof.

- **Substitutions happen in WINDOWS, not at fixed checkpoints (`runSubWindow`/`trySingleSub` in `engine/matchSim.ts`, `SUB_WINDOW_*` in `engine/constants.ts`, 2026-09-08, user report "we don't get many subs").** `MAX_SUBS` has been 5 since M5 and was **unreachable**: `SUB_CHECKPOINTS_ELAPSED` held two moments (60' and 75') and `attemptSub` made at most ONE change at each, so two was the ceiling however deep the bench. Measured on a full season of the 626-club world before the change: **1.58 subs per team per match, 12% of team-matches making none at all**, and a minute histogram of two spikes (13,368 subs at exactly 60', 13,499 at exactly 75') against a scatter of ~40/minute that is entirely injury-forced. Now: five subs spent across **three in-play windows plus a free half-time one**, a window may bring on up to `SUB_MAX_PER_WINDOW` (3) at once, and the in-play moments are **jittered per side**. Result **4.18 per team per match with 56% of sides using all five**, against a real top-flight ~4.3-4.5. `scripts/subWindowProbe.ts` is the gate and reports the distribution, the windows used, and — the part that matters when retuning — **why** a side stopped short of five.
  - **A window is the unit the LAWS count, and that is the whole reason this is not just "more checkpoints".** Bringing on three players at once costs a manager one opportunity, not three. So `runSubWindow` loops while it can justify another change and spends an opportunity only if it actually made one; a window that produces nothing is free. **More candidate moments than windows** (four moments, three windows) is deliberate — with exactly three the budget would be inert and every club in the world would change at the same three minutes, which is the artefact being replaced.
  - **HALF-TIME MUST NOT GRANT THE FATIGUE RELIEF, THE FRESHNESS BONUS OR THE LATE MARGIN, and getting that wrong is the single biggest trap here.** A free window with a normal gate is a free lunch and every side takes it: measured, half-time alone produced **1.46 changes per team per match** — more than any other minute in the match and about four times the real half-time rate. None of the three arguments applies at the break: nobody is gassed at 45', fresh legs buy nothing against a man who is not yet tired, and there is a whole half still to play. The gate at half-time is therefore `SUB_HALFTIME_MARGIN` (1.5) alone, with **form still counting** — hooking someone having a shocker is exactly what half-time is for, and is most of what a real half-time substitution is. That lands it at **0.33 per team per match**.
  - **`SUB_LATE_MARGIN` is the gate learning something true, not a fudge to raise the count.** The quality comparison is two ovr values with no reference to duration, so it silently prices every swap as though the replacement plays the rest of the match; a man brought on at 85' degrades five minutes of composites, not forty-five. The tolerance therefore grows as the clock runs out, and it is **self-limiting** — largest exactly when what it buys is smallest. **The exponent is load-bearing and linear is the wrong shape**: linear hands out half the full tolerance at 45', which is more than the gap between a starter and a typical bench player, so it re-creates the half-time problem from the other direction. Cubic keeps 45' worth ~0.9 ovr, 75' ~4.5 and 85' ~8.4.
  - **CHAMPION POINTS RISES MONOTONICALLY WITH `SUB_LATE_MARGIN` — this is the number to watch, not the sub count.** Measured over 8 seasons: **80.0 / 81.4 / 81.9 / 83.3 at margin 4 / 6 / 8 / 10**, against a merge base of 78.75 and the M1 table-spread gate's 78-94 band. A deep bench gets more out of a late change than a thin one, so the champion pulls away slightly; the effect is real (monotone) rather than seed noise, though an 8-season sample carries ~1.8 points of its own error, so **re-measure over ≥15 seasons before reading a small move in it as a regression** (the gate's own note). Everything else barely moves: goals/match **3.1372 → 3.1697** and home-win rate **.4220 → .4112**, the latter comfortably inside the M1 gate's 38-46%.
  - **The jitter is drawn off MATCH INTRINSICS, never the shared `rng`** (`SUB_WINDOW_STREAM` 87, hashed off the first man named in each XI) — the same rule cup rounds and touch attribution follow, so no other outcome's draw order moves and a single match stays reproducible for the live viewer's re-sim. `SUB_WINDOW_JITTER_SECONDS` (180) is kept under half the smallest gap between two moments so a jittered pair cannot cross and reorder. **Moments are therefore per-side, which forces `firedCheckpoints` to be per-side too** — a single shared Set silently gives both sides the first side's schedule.
  - **Spending all five and then losing someone to injury leaves the side a man down, which is new and correct.** `forceInjurySub` has always gated on `subsUsed < MAX_SUBS`; it was simply unreachable when nobody got past two changes. It is the real cost of emptying your bench, and `injuries.test.ts` pins **both** branches (replaced while subs remain, not replaced once they are gone) plus asserts the man-down case is actually exercised, so the test cannot silently stop covering it.
  - **Stoppage is NOT pinned at its cap, so more subs really do lengthen matches** — measured mean 267s past 90' against a 120-600s range, rising to ~359s. Every sub calls `bumpEvent()` at `STOPPAGE_SECONDS_PER_EVENT`. It turned out to cost almost nothing in goals (+0.03/match), but the arithmetic that made it look dangerous is right and anyone raising these constants further should re-check it rather than assume the cap absorbs it.
  - **It changes DEVELOPMENT world-wide, which is why this needed a dynasty audit rather than just the benchmark gates.** Box-score lines are gated on actually appearing, so ~2.6 more players per team per match earn an appearance, and `appearances` is what feeds `minutesFactor` in `progressPlayer`. Bench players across all 626 clubs develop faster than they did.

  - **Extra time and concussion substitutions are deliberately OUT.** Extra time (`playExtraTime` in `core/cup/simCup.ts`) is a fixed number of shots with no clock, no fatigue and no personnel changes, so there is nowhere to put a substitution in it — the "+1 sub, +1 window in ET" law needs extra time rebuilt as a real period first, which is its own project. Concussion subs need an injury *taxonomy* the model does not have (one `injury` event, no type) plus the opponent-compensation rule, for something that fires perhaps once in fifty matches and is invisible on screen.
- **The two halves are REAL PERIODS, each with its own stoppage (2026-09-10, user report).** The clock had no half-time in it: `computeStoppageSeconds` was called once per half at `clock <= 0` and both halves' worth was played together at the end of the second. That is sound for the SCORELINE (every per-tick roll is memoryless, which is what the old comment argued) and wrong for everything a viewer reads — first-half stoppage never existed as a passage of play, no event could be stamped 45+1, and a first-half injury bought three minutes that were handed to the 93rd. Reported as "stoppage reads 90, 91, 92, 93" plus "first half stoppage isn't tracked".
  - **`clock` still counts down monotonically and still measures PLAYING TIME**, so `minutesFor`, `enterClock`/`exitClock` and `splitTwoLeggedEvents` (which reads a jump back UP as the leg boundary) are all untouched. What changed is that it runs past 0 by BOTH halves' stoppage rather than pausing at 90, and that the first half's is played where it happened. **`BoxScore.firstHalfStoppage` is the one number that bridges playing time and displayed minutes**; optional, and absent is EXACT rather than a guess (a box score written before this really did have a first half with no stoppage).
  - **STOPPAGE ROUNDS TO WHOLE MINUTES, and that is load-bearing rather than cosmetic.** A board shows an integer, and the display depends on it: playback is indexed by minute, so a half ending 2.5 minutes into stoppage leaves the second half's minutes straddling the break and nothing can label 45+3 or 46 exactly. Both clamp bounds are whole minutes, so rounding cannot leave the clamped range. `matchClock.test.ts` pins that no two playing-time minutes ever produce the same label.
  - **A GOAL CONSUMES CLOCK AND THE REFEREE CREDITS IT BACK, and BOTH halves are required.** `GOAL_RESTART_*` (55-95s, drawn on the MAIN rng because it changes how much football is left) is what stops two goals sharing a displayed minute — `dt` is 2-10s, so a goal cost nothing and back-to-back goals in one minute were routine, including straight after a kickoff. Crediting it to the half's stoppage is what keeps playing time unchanged, which is why this shipped without a rebalance. **Consuming without crediting deletes ~2 minutes of football a match — a scoring change wearing a presentation change's clothes.**
  - **A goal ALSO bumps the flat per-event allowance, and that reads like double-counting and is not.** It was removed on exactly that reasoning and measured back in: dropping it buys **24 seconds** of displayed stoppage and deletes **1.1% of the match's football** (shots/match -0.3% → -1.1% vs the merge base), because on the old model a goal credited 20s and cost nothing, so those seconds were inside the scoring calibration. `STOPPAGE_SECONDS_PER_EVENT` is not "celebration time"; it is the regrouping and the walk back.
  - **The detailed engine's board has its OWN function and cap (`stoppageBoardSeconds`, `STOPPAGE_BOARD_MAX_SECONDS` 480), and `computeStoppageSeconds`/`STOPPAGE_MAX_SECONDS_PER_HALF` (300) are byte-identical to before.** The 480 exists FOR the celebration credit: at 20s an event a half needs 12+ notable events to reach 300, so the raise is nearly inert on its own, but a clipped credit is playing time deleted from exactly the most eventful halves, a quiet negative feedback on scoring. It still binds at p95 in the second half; that residual is small and unfixed.

Half-time is now fired from the period boundary in the loop and removed from `sideMoments`. **Any new rule phrased as "how far into the match are we" must read `matchElapsedNow`.**

Note the render tests can only reach the *open* tab (tab state, no DOM env), so `playerProfileColumns.test.tsx` covers the league table alone — the cup table's correctness rests on the shared column list plus `playerStatColumns.test.ts`.

Goals conceded tracks the defence almost as much as the keeper, which is what dragged the Goalkeeper of the Year down. - **Worldwide awards — Ballon d'Or + World Team of the Year + Goalkeeper/Defender of the Year** (`core/worldAwards.ts`, `computeWorldAwards`, pure/re-runnable/rng-free) — the whole world judged as one field, stored as `SeasonHistoryEntry.world` (`WorldAwards{ballonDOr: WorldAwardEntry[10], worldTeamOfYear, goalkeeperOfYear?, defenderOfYear?}`), surfaced on `/awards`'s **World** tab (per-competition awards move under a "By league" tab) and in Player Profile honours. Score = domestic POTY/TOTS score **+ a league-strength correction** + Continental Cup + international + league title, each part kept on the entry so the UI can show *why* he won.
  - **The league-strength correction is the load-bearing bit.** Match ratings z-normalize *within* each competition, so an uncorrected worldwide award goes to whoever plays in the weakest league (dominating weak opposition scores identically). `leagueStrengthOffsets` adds `(comp mean ovr − world mean ovr) × WORLD_AWARD_LEAGUE_STRENGTH_WEIGHT` (0.05). Ovr is the yardstick precisely because it's the one player number that *isn't* normalized. It's a **unit conversion, not a difficulty knob** — 0.05 is the empirical rating-per-ovr slope inside a league; inflating it over-corrects and makes a strong league's mid-tabler outrank a weak league's best. Tier 2 needs no special-casing: its mean drags its own offset down.
  - **Cup ratings take no correction** — cup matches normalize against the whole pooled 32-club field (`cupMatchData`), making them the only directly cross-league performance number the sim produces. Cup run bonus is keyed by `cupRoundsFromFinal` (`cup/cup.ts`, counts *backwards* from the final so Swiss round 0 = QF and legacy round 0 = R16 don't collide), pro-rated by appearances so a bit-part player doesn't collect a winner's share.
  - **`WORLD_AWARD_CUP_MULTIPLIER` is 1.0, and the intuition that says it should be higher is measurably wrong.** It shipped at 1.5 on "cup goals are rarer, so worth more". They aren't: only elite attackers on the best 20 clubs play the cup, so its per-game scoring rate *matches* the league's (same player, 13 goals in 8 cup games vs 25 in 38 league games), and a premium double-counts. At 1.5 (with rating weight 0.5, run bonus 0.6) the cup component spanned 0-3.1 against a league component spanning 2.4 — nine games outweighing thirty-eight — and 2 of 8 audited seasons crowned a player with a *below-6.8-average* league season. Now 1.0 / 0.2 caps the cup's *individual production* term. Measured effect: winner's median world-ovr rank 259 → 123, and the 85-ovr rank-2 player correctly beat the 73-ovr rank-408 cup runner. **Residual, known and accepted:** the winner is ~top-100 of ~4,200 who played rather than top-20, because the shared `AWARD_OVR_WEIGHT` (0.06) is deliberately small so a big statline can edge out a higher-ovr player — the same trade the per-league POTY makes. Raising it would change the existing league awards too, so it wasn't touched unilaterally.
  - **Team achievement is weighted separately from individual cup production, and deliberately much higher (2026-07-27, user call).** `WORLD_AWARD_LEAGUE_TITLE_BONUS` 0.3→**0.8**, `WORLD_AWARD_CUP_RUN_BONUS` [0.35,0.2,0.1,0.05]→**[1,0.55,0.3,0.15]**, `WORLD_AWARD_WORLD_CUP_BONUS` 0.6→**1.4**. Sized by an explicit exchange rate against `POTY_GOAL_WEIGHT.FWD` (0.08): title ≈ 10 goals, cup ≈ 12, World Cup ≈ 17 — the intended hierarchy is World Cup > Continental Cup > league. **Raising these is not the same risk as raising `WORLD_AWARD_CUP_MULTIPLIER`**: a run bonus is uniform across a squad (modulo `involvement` pro-rating), so it can only move the award *between* clubs, never inflate a player above a better team-mate. The failure mode to watch is therefore "the award became a prize for being on the best team", measured as winner's world-ovr rank. Measured at the time, *before* `WORLD_AWARD_OVR_WEIGHT` existed, over 20 seasons (2 seeds × 10): winner won his league 55%→**65%**, wins the Continental Cup **40%**, World Cup winner in **2 of 5** tournament years; cost was winner's median world-ovr rank 61→108. **Those trophy rates were then partly given back by `WORLD_AWARD_OVR_WEIGHT` below — see its sweep for the numbers that actually ship.**
  - **`WORLD_AWARD_OVR_WEIGHT` (0.14) is an EXTRA ovr term applied by the world awards only**, stacked on top of the `AWARD_OVR_WEIGHT` (0.06) already inside `potyScore`/`totsScore` (2026-07-27, user call). Deliberately a *second* constant: the shared one also drives the per-league POTY / Golden Boot / Team of the Season, so raising it would silently retune three shipped awards to fix a fourth. Principled as well as convenient — every other input is z-normalized within its competition, making ovr the only cross-league-meaningful number, the same property `leagueStrengthOffsets` relies on. **It trades directly against team achievement, and the trade is inescapable:** at 0.14 the winner's median world-ovr rank is **8** (mean 31, worst 150, from 108/210/882), but Continental Cup wins fall 40%→**15%**. Scaling the team bonuses up ~1.8× to compensate restored trophies *and put the rank straight back to median 61* — both levers reorder the same ranking, so raising them together just cancels. The full sweep table lives on the constant. **Do not "fix" the cup rate by raising the team bonuses; that has been measured and it cancels.**
  - **The Ballon d'Or is structurally a striker award — a formula property, not a tuning accident, and only partly mitigated.** Its base is `potyScore`, which contains **no defensive stats at all** (tackles/interceptions/saves live only in `totsScore`), so a CB's entire case is `avgRating` + the ovr terms. The higher per-goal weights for defenders (0.14 vs a striker's 0.08) can't compensate, because they multiply a stat defenders barely accumulate: a striker's 26 goals are worth 2.08 points while `avgRating` across the whole winner pool spans just 6.75–7.49. Before `WORLD_AWARD_OVR_WEIGHT` the split was **75% ST and 0% CB/DM/CM/GK — no defender, holding mid or keeper ever reached the top 10**; at 0.14 it is **45% ST / 30% AM / 20% W / 5% FB**, i.e. raw quality is now the only route in for a non-attacker. **Resolved 2026-08-24 by NOT touching this formula** (user call): rather than give the Ballon d'Or defensive terms, keepers and defenders got awards of their own (next bullet). The Ballon d'Or's arithmetic is byte-identical, so no save's past winners moved. The World XI is unaffected either way (fixed slots off the balanced `totsScore`).
  - **Goalkeeper of the Year + Defender of the Year (2026-08-24)** — `positionAward` in `worldAwards.ts`, ranked shortlists of `WORLD_POSITION_AWARD_SHORTLIST` (5) on `WorldAwards.goalkeeperOfYear`/`defenderOfYear`. **Scored on `worldTotsParts` — the same number that picks the World XI's slots — not on a new formula**, so the Goalkeeper of the Year *is* the World XI keeper **by construction, not by tuning**: `positionAward` takes the max over the GK group and `pickWorldTeam` takes the max over GK-slot candidates, which is the same set and the same score (both apply the qualified-first rule identically). Same argument makes the Defender of the Year always one of the World XI's back four. Measured 100%/16 seasons, but the proof is the reason, not the sample — and see the trophy-multiplier bullet for how nearly this was lost. GK pool = the `GK` group, defender pool = `DEF` (CB+FB, user call; DM stays in MID). Ties break on score → `avgRating` → pid, deliberately **not** the Ballon d'Or's goals+assists, which is meaningless for a keeper.
    - **The three worldwide awards now share `worldAwardParts`**, which takes a base score and a pair of cup weight columns and adds every cross-competition term (strength, extra ovr, Continental Cup, international, league title, domestic cup). Ballon d'Or passes `potyScore`+POTY weights, both position awards pass `totsScore`+TOTS weights. **That is the entire difference between them.** The refactor preserves left-to-right float association, so Ballon d'Or output is bit-identical (45 existing award tests unchanged).
    - **Only ever compares a group against itself, and that is correctness, not scoping.** `totsScore` is a *within-position* statistic (see `TOTS_SLOTS`' note): it pays a defender 0.03/tackle against a forward's 0.01 on a stat defenders collect in far greater volume. Any future "best outfielder" award built on it would be measuring nothing.
    - **`WORLD_TOTS_TROPHY_MULTIPLIER` (3, 2026-08-24, user call) scales every part of the score EXCEPT `league`** — Continental Cup, international, league title, domestic cup — **inside `worldTotsParts`, i.e. for every award on the `totsScore` base: the World XI and both position awards.** The Ballon d'Or (on `potyScore`) is untouched. **The problem it solves is dilution, not a missing term:** trophies were already there at full Ballon d'Or weight, but `totsScore` pays 0.03/tackle and 0.03/interception, so 200 of each is 12 points of a ~21-point score and a league title's 0.8 is under 4% of it — against ~16% for the same title on a striker's ~14-point Ballon d'Or.
      - **It is also the fix for the weak-league drift below — but by a narrower mechanism than it looks, and the first version of this note got it wrong.** The multiplier does **not** touch ovr or `leagueStrengthOffsets`: both sit inside `league`, the one part deliberately left alone, so if anything it makes them a *smaller* share of the total. The whole effect comes from the two multiplied terms that are cross-league-meaningful by themselves — the **Continental Cup** run (weak leagues' clubs rarely go deep) and the **international** campaign (weak nations rarely win). The other two, league title and domestic cup, are *league-relative* (Belgium's champion wins Belgium as surely as England's wins England) and contribute nothing to it. Corollary worth holding onto: diluting ovr is precisely *why* the keeper's median ovr rank slipped 3 → ~8 — one lever, both effects.
      - **Applying it at the shared base rather than at the awards is the load-bearing detail, and it was got wrong first.** It shipped for a few hours on the two position awards only, leaving the World XI on the plain score — which looked like the conservative choice (don't retune a shipped award) and wasn't: the XI slot then went to the best performer while the award went to the best performer who *also won things*, so the Goalkeeper of the Year stopped being the XI's keeper **about two thirds of the time** (17% and 50% agreement measured), on two panels of the same page. **A correction that belongs to a shared base has to be applied at the base, or everything built on it quietly stops agreeing.** Fixed by folding it into `worldTotsParts`; the by-construction agreement above is restored and re-verified at 100%.
      - **Measured, 2 seeds × 6 seasons, against the same runs' Ballon d'Or at 10/12 big-four winners:** keeper winners from the big four **12/16 → 11/12**; defender **9/16 → 9/12**; defender winners from Belgium/Turkey **5/16 → 1/12**; defender score from tackles+interceptions **50% → 37%**; defender's worst ovr rank **112 → 25**. Pool the season-measurements; never take a median of per-seed medians.
    - **`WORLD_AWARD_TROPHY_STRENGTH_WEIGHT` (0.06, floor 0.25, cap 2, 2026-08-24, user call) scales the league title and the domestic cup by how strong the league that awarded them is** — `clamp(1 + ovrDelta * weight)`, applied in `titleComponent`/`domesticCupComponent` and therefore to **all three worldwide awards including the Ballon d'Or**. Those two are the only *league-relative* trophies (every country crowns a champion regardless of standard), which is exactly the gap the trophy multiplier's note identifies as contributing nothing to league strength; the Continental Cup and international campaign are contested between leagues and correctly take no scale. The **floor is for the domestic cup, not the title**: a tier-2 league title scores 0 anyway, but a tier-2 club really can win its domestic cup, and a second division sits far enough below the world mean to drive the raw scale negative — turning a trophy into a penalty. `leagueStrengthOffsets` now returns the **raw ovr delta** and callers convert (rating units for the match-rating correction, this scale for trophies), so there is one measure of league strength rather than two.
      - **Measured, 2 seeds × 6 seasons: real but narrow.** 2 of 12 keeper winners changed, both toward stronger leagues (Portugal → England on one seed); **0 of 12 defender winners and 0 of 12 Ballon d'Or winners moved**. Beyond-league score share rose ~1-3 points.     - **The weak-league drift is NOT caused by weak leagues inflating the counting stats — measured and disproved (`scripts/leagueVolumeProbe.ts`, 2026-08-24).** That was the standing explanation here and it was wrong; every observation behind it came from award *winners*, who are maxima. The test is `isUserPlayer`: `clubs.includes(userTid) || tid === userTid` — `clubs` is *appearances*, so it means "played for you" past or present, which is the question an all-time board asks; the `tid` half is there because a just-signed player with no league game yet is shown wearing the user's crest and would otherwise read as a bug.
- **Retiree archive** (`core/players/archive.ts`, `LeagueStore.retiredPlayers`) — the permanent career record the all-time lists read, since `simOffseason` step 3 **deletes** retirees from `players` outright. Distinct from `players/retirements.ts`'s `RetiredPlayer` (a per-season farewell notice capped at `RETIREMENT_NOTABLE_LIMIT`, attached to one `seasonHistory` entry) and deliberately not merged with it. **Volume is the whole design constraint:** measured 661 retirees *per offseason* on a 240-club world (~66k rows/100 seasons ungated — the 88 MB save shape again), of whom only 351 ever made a senior appearance and 16.5 ever peaked at ovr 70. Two defences: a quality gate (`isArchiveWorthy`: ≥1 senior appearance **and** (`RETIREE_ARCHIVE_MIN_PEAK_OVR` 70 **or** `RETIREE_ARCHIVE_MIN_APPEARANCES` 200)) and a hard `RETIREE_ARCHIVE_LIMIT` (**20,000** as of 2026-08-22, was 2000 — see the schema-v3 entry under "Split player storage" for why the old value was bounding *write latency* rather than disk, and `scripts/archiveGateProbe.ts` for the ~270-a-season rate it is sized against) that prunes by **career score, not age**, so a long dynasty keeps its season-3 legends and drops its season-97 journeymen. **Honours are NOT stored** — every award is already on `seasonHistory[].awards`/`.world` keyed by pid, so they stay derivable forever. *Derivable is not the same as resolvable*: the award survives, the man it points at does not, which is what `SeasonHistoryEntry.awardWinners` exists to fix (next bullet). `peakOvr` reads `hist` (retirement rolls *after* progression's final decline, so `player.ovr` is a rating he never played at); best-single-season goals/assists *are* stored, being unreconstructable once the stat lines go. Row shape is `seasons: ArchivedSeason[]` (`{season,tid,ovr}` per season played — raw data, deliberately not a snapshot of derived honours; see GOAT gotcha (c)) + `totals: StatTotals` + `best: BestSeasons` (every key in `ALL_TIME_STAT_KEYS`, each best carrying `{value, season, appearances}` so the rate-stat floor applies to retirees too) — generic rather than a handful of named fields, so a new leaderboard stat needs no archive change. That widened the row ~3×, which is why `RETIREE_ARCHIVE_LIMIT` came **4000 → 2500 → 2000** (the second cut paid for the per-season line) to hold the same save-size budget. Pure/rng-free → sim results bit-identical. Migrated to `[]`; old saves' pre-existing retirees are unrecoverable (deleted without a trace) and the UI says so.
  - **Retirees are clickable and have a career page (2026-08-11).** `/player/:pid` falls back to the archive when the pid isn't in `players` and renders `ui/pages/RetiredPlayerProfile.tsx` instead of "Player not found" — so *every* historical link works, which was the point of keeping the record in the first place. Two shared pieces make that hold everywhere rather than on one page: **(a)** `computeArchivedHonors` (`core/playerHonors.ts`) — the honours walk is now parameterised by "which squad was he in that season" (`Player.stats` vs `ArchivedSeason`), so living and archived players share one derivation and can't drift (same reason `goat.ts`'s `computeHonours` exists as its sibling; the two still must agree). **(b)** `usePlayerRefs`/`PlayerRefLink` (`ui/components/PlayerRefLink.tsx`) — pid → name/nationality across the pool *and* the archive, used by every surface that used to print `Player 4821`: News Feed, Transfers, Finance, Club History, World Cup scorers, Season Preview's farewell list. **Cached in a `WeakMap` keyed on the `LeagueStore` object, not `useMemo`** — it renders once per row on lists of dozens, and a per-instance memo rebuilds the ~6000-entry map for every one of them; the context hands out a fresh league object per commit, so identity is the right key. Awards resolves winners through a local `AwardSubject` (live player first, then archive) so an old season's POTY/Golden Boot/TOTS board doesn't blank out slot-by-slot as its winners retire; the retiree chip is the same chip minus the attribute tooltip, and his Ballon d'Or stat columns show "—" (per-season lines don't survive archival). `OvrHistoryChart` now takes loose `points` + `pid`/`name` rather than a `Player`, since a retiree has no `hist`. The page deliberately shows *less* than a living profile (no attributes, no per-season stat lines) rather than faking it, and a retiree below `isArchiveWorthy` still renders as an unlinked name — callers must keep their fallback.
- **Award winners carry their own names (`core/awardWinners.ts`, `SeasonHistoryEntry.awardWinners`, 2026-08-21).** Every award is stored as a bare pid (`playerOfSeasonPid`, `goldenBootPid`, `teamOfSeason[]`, `world.ballonDOr[].pid`, `world.worldTeamOfYear[]`), and a pid stops resolving the moment retirement deletes the player and the capped archive declines to keep him. Measured across four real saves, winners resolving to *nobody*: **11 seasons 0/11 Ballon d'Or and 8/176 (5%) league POTY; 32 seasons 0/32 and 152/512 (30%); 100 seasons 30/100 and 1,177/1,600 (74%)**. The league POTY goes first and worst because it is per competition — a second-division or weak-league winner is exactly the modest career `isArchiveWorthy`/the archive-score prune drops first — while the Ballon d'Or lasts longer only because its winners are elite. `snapshotAwardWinners` copies name/nationality/pos/`ovrDuringSeason`/`SeasonStats.tid`/born for every pid a season's awards name, at **offseason step 3.65**, off `league.players` (still the pre-progression, pre-retirement pool both award passes scored). Pure, no rng draw, so sim results are bit-identical. **Measured cost: 190 winners = 18.5 KB/season on the 16-competition world, ~1.8 MB per century** (14.5% of a season-history entry) against a save already 12.9 MB after one season; `scripts/awardWinnerSize.ts` re-measures it. **The obvious alternative, exempting winners from the archive prune, does not scale and was rejected on arithmetic**: 16 competitions × 13 places is up to 229 pids a season, 10-20k over a century, against a `RETIREE_ARCHIVE_LIMIT` that was 2,000 rows at the time (20,000 since 2026-08-22). Three consequences. **(a)** Read order everywhere is career → archive → snapshot; `frivolities/honours.ts` also *stands a `CareerRow` up from the snapshot* for a decorated player the save has otherwise forgotten, or the "most decorated careers" board silently omits most of its own winners — those rows carry empty `totals`/`best` and are built **only** inside `computeAwardTrivia`, never mixed into `allCareers`, where a row of zeroes would land on every statistical leaderboard. It is also what makes a forgotten winner's award credit his club and his country, which a bare pid could not. **(b)** A snapshot-only winner has **no profile page**, so `PlayerRef.linkable` / `AwardSubject.linkable` are false for him and his name renders unlinked; `Frivolities`' `PlayerCell` now gates on `linkable`, not on mere existence. **(c)** `migrate.ts` backfills past seasons from the live pool then the archive — complete for a young save, partial for an old one, and **it must run**: this is the one thing that genuinely cannot be reconstructed later, so migrating freezes the loss where the save currently stands. It never refreshes an entry that already has the field (anything missing then is missing now; deletion runs one way). **`loadLeague` writes that backfill straight back to disk** (`namedAwardWinners` alongside `shrankOnLoad`) — the one migration whose result must be persisted rather than left in memory, since every other backfill recomputes identically next load while this one copies names off players the next offseason deletes for good. Fires once per save, since afterwards every entry has the field.
- **The name table: the archive's cap was the bug, and splitting the row fixes it at the source (`core/players/playerNames.ts`, `LeagueStore.playerNames`, 2026-08-22).** `ArchivedPlayer` answers "what was his career" — totals, a best season per ranked stat, a line per season — which costs **2,204 bytes** and is why `RETIREE_ARCHIVE_LIMIT` capped it at 2,000 when this was written. "What was his name" is a different question with a different shape: five fields, **82 bytes measured**, wanted for *every referenced pid* rather than the best 2,000 careers. Conflating them is what made a long save forget itself — at season 101 the prune bar had risen to **peak ovr 79** and 78% of historical pid references resolved to nobody. `extendPlayerNames` writes a row at retirement for each retiree the surviving history still points at; `playerNameIndex` is the read side, wired into `usePlayerRefs`, `Awards`' `subjectResolver` and `honours.ts`'s `identity()`. Measured over a simmed dynasty (`scripts/playerNameProbe.ts`): **nameless references 0 in every season**, table ~**300 rows / 21 KB per season** (~4 MB at season 159), against an archive already 448 KB by season 9. Pure, no rng draw, appended after everything else, so sim results are bit-identical. Four points worth keeping. **(a) Only retirees need a row, and the asymmetry is load-bearing**: `cullFreeAgentPool` deletes its victims' transfers, news events and cup lines *along with them*, so a culled nobody strands nothing; retirement deliberately keeps those records, which is exactly why the name has to be kept too. **(b) Bounded by construction, never by a cap** — a row exists only for a pid something references, so the table cannot outgrow the records pointing into it. A fixed cap is precisely what `RETIREE_ARCHIVE_LIMIT` does and it is the bug; the economics agree, since names are ~5% of the cost of the ~900 KB/season of history that references them. **(c)** It is a name, not a career: `linkable` stays false and there is no profile page. **(d) Forward-only.** `migrate.ts` backfills `[]` and deliberately reconstructs nothing — the live pool, the archive, the farewell lists and the award snapshots are all read directly by the UI already, so copying them in would duplicate rows that resolve anyway and still name nobody new. Same one-way door `awardWinners` documents.
- **The farewell lists are a fourth name source, free and retroactive (`farewellIndex`, `core/players/retirements.ts`, 2026-08-22).** `awardWinners` above stops the loss *going forward*; it does nothing for a save that has already lost its winners, because `migrate.ts` can only backfill from the pool and the archive — the two places that already resolve. Measured on the real 100-season save: the backfill moves named award places **30.2% → 30.2%**, i.e. nothing. Its whole value is freezing the current 30% before the next offseason takes more of it. What *does* recover ground is `seasonHistory[].retirements.notable`, which has been copying name/nationality/pos down since long before either field existed and was never read as a name source. Folding it in as the last tier of `usePlayerRefs`, `Awards`' `subjectResolver` and `frivolities/honours.ts`'s `identity()` recovers, on that same save: **award places 30.2% → 34.9% (+1,056), transfer rows 21.7% → 24.8% (+9,323), news events 22.2% → 26.7% (+11,343), cup stat lines 26.9% → 33.5% (+2,268)** — verified by `scripts/farewellRecoveryCheck.ts`, which also asserts no reference *stops* resolving. **Read-only and derived, so there is no schema change and nothing to migrate** — an old save gets these names back on load. Bounded by `RETIREMENT_NOTABLE_LIMIT` a season (~1,500 entries per century), so the index is cheap to build per league object. Two gotchas. **(a)** A farewell row records his **final** season, so its `ovr`/`tid` describe a different season from any earlier award — `AwardSubject.ovr` is therefore `number | undefined` and the Team-of-the-Season chip shows no rating rather than a confident wrong one; `honours.ts` takes the name and leaves `born` null instead of deriving it from his retirement age. **(b)** It is a name, not a career, so `linkable` is false — and **that flag must be tested, not the ref's existence**: `SeasonPreview` gated its farewell table's profile link on `refOf(pid)` being truthy, which was already wrong for award-snapshot pids from the previous bullet and became wrong for every retiree once this tier landed (an existing test caught it). The remaining ~65% on that save is genuinely unrecoverable: nothing ever wrote those names down.
- **Career honours on a Player Profile** — `core/playerHonors.ts` (`computePlayerHonors`, pure/derived, no schema change), the sole source of the profile's "Awards & Trophies" pills. Individual awards (Ballon d'Or, World XI, POTY, Golden Boot, TOTS) are stored by pid so they need no attribution; a **league title is a team honour and must be attributed**, and the gotcha is *what you attribute it with*. It reads `Player.stats[season].tid` — `accumulateStats` (`simThrough.ts`) opens a stats row for **every player on either roster** each matchday (not just those who appear, verified against a simmed season), so that row is the game's only per-season squad-membership record, and it's the same signal `clubHistory.ts` attributes award pids with. It must **not** use `teamForSeason`: that walk guesses at seasons before a player's first recorded transfer and falls back to his *present-day* club, which handed every arrival the club's whole back catalogue of titles — including seasons before he was generated (the bug this replaced). Known limitation, shared with open decision #4: `stats.tid` is the club he *finished* the season at, so a winter arrival at the champions is credited and a winter departure isn't.
  - **Sibling of `frivolities/goat.ts`'s `computeHonours`, and the two must agree.** They exist separately for a real reason — this one takes a live `Player` for one profile, that one makes a single pass over history for *every* career including archived retirees, who have no `Player` at all — but they answer the same question and a divergence shows up as a profile and a GOAT row disagreeing about the same trophy. `goat.test.ts` pins them together for a living player; change the attribution rule in one and fix the other.

**The Database (`/database/players`, `/database/clubs`, 2026-09-08, user ask)** — every player and every club in the world in one sortable, filterable table. Pure and derived, **no persisted field, no migration, no rng draw**, so no dynasty audit and no scoreline rebase.
- **Potential is sorted and filtered through the SCOUTING FOG, and that is a correctness requirement rather than a nicety.** Ordering rows by the true potential while displaying a band leaks the hidden number **silently** — no error, just a ranked list that answers the question the whole scouting/difficulty model exists to keep open. `ui/potentialView.ts` is now the single place that decides what the user may know (God Mode first, then the user's per-pid scouting tenure); `PotDisplay` and `PlayerProfile` — which between them held **four** copies of that logic, including the value chart's priced midpoint — go through it, so a fifth surface can't drift. **Known, pre-existing and deliberately NOT fixed here: the Transfers search's own POT filter still tests the true value** (`playerMatchesFilters` defaults to it), so a min-POT filter there is a narrow leak that predates this page; the accessor parameter is the seam to close it through.
  - **The rule is "sort by a number the reader can SEE", and it settled on the band's TOP rather than its midpoint (2026-09-08, user call).** `ceiling` is what every POT column sorts and filters on. The cell reads "70–86", so a reader tracking the right-hand number down the column watches it descend and the order explains itself; a midpoint nobody can see leaves a column that looks unsorted. **Measured, it costs nothing in leak** where rows are equally scouted: the band is `potential + shift ± a half-width identical for everyone at that tenure`, so top, middle and bottom are **one ordering shifted by a constant** — over 4,000 synthetic 12-player trial groups, top / middle / bottom put the true best player in row 1 on 71.7 / 71.2 / 71.6% (chance 8.3%, true potential 100%). Two things checked before adopting it: the `RATING_MAX` clamp catches only **31 of 15,650** players on a fresh world at default scouting — **but that reassurance did not survive a real save, and the correction is the point.** Opened in a browser on a season-5 save the clamp caught **151 of 10,106 (1.5%)**, so a POT-descending sort opened with a page and a half of `–99` rows in arbitrary order, a 33-overall teenager above an 89-overall international. The fix is `PlayerDbRow.scoutedPotFloor`: the sort key is `ceiling + floor/100`, ordering strictly by (high, low) with no second comparator, and the floor is the *other* number already printed in the cell, so the column still ranks on nothing the reader cannot see. **The generalizable bit is the measurement, not the fix — a clamp rate measured on a fresh world at one scouting spend is a lower bound on what a played save does, and this file's own "barely ever clamps" line was written from exactly that lower bound.** The second check: where tenure *differs* it does reorder, giving an unscouted player **+6.38 rating points** over the identical player scouted (midpoint: +0.39). That last is accepted rather than a flaw — he genuinely might be that good and the cell says so, and it is the only rule under which a mixed-tenure column still reads as sorted.
  - **Price on the MIDPOINT, sort on the ceiling, and `buildPlayerRows` takes both accessors so the two cannot be conflated.** They answer different questions: a price is an expected value, so pricing every unscouted player at his best case would inflate the column for no reason beyond nobody having scouted him. `trueTransferValue` pays a premium for an unfulfilled potential gap, which is what makes the distinction load-bearing rather than stylistic (and why `careerValueHistory` already priced on the midpoint).
  - **The same leak was live on FOUR shipped pages and this is the fix's real value (2026-09-08).** `pot: (p) => p.potential` — the true number — was the sort accessor on **Youth Intake, Academy, Free Agents and Loans**. Youth Intake is the severe one: it opens **sorted by true potential descending against `YOUTH_TRIAL_SIGN_LIMIT` (5)**, so the top five rows *were* the five to sign, every time, and CLAUDE.md's own claim that "the fog on potential is what makes 5-of-12 a real call" was false in practice. Free Agents was next worst because its `ovr + potential` pre-sort decides **which players are listed at all**, not merely their order, so the fog was bypassed before the table rendered. `test/ui/potentialSort.test.ts` greps all five pages for the accessor shape and pins that the regex matches the old line and not the new one — a behavioural test cannot catch this, since both orderings render a perfectly plausible table.
  - **It came back on a SIXTH surface within a day, through a PR that merged in between, and the guard did not fire (2026-09-09).** #340's loans-in feature added two more tables that render `PotDisplay` and sorted them by the true value — `pot: (c) => c.player.potential` on the loan-offer table and `pot: (t) => t.player.potential` on the loan-target search. The guard's regex was `\w+\.potential`, which matches `p.potential` and **not** `c.player.potential`, so it passed green while two surfaces leaked; it is now `[\w.]+\.potential`. **Two things generalize.** A grep-based guard is only as wide as the shapes its author happened to have in front of them, so widen it to the *category* rather than the instance and assert directly that it still matches the old line (this file's test does, which is what makes the widening checkable rather than hopeful). And **this leak's natural rate of return is high**: every new surface listing players wants a POT column, `PotDisplay` makes showing the band the easy default, and sorting by `player.potential` is the obvious next keystroke — so expect it on the next such page rather than treating the fix as finished.
- **It pages, and that is the one thing not to relax.** 15,650 players against a `/transfers` freeze that was 10,684 elements and 2,066 flag images at a **147ms** JS render — the app's only known performance failure is DOM weight, and it is invisible to every JS measurement. So `PLAYER_DB_PAGE_SIZE`/`CLUB_DB_PAGE_SIZE` are 100, parallel numeric columns are plain text, and the only art is one flag per player row (clubs carry none). Measured: player overview **2,488 elements / 100 images**, attributes ~3,400, clubs' 16-column season set **under 3,500 / zero images**. `databaseRender.test.tsx` pins **every** column set rather than the narrow default, which is why the column set had to become URL state — a budget that only measures the cheap view guards nothing.
- **Filter, then sort, then slice.** Filtering after the slice shows "the first hundred of whatever ranked globally", which looks right and is not. The filter predicates moved out of `core/transfers/recommendations.ts` into **`core/players/playerQuery.ts`** so the database and both transfer searches answer "does this player match?" the same way; `playerMatchesFilters` gained a `potentialOf` accessor precisely so a surface that *displays* an estimate can *filter* on it.
- **The league filter is a `CompetitionScope`, and "top 5 leagues" is DERIVED from the world's own strength ladder** (`strongestCountries`, ranking countries by their top flight's `competitionStrengthOffset`), never a list of country names — the world is editable in World setup, so a hardcoded `["England", "Spain", …]` would go on claiming to be the strongest leagues in a world where it is not. `scopeCompIds` returns **null for "everything"** rather than a set of every id, so the 626-roster scan skips the membership test on the common case. Transfers took the same control, since it is the same question.
- **Two sort keys collide between the attribute and stat column sets, and it fails silently.** `crosses` and `interceptions` each name both an attribute and a counted stat, so one flat key space lets a header sort by the other one — on two columns of sixteen, with no error. Stat keys are therefore namespaced `stat_*`, and a test pins both readings of both names.
- **The club table reads strength off `computePowerRankingSnapshot`, not a fresh `computeTeamRating`.** Same number the Power Rankings page shows, and one pass covers rating, form and record; the money columns are Finance's own figures. A test pins the club rows to that snapshot, because two pages disagreeing about how good a club is reads as a bug. Two things it refuses to invent: a standings table over no matches is array order rather than a ranking, so the position column reads "—" until something is played (the gate Finance's "1st of 20" line already uses), and a loan or a free move is not a fee.
- **The Clubs tab CRASHED on every save that had kicked a ball, for three days, and the shape of the miss is the lesson (2026-09-11, user report).** `buildClubRows` built each division's table from that division's club ids but handed `computeStandings` **the whole world's `league.played`**; `record` does `rows.get(tid)!` and dereferences undefined on the first fixture from another division, so the page threw into the error boundary. It survived review, its own test file and a browser check because **all three only ever saw a fresh world** — `clubDatabase.test.ts` builds `makeLeague(0, 4)` and even asserts `expect(league.played).toHaveLength(0)`, and matchday 0 is the one state in the game where this cannot fire. **Every other caller of `computeStandings` filters** (`Standings`, both Dashboards, `Finance`, `clubSeason`, `manager/index`, `seasonQualification`); this was the only one that didn't, which is also how to check the next one. Now bucketed by the home club's competition in one pass (36 competitions × ~10,500 matches is 36 scans as a filter, one as a bucket), skipping any match whose two clubs are in different divisions. The regression test hand-builds two fixtures in two divisions rather than simming a season — the fault needs two matches, not minutes of sim — and was verified to fail without the fix with the user's own error text. **The generalizable bit: a page whose fixture is a FRESH world is untested against the state it spends its life in.** Same trap as the Database's season picker defaulting to an empty season, one bullet down.
- **Career totals go through `totalsOf`** (Frivolities' own fold) and are built **on demand**, not inside `buildPlayerRows` — the walk is every season line of every player in the world, and only one column set reads it. The season view narrows to players the season has a record of (`accumulateStats` opens a line for every matchday squad member, so *having a line* is the squad-membership record) and shows the club he played for **then**, off `SeasonStats.tid`.
- **Filters, sort and season live in the URL** (`ui/databaseUrl.ts`), writing only what differs from the default — a query string full of empty parameters makes "did I filter this?" unanswerable at a glance. Reading is lenient field by field, so a stale or hand-edited link opens rather than failing.
  - **The CLUBS tab held its sort, scope and name filter in `useState` and so was not shareable at all, while the changelog and this entry both claimed it was (found in a browser, 2026-09-08).** Only `cols` went through the URL, so `?sort=wages` was accepted into the address bar and silently ignored — worse than not supporting it, because the link looks like it works. Both tables now read the same four parameters (`in`, `q`, `sort`, `dir`) off `useSearchParams`. **An unrecognised sort key falls back to the default rather than to nothing**, on both tabs: `sortRows` returns the natural order for a key with no accessor, which on the clubs table is power-ranking order and therefore looks convincingly like a sort — the failure the leniency promise above exists to prevent. `clubSortKeysFor` mirrors `sortKeysFor` so switching column sets resets a sort the new set has no header for.
  - **The season picker defaulted to the season being PLAYED, which is empty on matchday 1 (found in a browser, 2026-09-08).** `league.played` is emptied at the rollover, so at the top of a new season nobody has a stat line yet and the Season tab opened on "0 of 10,106 players match" on a save with four seasons behind it. The second half is what made it read as broken rather than empty: the picker's options are exactly the seasons that *do* have lines, so a `<select>` whose value is not among them falls back to displaying its first option — the tab said "2029" while the table was showing 2030. It now defaults to the current season only when that season is in `seasonsWithStats`, and to the newest that is otherwise. **The general shape: a `<select>` whose value can fall outside its own options will lie rather than error, so any defaulted picker must pick from the list it is about to render.**

**Overview / Attributes / Performance on the tables you shop from (`ui/playerViews.tsx`, 2026-09-11, user ask)** — one switch above Transfers' two tables, Free Agents, the Watchlist, the national Player Pool and My Squad. The Database had column sets and these didn't, and these are where the decision is actually made ("performance first, attributes second, ovr third", picking an international squad). Columns come from the Database's own definitions (`SKILL_LABELS`/`SKILL_ABBREV`, a nine-key subset of `STAT_COLUMNS`), so a header reads the same wherever it appears; each page keeps its identity block and its action column and swaps only the numbers in between. Pure and derived, **no persisted field, no migration, no rng draw**, so no audit and no scoreline rebase.
- **The view is URL state (`?view=attributes`), and that is what makes it TESTABLE rather than merely linkable.** A view in `useState` cannot be reached by `renderToStaticMarkup` and there is no DOM test env here, so the wide sets — the ones a DOM budget is actually for — would have been unguarded, exactly as `Database.tsx` records for its own column sets. `usePlayerView(param)` takes a parameter name so Transfers' two tables get one each (`view`, `searchView`), and uses `setParams`' **functional** form so it can't discard another param written in the same handler.
- **The failure a column switch invites is MISALIGNMENT, not a crash**: a branch emitting fifteen headers and fourteen cells shifts every number one column left, renders perfectly and reads as nonsense. `playerViews.test.tsx` therefore counts header cells against every body row's cells for **every page in every view** (15 cases), with a vacuity guard so a page that rendered no table can't pass by rendering nothing.
- **A sort must not survive into a view with no header for it** (`viewKeepsSort`), or `sortRows` quietly orders by wage while showing attributes and the table reads as unsorted. Skills and `stat_*` keys are recognised centrally; each page passes its own `overviewOnly` list. Stat keys stay namespaced for the documented reason — `crosses` and `interceptions` each name both an attribute and a counted stat.
- **Match rating needs a qualifier or sorting on it is worthless**, since an average over one or two games tops any list. `viewSortAccessors` takes the rows and sinks anyone under `RATING_LEADER_QUALIFY_FRACTION` of the most appearances *among those rows* below the regulars (Stat Leaders' own rule; relative to the rows because these tables mix 22- and 38-game divisions). A player with no line at all sorts below both, rather than landing mid-column with no number in it.
- **The Player Pool sorts BEFORE it slices**, over every eligible player rather than the forty shown.
