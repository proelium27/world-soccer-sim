## Open design decisions (need a user call before coding)

From the 2026-07-11 bug hunt; each has more than one reasonable fix — discuss options first:
1. **Winter-sale wage dodge** — season wages charged once at offseason settlement against the current holder, so selling a high earner in winter dodges his whole season bill. Pro-rate, charge-at-transfer, or accept+document.
2. **Deficit at the 30-man cap** — the "no club runs a deficit" tuning was only proven for the 25-man composition; a stacked full user squad with a low finish can go negative. Retune, cap scouting relative to wages, or allow user deficits + add debt UI.
4. **Mid-season transfer stat attribution** — `SeasonStats` is one running total; Leaders/Roster credit the whole line to the *current* club. Per-stint stats (schema change) or a "joined mid-season" UI marker.
6. ~~**Unbounded save size**~~ — **RESOLVED 2026-07-25, see "Save size & the free-agent cull" below.** ⚠️ Note the framing here is *wrong*: this was diagnosed as the cause of the `/transfers` freeze, and it is not. The freeze is an uncapped DOM list (see "The `/transfers` freeze — root cause"). Save size was a genuine, separate problem. Original measurement kept here because it's the reference baseline: **Unbounded save size — the real cause of the "transfers page freezes" reports (measured 2026-07-25).** The save grows without bound and **every mutation writes the whole object to IndexedDB** while **every sim `structuredClone`s it to the worker** — both block the main thread, both scale with total size, so the whole app freezes and it gets worse the longer you play. Measured on a fast desktop (`scripts/leagueSizeTiming.ts`): season 1 → 9 MB / clone 67ms / save 75ms; season 9 → 59 MB / 716ms / 542ms; season 14 → **88 MB / clone 4230ms / save 2756ms**, growing superlinearly. Mobile is 5-10× slower, matching production INP on `/transfers` (p50 6.3s, p75 **31.5s**, worst 539s) — and `/dashboard` is nearly as bad, because **it is not a transfers-specific bug at all**. Per-field at 14 seasons (`scripts/leagueSizeBreakdown.ts`, `scripts/leagueSizeDeepDive.ts`): `players` 56.2 MB (64%; `hist[]` **34.0 MB** / 127k rows, `stats[]` 16.0 MB), `cupHistory` **18.6 MB** (21%), `transfers` 5.2 MB, `powerRankingHistory` 4.0 MB, `newsEvents` 2.4 MB. Candidate savings: drop every off-roster player 24.7 MB (28%) · **strip `boxScore` from archived cups' `leaguePhase` matches 14.8 MB (17%)** · drop `hist[]` for off-roster players 17.5 MB (20%) · `powerRankingHistory` 4.0 MB · off-roster `stats[]` 3.3 MB. **The league-phase one is free of feature cost — verified nothing reads it:** `cupStatsForPlayer` (`core/cup/cupStats.ts`, the Player Profile Cup tab) iterates only `cup.ties`; `Cup.tsx` has no `boxScore` reference and builds the table via `leaguePhaseTable` from scores; `clubHistory.ts` only keys `cupHistory` by season. Everything else trades away real history (retired players' OVR chart / career stats), hence a user call. Any fix needs a `migrate.ts` change and **deletes data from existing saves**, so confirm before shipping.

7. ~~**Honours boards go blank as a dynasty ages**~~ — **RESOLVED 2026-08-21 to 08-23.** The call went to the *middle* option, a name table for award winners only: `core/awardWinners.ts` snapshots every award pid's name onto the season entry (see "Award winners carry their own names" above), the farewell lists are read back (#263), and `RETIREE_ARCHIVE_LIMIT` went **2,000 → 20,000** once the archive moved to its own store (#266), since the cap was bounding write latency rather than disk. Original measurement kept as the reference baseline: award slots resolving to nothing were **8.5% blank at season 10, 25% at 27, 54% at 47, 69% at 75**, alongside 20,855 distinct players rendering as `Player <pid>` on the season-75 save. **Still open, and still a user call:** the name table covers award winners only, so a rank-and-file player the archive drops can still print as `Player <pid>` on Transfers / News Feed / Club History. The measured "name table for everyone" option (~68 bytes a row, **1.42 MB** on the worst save) covers those too and was not taken.

(Item 3, youth intake position distribution, is resolved — `generateYouthIntake` now weights the position draw by `ROSTER_COMPOSITION` instead of uniform, matching intake to actual roster demand. Item 5, Division-2 long-dynasty drift, is resolved — see `enforceDivisionCeilings` above.)

**Lower-severity leftovers** (no design input needed, not yet done): no general guard against fielding <11 when a roster drops below 11 healthy players (`selectXI` silently skips slots) — partially covered for the user's club by `ensureUserRosterSafety`; AI and other paths unguarded. `pickReplacement` would hand back an outfielder as a "GK replacement" if GKs could ever be subbed/injured/carded (currently unreachable).

**Open, unreproduced: "the transfers tab keeps crashing" (reported 2026-07-25).** Not found, still live. Ruled out so far: the pure data paths (`scripts/transfersFuzz.ts`, 1256 checks over 4 simmed seasons × both phases × every position × extreme/absurd filter values × odd name queries — 0 throws); the render tree on fresh and 1/2/3-season simmed leagues with negotiations in every status, the orphaned-talks table and the `FREE_AGENT_TID` sentinel (`test/ui/transfersRender.test.tsx`); old saves missing a persisted field (`migrate.ts` backfills every field the page reads). Untested surfaces that remain: anything needing real interaction (the `pinnedBuys` effect after a completed buy, column sorting, live typing into the debounced filters) — there's no DOM test env, so these need a browser. **Resolved: an uncapped DOM list (`WINDOW_TRANSFER_LIMIT`), not an exception and not save size** — the user's symptom was "the page never opens and the whole site freezes indefinitely", and a hang never throws, so the boundary doesn't catch it. The page's own work is *not* the problem (flat ~40-100ms). See **open design decision 6 (unbounded save size)** for the measured root cause and the fix options. If a genuine `/transfers` *throw* is ever reported on top of this, `capture_exceptions` is now on, so **check PostHog error tracking first** for the stack trace.
