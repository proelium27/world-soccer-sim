# Roster files, EA FC import, crests and logo packs

> Moved verbatim from CLAUDE.md on 2026-09-25 to keep session context small. This is the detailed ledger for this area: read it before touching the code it describes, and add new entries here, not to CLAUDE.md. References to "this file" below meant CLAUDE.md as a whole; the other sections now live alongside this one in `docs/ledger/`.

**EA FC roster converter** (`scripts/eafcRosterConvert.ts` + `scripts/eafc/`, docs in `docs/eafc-import.md`): turns an EA FC player CSV into a roster file for the Leagues → Import Custom League flow, for playing with real clubs/players. Dev-only and **never shipped or committed** — the CSV and generated JSON are gitignored, the game keeps shipping fictional clubs (trademark caution). The load-bearing part is the rescale: EA overalls are **rank-matched onto a freshly generated world's OVR distribution** rather than used raw, so the imported world carries the same OVR distribution a generated one does and the anti-inflation equilibrium is untouched. **`OVR_SCALE_SHIFT` did NOT make that redundant, though it does make it nearly invisible in the one league people check.** Pre-shift a generated world spanned ~23-81 against EA's 47-91, so raw EA numbers would have lifted the world ~10 points; since the shift a generated big-four top flight runs 61-92 against EA's 62-91, so for a *fully covered* league the match is now close to the identity and an imported star keeps roughly the rating he really has (measured 2026-09-07: EA 91 → 90/91 in England, Spain and Germany). That is a side effect, not a reason to delete it — the deeper tiers are nothing like EA's range (a third division here sits in the 30s and 40s and EA models no such thing) and a partly-covered league still scales against the pooled world, so the match is what keeps both honest with no tuned constant to drift. The converter stamps `ovrScale: OVR_SCALE_SHIFT` on its output precisely *because* its numbers are already current; absent, the importer reads a file as pre-shift and lifts it again. Per-skill ratings come from EA's attributes (the two sets are both 1-99 and mostly namesakes) then get uniformly shifted to hit the rescaled overall, so players keep their individuality; potential gets its *own* curve (different distribution — reusing the overall curve gave every wonderkid an identical ceiling). **Leagues are matched by `league_id`, never by name**: names collide across federations and the exports drop the country prefix ("Bundesliga" is Germany's *and* Austria's, "Premier League" England's *and* Ukraine's), which silently imported 12 Austrian clubs into the German top flight — `scripts/eafc/inspectLeagues.ts` audits a dataset for exactly this before you trust it. **Coverage is every tier-1 and tier-2 competition (24 of the world's 28)** — the big four's third divisions are deliberately uncovered, since rules for them would be written from real league names with no dataset to verify against, and a test pins that they stay uncovered so it reads as a decision rather than an oversight **Verified against the real FC26 export on 2026-08-29, and two of the four newest leagues were importing NOTHING** — a name rule that matches nothing and one that matches the wrong country both present as an empty competition. Scotland's cell there is a bare `Premiership` (correctly left unclaimed, since Northern Ireland's NIFL would take it) and Greece's is a bare `Super League` that **four** federations in that one file share (Greece 63, China 2012, Switzerland 189, India 2149), so the ambiguity guard dropped all four. Both are now reached by **id** (50, 63; plus the Netherlands' 10) and the bare `super_league` pattern is gone — Belgium's `Pro League` situation exactly. **A partly-covered league is scaled against the pooled world, not its own band** (`PARTIAL_LEAGUE_COVERAGE` 0.6, lowered from 0.75 on 2026-09-14 because Brazil's 13-of-20 Série A pooled came out 68.2 XI OVR against a generated 73.5, and 71.8 on its own band): rank-matching maps the source's *weakest* player onto the reference league's weakest, so FC26's 4-of-14 Greek clubs — the four best in the country — came out stating Panathinaikos were relegation fodder (top-11 56.7 against 62.6 pooled). The pooled curve only protects because the pool holds other leagues; a one-league conversion is its own pool. Slot counts now come from `competitionTeamCount` rather than a flat 20, so an over-full league is cut by squad strength here instead of by slot order in the importer. (Belgium/Turkey added 2026-08-12, the Netherlands/Greece/Scotland/Serbia 2026-08-28; `COVERED_COMPETITIONS` is derived from the rules so the "which divisions stay fictional" report can't drift, and a test now asserts it covers every competition `worldCompetitions()` ships). **A third trap: `LEAGUE_RULES` ORDER is load-bearing, not cosmetic.** `mapLeague` returns on the *first* matching rule, so a tier-2 name that *contains* another rule's pattern must be listed above it. Two live cases: "Scottish Championship" contains England's bare `championship` (listed after England it silently imports every Scottish second-tier club into the English Championship — the same failure as the 12 Austrian clubs), and "Super League 2" contains Greece's own `super_league`. Both second tiers therefore sit *above* the rule they would otherwise be eaten by, and tests pin both directions. Three bare names are deliberately left unclaimed because other countries share them: `premiership` (Northern Ireland's NIFL), `prva_liga` (a *top* flight in Croatia/Slovenia/Bosnia/Montenegro while being Serbia's second tier) and unqualified `superliga` (Denmark's). **The Dutch, Greek, Scottish and Serbian rules have no verified ids** — they were written from real league names, not confirmed against a dataset, so they resolve via the unambiguous-name fallback exactly like Portugal's second tier; run `inspectLeagues.ts` over a real export and add ids to `LEAGUE_IDS` before trusting an import covering any of them. Two traps that generalize: **(a)** FC26 has *three* leagues named exactly "Pro League" — Belgium's (4), Saudi Arabia's (350), the UAE's (2013) — so Belgium has **no bare name rule at all** and is reached by id only; a `pro_league` pattern would have put Al Hilal in the Belgian top flight. **(b)** `normalizeLeague` **must not fold accents**, however much `s_per_lig` ("Süper Lig") looks like a bug: folding was tried and measured to hand Brazil's "Série A" (14 clubs) to Italy and "Primera División" to Spain, since both then match a pattern *and* are unique names in the file, so the unambiguous-name fallback trusts them — 19 foreign clubs, silently. Turkey carries the mangled form as a pattern instead. No dataset seen so far has Belgium's, Turkey's or Portugal's second tier, so those resolve by name only and stay fictional unless a names file fills them. `applyRosterFile` realigns each slot's shuffled `academyBase` (`realignAcademyBases`, 2026-08-10): imported clubs are sorted by `computeTeamRating` and handed *that same group's* existing anchors in descending order, so a superclub can't inherit a weak youth anchor and drift over a long dynasty. **It's a permutation, not a recalculation** — same multiset, reassigned once, nothing derived from the imported ratings — so the anti-inflation equilibrium is untouched (a test pins the multiset). Only squad-*replaced* clubs take part, so a partial import can't degrade untouched clubs; the corollary is an imported club can only take an anchor another imported club held. **A fourth trap, on the SHIPPED pipeline rather than a corner of it (2026-09-07): `mergeRosterFiles` rebuilt its output as `{format, formatVersion, competitions}` and so dropped the base's `ovrScale`.** The hosted "Download Real Rosters" file is converted *and then* merged with a names file, so every future rebuild of it would have gone out unstamped — and unstamped means "pre-shift", so `rescaleRosterFile` lifts it a second time and the entire imported world lands 11 points above where the rank-match put it. Nothing throws; the file parses; the world is just too strong. The names file cannot disagree about the scale (identities only, no ratings), which is what makes taking the base's value unconditionally correct rather than a guess; `nationalities` was being dropped by the same line and is carried across too. `eafcConvert.test.ts` pins it by round-tripping a merged file back through `parseRosterFile` and demanding the ratings come out unchanged — the assertion has to be that round trip, since the merge output on its own looks perfectly fine. **The Americas (2026-09-14, release `rosters-2026-09`).** Ids 353 (Argentina), 39 (MLS) and 7 (Brazil) were verified against FC26; FC27 carries Argentina and MLS but no Brazilian or Mexican club, so Brazil's 13 licensed clubs come from FC26 (`~/Downloads/fc27-tooling/americas.py` builds the CSV). Mexico and every American second tier are names only, from a web-verified names file. Two merge-tool fixes came with it: **(a) a split division is seated positionally**, so `scripts/eafc/conferences.ts` orders MLS East-first and Argentina's Zone A first in both the converter and the merge (strength order put Seattle in the East, and appended names-only clubs landed in the wrong zone); **(b) `mergeRosterFiles` compares clubs within one country and tries an exact name before containment** — world-wide, Santos Laguna was rejected as Brazil's Santos (a guest club took its Liga MX slot) and New York City FC took the Red Bulls' colors; a `DISTINCT` table holds the same-country near-names, and two all-noise names ("Sport", "Athletic") no longer compare equal.

**Imported clubs draw no crest art (2026-08-10, user call).** `ClubCrest` keys crest images by **tid — a slot** — which is right for the shipped fictional clubs (a club's name is editable, its tid never changes) and wrong the moment a slot becomes a real club, since the badge then belongs to the club it displaced. `applyRosterFile` flags every slot the file *named* (squads or not — an identity-only entry is exactly the stale-crest case) with `StoredTeam.importedIdentity`, and `CrestArtProvider` suppresses art for those tids. **A context, not a prop**, because `ClubCrest` is rendered from 14 call sites that mostly hold only a tid; one of them forgetting the flag would show a wrong badge on that surface alone — the kind of bug that hides. Wrapped around the in-league shell (`Layout.tsx`) *and* the new-league club picker, so the preview matches the save. Optional field → no migration (absent = not imported). Knock-on: colors become the club's entire identity, so `mergeRosterFiles` now adopts real colors from the names file (the converter hashes them out of the club name — Liverpool came out purple).

**Custom club logos: a logo pack, matched by NAME rather than by slot (`core/teams/logoPack.ts`, `ui/logoImages.ts`, 2026-09-03, user ask).** The bullet above is the problem statement: the game ships 80 crests covering England's and Spain's top two divisions, so 546 of 626 clubs wear a swatch, and a roster import makes it *worse* by design — the slot's badge is suppressed and nothing replaces it. A pack is a sibling of the roster file (`{format: "world-soccer-sim-logos", formatVersion: 1, logos: [{match, image}]}`, `image` a data URL) loaded from the same New League screen, and the picker also takes **loose picture files**, folding them into one pack with the filename as the club name — because the thing a person actually has is a folder of PNGs, and making them build a JSON first would put a build step in front of the feature.
- **The two files match on different things and that is the load-bearing distinction.** A roster file maps clubs **positionally** onto a competition's slots, which it must: the clubs it carries have no identity in the save yet, they *are* the identity being installed. A logo pack matches by **name**, because by the time it applies the names exist and a name is the only thing the author of a badge folder knows. Matching a logo positionally would mis-badge every club the moment a roster file listed its clubs in a different order. The corollary the UI has to state out loud: **load the roster file first**, or the badges go looking for clubs that don't exist yet.
- **Stored in its own IndexedDB store (`crests`, keyed `[lid, tid]`, DB_VERSION 4 → 5), never on `LeagueStore`.** Same argument as `players`/`retirees`/`careers` rather than a new one: the league record is rewritten in full on every mutation and `structuredClone`d to the worker on every sim, so a few MB of badges there would be paid for on every lineup drag and every matchday — the exact bug versions 2, 3 and 4 exist to undo. Nothing in `src/core` knows crests exist; they take no rng draw, cross no worker boundary and are read by no sim code, so **no dynasty audit and no scoreline rebase**. `saveLeague` doesn't touch the store (badges are written once at import), `deleteLeague` clears it **inside its own transaction** so a reused lid can't inherit them, and `migrate.ts` needed nothing — a save written before this had no badges, and empty is the truth rather than a shape waiting to be split.
- **Images are downscaled on the way in and that is not optional.** `imageToLogoDataUrl` re-encodes to `CREST_IMAGE_SIZE` (160) square WebP at 0.9, never upscaling, on a transparent ground. Real badges run ~110 KB each (the size of the shipped art) and a 626-club world of them is ~69 MB read into memory and written to disk for something drawn at 20 pixels; re-encoded it is ~3 MB. Decoded through an `HTMLImageElement` rather than `createImageBitmap` **for SVG**, which many badge packs are and which `createImageBitmap` has never handled consistently — rasterizing is also what makes accepting SVG *safe*, since an SVG is a document that can carry script and none of it survives a canvas. `MAX_LOGO_DATA_URL` (512 KB) only ever catches a pack somebody hand-wrote around that step.
- **`isImageDataUrl` is a security check, not a validation nicety.** These strings go straight into an `<img src>`, and `data:` covers `text/html` and `image/svg+xml` as readily as PNG, so the parser accepts exactly the raster types a canvas emits. Enforced twice — in `parseLogoPack` and again in `exportImport`'s reader — because a save file is a thing people send each other.
- **A custom badge outranks BOTH the shipped art and the imported-club suppression**, which is the whole point: suppression exists to stop a real club wearing the fictional badge of the slot it took, and this is the answer to exactly that. `CustomCrestProvider` is a second context beside `CrestArtProvider` for the reason that one is a context at all — `ClubCrest` is rendered from 14 sites holding nothing but a tid. Wrapped around the in-league shell *and* the new-league picker, in the same order, so the preview matches the save. `objectFit: contain` because a custom badge is whatever shape the file was and every caller sizes its layout on `size`.
- **The export carries them as a SIBLING key, stripped before `migrateLeague`.** `migrateLeague` hands back the object it was given, so a `crests` key left on it would ride onto the league record and be re-serialised on every mutation from then on — silently, and only for saves that had been through a file. The reader is deliberately **lenient** where `parseLogoPack` is strict (a bad badge must never cost someone a 60-season dynasty), and `importLeagueJSON` now returns `{league, crests}` rather than a `LeagueStore` — a signature change taken over a wrapper precisely so a future caller can't silently drop the badges.
- **The AI prompt says there is NO logo field, and that line is written to head off a mistake rather than in response to one.** `colors` sits in the club shape as the club's visual identity, so a badge is the natural next key for an AI to invent, and `parseRosterFile` builds its output from named fields — an invented one is **dropped in silence**. That is this feature's own failure arriving from a new direction: the author believes the badges are in the file, gets none, and has nothing to tell them why. Deliberately a *don't* plus a pointer at the real route (image files, same screen), never an instruction to produce one — asking a language model for a picture gets hallucinated base64, which *would* be fatal, since `parseLogoPack` rejects a data URL it cannot read. `rosterAiPrompt.test.ts` pins the wording, the pointer, the absence of any `data:image` string, **and** the silent-discard behaviour the claim rests on — so making the parser strict about unknown keys fails the test rather than leaving the prompt saying the opposite of what happens.
- **Creation-only, like the roster import, but for a much weaker reason — and it is the obvious next move.** A roster import is creation-only because it *destroys careers*; a badge destroys nothing, so the only thing keeping this at creation is that the picker lives there. An existing real-clubs save cannot be badged at all today, which is the likeliest thing a player will want. `saveCrests(lid, byTid)` + `resolveLogoPack(league.teams, pack)` is the whole of it wherever a second surface goes.

**One league file with an import checklist, plus an export (`core/teams/leagueFile.ts`, `ui/components/ImportChecklist.tsx`, 2026-09-18, user ask "like Basketball GM").** Not a new format: a roster file whose clubs may carry an optional `logo` (image data URL). Every existing roster file is therefore a league file with no badges, and one parser and one importer serve both. Four things to know.
- **`logo` is read LENIENTLY** (anything but an `isImageDataUrl` within `MAX_LOGO_DATA_URL` is dropped, never thrown), for the reason exportImport's badge reader is lenient, and because it keeps an AI-invented `logo: "https://..."` a silent no-op, which is what the AI prompt's "don't add a logo" line and `rosterAiPrompt.test.ts` rely on. File badges are keyed by the SLOT they land on (`clubLogosByTid`), not by name, so they need no second resolve and work with names unticked. A separately loaded logo pack wins a clash.
- **The checklist is a pure transform before the ordinary import**: `selectFromRosterFile` drops excluded leagues (keyed `competitionKey`, the same key `combineRosterFiles` folds on) and strips `players`/`logo`; names and colors can't be stripped (required fields) so they travel as `RosterIdentityOptions` into `applyRosterFile`, where an unticked half keeps the slot's current value. **`importedIdentity` is set only when names are imported**: a slot that keeps its fictional name keeps its crest. The default selection is the identity, so an untouched checklist imports exactly what it did before. Applied inside `describeRoster` so every preview on the page and the import read the same trimmed file.
- **Export (`buildLeagueFile`, Leagues → Export League File)** is `buildRosterFile` plus senior squads with exact `ratings` and the save's custom crests from `crestDb`, stamped `ovrScale`. Written as plain JSON (editable), not gzipped. Ages are clamped to `ROSTER_FILE_AGE_MIN..MAX` or one academy graduate would make the file unreadable. A full 898-club export with squads measured ~7 MB. `leagueFile.test.ts` round-trips a squad back to identical players.
- Nationality mixes aren't on the checklist: `combineRosterFiles` drops them for world-wide files anyway (they only apply to per-league files on added leagues), so a box would do nothing.

**Roster import is creation-only (2026-08-10, user call).** The per-save "Import Teams" button is gone; the entry point is Leagues → **Import Custom League** → `/new-league?roster=1`, and since 2026-08-28 a "Load roster files" button on plain `/new-league` as well. **Creation-time is the invariant, not which screen** — both land in the same page state. Reason: a roster file *replaces squads*, and `applyRosterFile` drops every replaced player who has no recorded stats — on a save in progress that silently deletes real careers, stat lines and the transfer history keyed to those pids. At creation there is nothing to destroy. Three consequences worth knowing: **(a)** `applyRosterFileToNewLeague` (`teams/rosterImport.ts`) is the entry point, and it re-runs `assignAIFormations` + `reconcileScoutingObserved` after the import, because `createLeagueState` derives both from squads the import then throws away (formations picked for deleted players; the user's fog-of-war stamps pruned along with the pids they pointed at, leaving the imported squad permanently unscouted). It is **only** safe on a fresh league — re-stamping scouting resets every observation to season 1, which mid-save hands the user a fully-scouted squad. **(b)** `resolveRosterSlots` now takes a structural `RosterSlotWorld` (`{competitions, teams}`) rather than a `LeagueStore`, so the club picker can resolve a file against `worldTeamSlots()` — the slot layout of a save that doesn't exist yet — and show real club names *before* paying 4s to generate 6000 players. `worldTeamSlots` duplicates `generateWorld`'s tid layout by necessity; `rosterImport.test.ts` pins it against a real generated world so the two can't drift. **(c)** Crest art does **not** follow an import (`ClubCrest` keys images by tid, i.e. by slot), so an imported club wears whatever crest its slot had. Colors do follow.

**The AI prompt has to live on the screens that IMPORT, and for a year it didn't (2026-09-02).** `buildImportPromptText` (`teams/rosterAiPrompt.ts`) was offered only from `TopBar`, `TopBar` renders only inside `Layout`, and `/leagues` and `/new-league` both sit **outside** `Layout` (`App.tsx`) — while import is creation-only per the entry above. So the only copy of the format spec lived behind a save you had to already have, on a route you had to already have left; the roster screen's own help text said as much, telling the reader to go and find "the top bar of any save". **The tell that this mattered is what arrives in the wild**: a 232-club / 5,873-player all-time-teams file (2026-09-02) broke four rules the prompt states plainly — no `country`/`tier` on any entry, real-world division sizes rather than this world's (French 20 against 18, Scottish 17 against 12), an invented competition ("Brazilian Division 1"), and adjectival names *reconstructed* rather than copied ("Netherlands Division 1" for "Dutch Division 1"). That is what a file written without the spec looks like, and none of it is the author's fault. Fixed by widening the builder from `LeagueStore` to the structural **`RosterSlotWorld`** it already had lying around — a save satisfies it, and so does `worldTeamSlots()`, so a pre-save screen can describe a world that doesn't exist yet. `CopyAiPromptButton` is the one control (clipboard, download fallback, transient label); `/new-league` passes the **live configured** world so a renamed or added league is in the prompt, `/leagues` passes the shipped default because it has no world of its own. `test/ui/aiPromptReach.test.tsx` pins all three routes and **matches a `<button>` element, not the label string** — the old help text contained that same label, so a substring check passes on the broken code.
- **The `colors` trap is the one FATAL authoring mistake, and it is caused by ACCURACY.** `parseRosterFile` demands exactly two hex strings and *throws*, and a throw rejects the entire file — so one club costs an author every other one. That is what killed the file above: Fluminense and Bahia listed their real **three** colours. The prompt now states the two-colour rule, names it as the commonest rejection, and carries it on the pre-answer checklist. **It also had to qualify its own framing**: the three numbered list rules genuinely "fail QUIETLY", and the prompt said so unscoped, which teaches an AI that everything degrades gracefully and nothing is worth re-reading. Field *shapes* are the opposite and now say so. `rosterAiPrompt.test.ts` pins the wording **and** the behaviour behind it (a three-colour club throws; removing that one club accepts the same file), so making the parser lenient here fails the test rather than leaving the prompt warning about something that no longer happens.

**Roster import takes several files (2026-08-11).** A world is authored a league at a time (an AI won't emit twelve competitions of squads in one answer), so both pickers — Leagues → Import and the `?roster=1` screen's "Add another file" — are `multiple` and the selected files are folded by `combineRosterFiles` (`teams/rosterFile.ts`) into the single file `applyRosterFileToNewLeague` applies. Competitions are independent, so combining is concatenation in load order; the one ambiguous case, two files claiming the same competition, can't be interleaved (clubs map *positionally* onto slots) so the later file wins outright and the collision is reported. `PendingRoster` therefore hands over `files[]`, and `NewLeague` keeps the loaded `sources` so later picks add to them rather than replace. A file that won't parse is skipped and named on the picker screen; on the Leagues screen it stops the batch instead, because that screen is left behind on the way to the picker and any error it raised would go with it.
