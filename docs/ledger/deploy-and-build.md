## Analytics & deploy config

**PostHog needs `VITE_POSTHOG_KEY`/`VITE_POSTHOG_HOST` at BUILD time, and a build without them fails silently (2026-08-20).** Vite inlines `import.meta.env.VITE_*`, so the values are baked into the bundle by `npm run build` — they are not runtime config, and a host-side secret cannot reach an assets-only static deploy. Missing, `posthog.init()` (`src/ui/main.tsx`) is handed `undefined`: nothing throws, nothing logs, and the site reports no pageviews, no gameplay events and no crashes while looking perfectly healthy. That is what the 2026-08-15 Vercel → Cloudflare move (`wrangler.jsonc`, assets-only) did — the vars lived in the Vercel project, didn't come along, and production went analytics-dark for five days while Vercel *preview* deploys kept reporting normally, which is what made it look like a PostHog outage rather than a build problem. **The values are therefore committed, per build target** — `.env.production` (web) and `.env.itch`, both carrying the key, so any checkout builds a working bundle with no dashboard configuration anywhere and there is nothing left to lose in the next host migration. Safe because the project key is PostHog's public write-only token, already served to every visitor in the bundle. Three gotchas: **(a)** Vite loads only `.env` and `.env.<mode>`, and `.env.production` is itself a mode file, so it is *not* loaded by `--mode itch`/`--mode crazygames` — hence the duplication rather than one shared file (`.env` would cover every mode, but it is gitignored, which is the out-of-band storage this arrangement exists to avoid). **(b)** `.env.crazygames` deliberately carries **no** key: that build aliases `posthog-js` to a no-op shim (`vite.config.ts` → `src/ui/vendor/posthogNoop.ts`), so the omission looks like an oversight and isn't. **(c)** `npm run dev` runs mode "development" and so loads neither, meaning dev sessions report nothing by default — which is wanted, since dev clicks would otherwise land in the same project as real players and burn quota. `.env.example` exists only to opt a local dev session in. **Verify a deploy, don't assume:** `curl -s https://worldsoccersim.org/assets/index-*.js | grep -c phc_` — zero means that build has no key.

**worldsoccersim.org DEPLOYS ITSELF, and the repo gives no sign of it — this cost an hour and nearly shipped a duplicate pipeline (2026-09-04, `docs/cloudflare.md`).** Cloudflare **Workers Builds** is connected to the repo and publishes on every push to main. Nothing in `.github/workflows/` does it, and all the repo contains is `wrangler.jsonc` sitting alone, which reads exactly like a deploy someone runs by hand — that inference was drawn **twice in one session, confidently, and was wrong both times**. **It surfaces as a CHECK RUN, not a GitHub deployment**, which is the specific trap: querying `/deployments` shows only `vercel[bot]` and `github-pages` and looks like proof nothing automates Cloudflare. Look at `gh api repos/.../commits/<sha>/check-runs` for `app.slug == "cloudflare-workers-and-pages"`.
  - **The behaviour to know is LAG, not failure.** Measured merge-to-live: #331 **6m21s**, #329 ~19 min, #316 ~20 min — single digits usually, ~20 when Cloudflare's dependency cache is cold. So the domain is legitimately behind main for a few minutes after every merge, and checking inside that window presents as *"I merged this feature and it isn't in the game"*, which points at the feature rather than the clock. Two non-failures: **rapid merges are coalesced** (#318 and #329 merged two minutes apart and only #329 built — an *absent* check run means a later commit superseded it), and **nothing gates the deploy on tests** (PR runs gate merges; main publishes on push regardless).
  - **The Vercel project is a leftover of the pre-2026-08-15 host and the domain is NOT pointed at it** (`server: cloudflare`, no `x-vercel-*` on any response) — yet it still builds every push including a `Production` deployment, so a current Vercel link proves the code is on main and proves nothing about the live site. That is how this presented: feature on the Vercel link, not on the domain, the two assumed to be one thing.
  - **A second deploy workflow was built and CLOSED unmerged** (#333). Running `wrangler deploy` from Actions duplicates what Workers Builds already does, so it would mean two pipelines racing to publish the same Worker on every push; it also would not have helped, since `npm ci` dominates and Cloudflare did #331 end to end in 6m21s. The only real reason to own the deploy is **gating it on CI green** — and that is a trade, not an upgrade (~6 min becomes ~35), and it requires turning Cloudflare's build **off** first. One deployer or the other, never both.
  - **How to date a stale deploy**, since guessing from feature greps is what produced the wrong answer: `git archive <sha> | tar -x`, symlink `node_modules`, `npx vite build`, compare the `index-*.js` hash **and byte size** to the live one — Vite output is deterministic given the same lockfile (#316 → `index-BSYiCOl2.js`, 1,748,391 bytes, matching exactly). **Do NOT date a bundle by grepping changelog text**: `changelog/index.ts` globs its entries and Vite code-splits them into `Changelog-*.js`, so every changelog string reads 0 in the index chunk whatever the commit — a decisive-looking negative that is pure noise.
  - **The two guards that DID ship** cover what the deploy doesn't check. `ci.yml`'s typecheck job now runs `npm run build` and asserts `phc_` in `dist/assets` — the silent-analytics failure the paragraph above documents, moved from five days to one PR (added to that job rather than a new one because the file's own header is about a 20-job account ceiling). `verify-live-site.yml` fires on Cloudflare's check run and **deploys nothing**: red if the build failed (otherwise a grey check that scrolls away while the site sits on the previous bundle), else asserts the domain serves a bundle with its key and a working SPA fallback. It cannot run on the PR that adds it — GitHub dispatches `check_run` only against workflows already on the default branch.
  - **The generalizable lesson, and the reason this entry is long: the deploy pipeline lived somewhere the repo could not see, and absence of evidence in one API was twice read as evidence of absence.** Both times the correction came from the user saying the explanation did not match their experience. When production and a preview disagree, suspect the deploy — then *measure how far behind and by what mechanism* before narrating why.

**The free tier is 1M events/month, and it has been exhausted once.** Autocapture fired on every click in a click-heavy game (685k events in 30 days, 67% of volume) and blew the allowance on 2026-08-03; ingestion stopped project-wide for the rest of the cycle and only `$exception` kept flowing, on its own quota. `autocapture: false` shipped in #205. Nothing reads autocapture data — every dashboard is built on the explicit events in `src/ui/analytics.ts`, whose rule is "a handful of meaningful moments, not one event per click". Keep it that way before adding events.


- **Build targets** (`vite.config.ts`, `.env.<mode>`) — the default build serves worldsoccersim.org; `itch` and `crazygames` are **embedded** targets (someone else's iframe, at a path we don't control), grouped by the `EMBEDDED` set: relative `base` and hash routing, because there's no server to answer a history-API deep link. `crazygames` additionally strips AdSense and the SEO block from `index.html`, aliases `posthog-js` to a no-op, skips `<RouteSeo />` (or `useRouteSeo` recreates the canonical tag at runtime, pointing at a playable copy of the game — the one outbound link their rules forbid), and adds the CrazyGames SDK. **`src/ui/crazygames.ts` is the only place that touches the SDK**: no-ops everywhere else, queues every call behind the async `init()`, and survives the script being blocked. It also drops the announcement banner (theirs is a fixed 16:9 container as small as **914x514**, where a 36px strip is 7% of the height, and a full-width "Join the Discord" bar risks reading as the main CTA their rules disallow; the sidebar link is fine). **Two layout fixes it surfaced are global, not embed-only**, because they were equally broken in any narrow browser window: the top bar's inline save controls collapse into the existing overflow menu below `xl` (1200px) rather than `md` (768px) — the row needs ~1020px and was wrapping onto two lines and truncating the season — and the sidebar narrows 220px → 170px between 768px and 1199.98px. Full runbook + upload-form answers: `docs/crazygames.md`. Three gotchas: **(a)** the HTML surgery keys off marker comments and **throws if they go missing**, so editing `<head>` can't silently ship AdSense to review; **(b)** files in `public/` are copied verbatim and do *not* get Vite's base rewriting, so they must go through `publicAsset()`/`LOGO_URL` (`src/ui/publicAsset.ts`) — a bare `/favicon.png` resolved against the *host's* domain and 404'd the top-bar logo in both embedded builds, a bug that only shows up in an iframe at a subpath; **(c)** `dist-crazygames-harness.html` (repo root, never shipped) loads the built bundle in an iframe pinned to both measured CrazyGames sizes — the only way to see either the subpath bugs or the cramped layout, since a plain tab is neither iframed nor 16:9.
  - **`pages` is a fourth target and it is NOT embedded (2026-08-26).** It publishes the same game to `proelium27.github.io/world-soccer-sim/` from `.github/workflows/pages.yml` on every push to main. Not in `EMBEDDED`, deliberately: it is an ordinary page on its own domain, so it keeps history-API URLs rather than switching to hash routing. What it needs instead is the **two things a subpath host takes**, and both are silent when missing. **(a) A base path**, `PAGES_BASE` (default `/world-soccer-sim/`, which must track the repo's current name; the workflow fills it from `configure-pages`' reported base path, which is the only source that knows about a custom domain, and falls back to the repo name so a fork or rename needs no edit), which reaches the app as `import.meta.env.BASE_URL` and is now the **router's `basename`** — without it the browser sits at `/world-soccer-sim/manual` while React Router looks for a `/world-soccer-sim/manual` route and matches nothing. `basename` is `undefined` for the hash builds, whose base is the relative `./` (not a URL path, and a hash router has no prefix to strip). **(b) `404.html`**, a copy of `index.html` written by the pages build: Pages has no rewrite rules, and its one hook is serving that document for any path it can't resolve, with the requested URL intact — so a deep link boots the app on the right route. It answers **404**, which is invisible to a player and costs nothing in search because `SITE_ORIGIN` canonicalizes every page to worldsoccersim.org. The workflow asserts the file exists, since a missing fallback only shows up when someone opens a page other than the entry point. The pre-React placeholder's absolute `/leagues` links get the base prefix here for the same reason the CrazyGames build hash-rewrites them. **`.env.pages` carries the PostHog key** — a third copy, for the reason `.env.itch` spells out: `.env.production` is itself a mode file and is not read for `--mode pages`, so a key kept only there ships a bundle with `posthog.init(undefined)`, silent and inert. **The base is baked into every asset URL at build time, so RENAMING THE REPO BREAKS THE LIVE SITE until it is redeployed** — the deployed HTML keeps asking for the old name's `/assets/`, the page loads and every asset 404s. Measured, not hypothetical: `soccer-gm` became `world-soccer-sim` hours after the first deploy and the site went blank. No static file can detect its own URL changed, so a rebuild is the only fix and also the whole fix (the workflow reads the name at build time). Same applies to adding or removing a custom domain.
