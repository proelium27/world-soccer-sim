## Core invariants & gotchas (durable — read before touching sim code)

- **RNG stream order is load-bearing.** The sim is seeded/deterministic; inserting or removing an `rng` draw shifts every downstream roll (different ratings, names, results). When adding per-player traits or post-hoc attribution, derive them from a *separate* seeded stream (`mulberry32`/`hashInts` off pids/match-intrinsics), never from the shared `rng`. This has caused real bugs (AI deficits, shifted generation) multiple times — see any "RNG-stream-order" mention in git history.
- **OVR scale:** 76 ≈ average starter, 81 ≈ good starter, 86 ≈ a team's best, 91-96 ≈ league-wide elite, 97+ ≈ rare outlier. `OVR_WEIGHTS` (`players/templates.ts`) drives both generation and progression's `computeOvr`. **Those numbers are 11 higher than they were before 2026-09-06 — see `OVR_SCALE_SHIFT` below, and treat any OVR figure written elsewhere in this file or in `docs/` as being on the OLD scale unless it says otherwise.** Nothing was recalibrated to reach them, so every measurement recorded here (a rung gap, a damping sweep, an 80+ population target) still describes the same football; add 11 to read it in today's units.
- **The whole rating scale was lifted +11 to read like EA FC, and it is a RELABEL rather than a rebalance (`OVR_SCALE_SHIFT`, 2026-09-06, user ask).** Measured, a big-four top flight generated **50 / 64.5 / 81** (min/mean/max) against EA FC's Premier League at roughly **62 / 76 / 91**, so the game was ~11 low at the mean and ~9 at p90; it now generates **61 / 75.5 / 92**. **(That min/max pair is superseded by the 2026-09-09 generation age model two entries down; the MEAN is unmoved, which is the half this calibration rests on. A big-four top flight now generates 35 / 75.1 / 94 — the bottom is teenage prospects, a population EA squads do not carry, so `min` stopped being an apples-to-apples comparison rather than drifting; world-wide, mean and median are identical before and after, p90 74 → 75, p99 84 → 86, max 92 → 94.)** The change is one constant, the ~19 constants that name a POSITION on the ovr scale (each now written `<calibrated value> + OVR_SCALE_SHIFT`, so the original stays visible and the relationship is structural), and a save migration.
  - **It ships without a dynasty audit because the game is provably invariant to a uniform shift, and that was VERIFIED rather than argued.** Three legs: (a) match composites z-normalize within each competition, so a constant added to everyone moves the mean, leaves the sd, and leaves every z-score; (b) both money curves are differences from a floor — wages are `(ovr − WAGE_OVR_FLOOR)³`, value is `(ovr − VALUATION_OVR_FLOOR)^n + (ovr − VALUATION_ELITE_THRESHOLD)²` — so shifting those floors with the ratings leaves every wage and fee identical to the pound; (c) everything else that reads ovr reads a **gap** (familiarity penalties, `SECONDARY_POSITION_CUTOFF`, `slotValue`, the country ladder's 0.94-per-offset-point, Power Rankings' Elo-per-point, `POSITION_OVR_CALIBRATION`, the scouting fog's half-widths). **The single distinction to get right is POSITION vs WIDTH vs WEIGHT**: a position shifts, a width and a weight must not.
  - **The one REAL bug the sweep caused was an inverted difficulty ladder, and it is the best argument for the `original + SHIFT` idiom.** `DIFFICULTIES` carries a `protectedStarOvr` per level and only `normal` referenced `PROTECTED_STAR_OVR` — easy/hard/brutal were written out as 85/78/76. Shifting normal alone put **easy's bar (85) BELOW normal's (91)**, so Easy would have withheld *more* players from the user than Normal: the lever silently ran backwards, which is a gameplay inversion no type checker or scoreline hash can see. Caught by `difficulty.test.ts`'s ordering gate. All four are now offsets from the constant. **The lesson generalizes past this change: a constant that names a position on the scale and is DUPLICATED anywhere — a difficulty profile, a UI band, a test fixture — is where a scale move breaks, not the arithmetic.** Every fixture failure in this branch was the same shape (`ratingColor`'s 40/65/90, `negotiation`'s hardcoded 74 "breakout", `archive`'s worthy peak of 80, `clubGoat`'s 90-vs-78 straddling the GOAT baseline).
  - **`scripts/ovrScaleProbe.ts` is the gate and `scripts/ovrScaleMatchProbe.ts` is the second half.** The first fingerprints every player's ovr/potential/wage/value plus a scoreline hash; the second reports goals/match, home-win rate and champion points, because a hash is all-or-nothing and cannot tell a one-goal difference from a broken sim. **Setting `OVR_SCALE_SHIFT = 0` reproduces the merge base exactly** (every shifted constant is `original + SHIFT`), so the A/B is one edit rather than a worktree.
  - **It is NOT bit-identical, and the reason is the rating clamps at 1 and 99.** Measured: **97.78% of players shift exactly +11**, the rest by +10/+9/+8/+7 — those are the weak-league players whose ratings were underflowing into `RATING_MIN`, and a shift lifts them off it (**ratings pinned at 1: 7,291 → 1,531**), so they gain less than 11. Wages differ for **0.72%** of players and values for **7.09%** (value also reads `potential`, which the same clamps move). Distributionally nothing moves: **goals/match 3.1414 → 3.1372, home-win rate .4191 → .4220, champion points 78.25 → 78.75** over 8 seasons whose own range is 71-90. So the `touchStats.test.ts` scoreline hash needed rebasing, and the un-clamping is a small **improvement** — it is the same youth-underflow `YOUTH_BASE_FLOOR` exists to fight.
  - **Applied to `rollRating`'s OUTPUT, not to the generation bases, and that is what dissolves the one real hazard.** `base` is `LEAGUE_BASE` plus the country and division offsets, and `academyBase` feeds `YOUTH_BASE_FLOOR`'s softplus — a nonlinearity anchored at absolute zero, so shifting the bases would move which academies saturate on it and silently retune the weakest leagues' youth. Shifting the output leaves the whole base-side arithmetic reading exactly as it did, which is why `LEAGUE_BASE` (54), `YOUTH_BASE_OFFSET` (34), `academyBase`, `TIER_OFFSET` and `COUNTRY_STRENGTH_OFFSET` are all **untouched and still on the old scale**. Don't "tidy" them into the new one.
  - **The `ABS` tier deliberately does not shift**, and the reason is checkable: `ABS` marks the skills irrelevant at a position, and cross-referencing `GEN_OFFSETS` against `OVR_WEIGHTS` shows every one of them carries **zero** ovr weight there (a GK's finishing, an outfielder's goalkeeping). So leaving them on their absolute `ABS_LOW_MIN`..`ABS_LOW_MAX` floor moves no player's ovr by a point, and it is the more EA-like reading anyway.
  - **`GENERATIONAL_DAMPING_END` is the one constant that could not take the shift**, being 95 against a `RATING_MAX` of 99 — the faithful translation is 106 and there is nowhere to put it. Capped at 99, so a generational talent's headroom above `GROWTH_DAMPING_END` compresses from 15 points to 8: the rarest legend peaks in the mid-to-high 90s against a field topping out ~91, where before he reached ~95 against a field topping out ~80. Taken deliberately rather than by shrinking the shift, since EA's own best player is 91 and a 16-point gap to the world is not a thing that scale has ever had. Reaches ~1 player every 30 seasons.
  - **The migration is MANDATORY, not cosmetic, and `meta.ovrScale` is the save's first piece of version information about its own numbers.** Absent means 0. An unlifted save fields 65-rated players against an 81-rated Division 2 ceiling (nobody is ever swept), a 91-rated protected-star bar (nobody is ever protected) and a wage floor 11 points below its own squad, pricing a first-teamer at **roughly a fifth** of his proper salary — silent, not loud. `rescaleRatings` runs **first** in `migrateLeague`, before every other backfill, because the rest of that file already reads ratings as current-scale (`migrateFields` re-derives `ovr`, `cullOnLoad` gates on `FREE_AGENT_CULL_MAX_PEAK_OVR`). It lifts the live pool *and* the three places holding a bare ovr with no ratings behind it — `retiredPlayers`, `seasonHistory[].awardWinners` and `seasonHistory[].retirements.notable` — since nothing else could recover those and every retiree would otherwise read 11 worse than the living forever. Writing the marker back is what makes it idempotent; `test/db/ovrScaleMigration.test.ts` pins the double-lift.
  - **What a shift CANNOT do is narrow the range, and that was the design call.** The game spans 5→81 at generation against EA's ~47→91, about twice as wide, and a shift preserves every gap by definition (English D1 sits 43.3 points above Serbian D3 before and after). So the top flights land on EA and the deep tiers stay below anything EA models, which is the right trade — EA has no Serbian third division to be inconsistent with. Closing that gap means **compressing**, which breaks all three invariance legs above (every gap shrinks ~x0.49, so `POSITION_FOREIGN_PENALTY` 16 silently doubles in real terms) and is a genuine multi-week rebalance with 4-seed audits. Don't reach for it casually.
  - **A ROSTER FILE needed its own marker, and its rule is the OPPOSITE of `meta.ovrScale`'s (`RosterFile.ovrScale`).** A file's `overall`/`ratings`/`potential` are absolute numbers with nothing behind them to re-derive from, so a file has to declare its scale. **Marked -> lifted by the difference. UNMARKED -> read exactly as written, NOT treated as scale 0.** A save with no marker is unambiguous (this game wrote it, on the scale in force then); a roster file with no marker is of unknown provenance, and the two kinds in the wild want opposite treatment — converter output really is on the game's own scale, while a hand- or AI-authored real-world file was never on it at all and carries real-world numbers, which is exactly why the converter rank-matches instead of using EA overalls raw.
    - **Guessing "old scale" for unmarked files shipped for a few hours and the user caught it: "every player has a 99 potential now."** Reproduced immediately — a file stating ordinary EA potentials (78-95) imported with **40% of the squad on potential 99**, all indistinguishable, because a lift pushes numbers already near the top of a 1-99 scale into the `RATING_MAX` clamp. Overalls survive a lift (they are low on the old scale); **potentials do not, and that asymmetry is the whole trap** — the same +11 is harmless on one field and saturating on the other. Reading an unmarked file literally is also what the game did before the scale moved, so nothing anyone already has changes behaviour.
    - **Normalised in `parseRosterFile`, NOT at import, and that is what makes combining safe.** `combineRosterFiles` merges competitions out of several files into one, and a combined file carries a single `ovrScale` — so lifting at import would apply one scale to files authored on two. Normalising as each file is read means everything downstream (combining, `retargetRosterFile`, the picker's preview) is already in one set of units. Still called again in `applyRosterFile`, which is free because it is idempotent, and covers a hand-built file that never went through the parser.
    - **The EA FC converter MUST stamp it, and that is the trap in the other direction.** `scripts/eafc/scale.ts` rank-matches onto a *freshly generated* reference world, so its output is already on the current scale — but under the marked-means-lift rule an unmarked converter file would be read literally and land 11 low against new-scale filler. Stamping is what makes it correct, and it is why **the hosted "Download Real Rosters" file wants regenerating**: it predates the marker, so it imports on the old scale until someone re-runs the converter, and a fresh conversion is stamped so it only has to be done once.
  - **Bonus: the EA FC converter needed no change and got better.** `scripts/eafc/scale.ts` rank-matches against a *freshly generated reference world*, so it follows the new scale by construction; for a fully covered league it is now close to the identity (EA's 62-91 onto the game's 61-92), meaning an imported star keeps roughly his real rating. Rank-matching still stays, since the deep tiers and partly-covered leagues are as far apart as ever.
- **OVR is calibrated to mean the same thing at every position, and it takes TWO constants because two independent mechanisms break it (2026-08-23).** A position's OVR weights sit on the very skills its generation tiers roll highest — that is *what makes them* its key skills — so the weighting and `GEN_OFFSETS` amplify each other. Measured on a fresh world before the fix: mean OVR ST 55.9 down to FB 49.4, and **132 of 320 clubs had a striker as their best player against 1 with a full-back and 6 with a centre-mid** (expected ~38/51/51 at their roster shares). Full-back is the only position with no `star` skill; striker and winger have two each. The fix is *not* a reweight — the rows are read by the sim's slot logic, secondary positions and the position-change check, so flattening them would trade a true statement about football for arithmetic. Instead: **(1) `POSITION_OVR_CALIBRATION` (levels)** — an additive per-position shift, **zero-sum weighted by `ROSTER_COMPOSITION`**, so the world mean OVR is untouched and `LEAGUE_BASE` / `GROWTH_DAMPING_START` / `DIVISION_2_REFUSAL_OVR_THRESHOLD` / `PROTECTED_STAR_OVR` / the wage and valuation curves all still mean what they did. **(2) `POSITION_RATING_SPREAD` (spread)** — OVR is a weighted *mean* of independent draws, so its noise is `RATING_NOISE_SD × sqrt(Σ(w/W)²)`: a row concentrated on few attributes varies more and wins every extreme. Keeper is the outlier (goalkeeping is over half his weighting, 0.58 vs 0.34-0.42 outfield), and fixing only the levels handed him the problem instead — **GK went 68 → 103 of 320 clubs**. It scales the *generation draw* rather than the weight row, because the sim's `keeping` composite **is** the goalkeeping rating (`league/matchPlayers.ts`) and the AI prices keepers off OVR, so a diluted row would make OVR a worse read on the one thing he does; composites are z-normalized per competition, so a uniform change in a position's raw spread is nearly invisible to the football. **Derived at module load from `OVR_WEIGHTS`**, so editing a row re-derives it instead of silently reopening the gap. `computeOvr` also now **normalizes** skill weights (a row states relative importance only — GK's 92-sum hand-correction is obsolete and was also compressing keepers' slope against team strength) and **centres height** on the position's own range (a level effect wearing a skill weight's clothes). Result: every position within 0.3 OVR on mean, sd and p90, and club-best tracks roster share. Tools: `scripts/positionOvrCalibrate.ts` (prints the table), `scripts/positionOvrProbe.ts` (the symptom), `test/core/positionOvrBalance.test.ts` (the gate). **Three traps.** (a) **`SECONDARY_POSITION_CUTOFF` MUST be re-derived in the same change** — its bars are percentiles of a per-pair *gap*, so any level move shifts every bar touching that position; left alone, "holds a second position" ran CB 93% / DM 93% against FB 1%, i.e. the fixed share the design rests on had stopped being fixed. (b) **Measuring "best player at his club" needs a fair tie-break.** OVR is an integer and a squad's top few sit within a point or two, so awarding the tie to whoever comes first in the roster array biases the whole table by generation order — it read as a 4-point positional skew that wasn't there. (c) The 8×8 matrix of "mean OVR of position A's players evaluated at B" must keep its **diagonal maximal** (it does, before and after) — that is the check that the calibration didn't turn some position into a conversion magnet. `migrate.ts` re-derives `ovr` (and every `hist` snapshot's) from stored ratings on load, clamping `potential` up to it; the spread half applies at generation only, so old saves keep their original spread.
- **Anti-inflation (fragile equilibrium — several mechanics exist only to hold it):** youth intake anchors to a fixed-at-generation `academyBase`, never to the club's current roster average (the torn-out anchor caused unbounded ratchet). Potential is a *scout estimate* (`estimatePotential`), never a growth input. Every position's expected lifetime rating arc is ~0/slightly negative. `developmentBias` (persistent per-player trait, deterministic from pid) **must taper to exactly 0 by peak age**, or inflation reopens. `growthDamping` scales down only *positive* deltas as ovr climbs. `YOUTH_BASE_OFFSET` offsets the fact that `generatePlayer` doesn't vary quality by age **on the youth-intake path — world generation stopped being age-blind on 2026-09-09, see the next entry**. Any new mechanic that shifts these must be dynasty-audited (`scripts/`).
- **WORLD GENERATION HAD NO AGE TERM, AND EVERY "the ratings go weird after about season 5" REPORT IS THAT ONE FACT (2026-09-09, user report).** `generatePlayer` rolled every rating from the club's `base`; `age` only ever set `born`. Measured on a fresh big-four top flight, mean OVR by age ran **18 → 76.2, 22 → 76.2, 27 → 75.7, 33 → 75.2** — flat to within a point across all sixteen ages. The sim then ran the age curve over that, which is the bug: a generated 18-year-old had been handed a 27-year-old's ratings *and* the eight years of growth that produce them.
  - **Three symptoms, one cause, and they are worth keeping separate because each looks like a different subsystem's fault.** (a) **The best players were all 20-23.** Ages of the ten best players in the big four: season 1 `25 21 32 29 19 22 32 23 32 33`, season 3 `20 20 20 20 21 20 22 21 23 23`, season 4 `21 21 23 21 23 21 21 22 21 21`. Mean age of the top 30 fell 26.0 → 21.5 in two seasons. (b) **The top ran into the ceiling.** Best OVR 91 → 99 by season 5, the 90+ population 11 → 60, individual ratings pinned at `RATING_MAX` 0.10% → 1.08% and still climbing at season 12. (c) **Squads hollowed out.** Big-four top-flight mean 75.4 → 63.3 by season 4 while p90 *rose* 84 → 86: the generated 30-33 band only ever declined and retired, so a uniformly-good squad became a strong XI plus filler.
  - **A FOURTH bug fell out of the same measurement: a permanent hole in the age distribution.** Starting rosters were `INITIAL_AGE_MIN`..`MAX` = 18-33 while youth intake starts at `YOUTH_AGE` = 16, so **no player was ever created with a birth season in between**. The whole pool had zero players aged 17 at season 1, 17-18 at season 2, 18-19 at season 3 and **28-29 by season 13** — a gap `18 - YOUTH_AGE` years wide marching up one year per season, crossing peak age around season 10. `INITIAL_AGE_MIN` is now `YOUTH_AGE`, so intake lands *inside* the range instead of below it. Measure a birth-season gap on the **whole pool**, never on rosters: the free-agent pool would hide it.
  - **The amplitude is DERIVED FROM `BASE_AGE_CURVE`, not measured, and that is the load-bearing design call.** The exact correction for "he was paid growth he had not earned" is the growth he has left: `ageCurveOffsets` (`players/generate.ts`) integrates the sim's own curve from his age to `BASE_AGE_CURVE_PEAK` and starts him that far down, so progression gives back precisely what generation took off. Deriving it means a curve retune reaches both sides at once. **Split per rating group** (physical at `age + PHYSICAL_AGE_SHIFT`, skill at `age + SKILL_AGE_SHIFT`, 4.5 years apart, plus `GK_AGE_SHIFT`), mirroring `stepRatings`, which buys the right thing for free: a generated veteran has lost his legs and kept his technique.
  - **MEASURING THE EQUILIBRIUM AND COPYING IT WAS TRIED FIRST AND IS WRONG — do not rebuild it.** `scripts/generationAgeCalibrate.ts` sims to equilibrium and prints the profile ready to paste; the settled rostered hump spans **~33 OVR from 16 to peak**, and reproducing it blew the calibrated range apart (max 91 → **98**, the 90+ population 11 → **182**), because a hump that tall does not fit inside a 31-point league. The cause is `AI_PROSPECT_SLOTS`: an AI club keeps five high-potential teenagers on its **senior** roster at ~42 OVR who never play, so **21% of an equilibrium big-four squad is aged 16-19**. That is a sim artifact with no counterpart in a real squad or in EA's ratings. The curve's own hump is ~16 points and fits. Keep the script — the equilibrium is still the thing to check the result *against*, and its **25-season floor is not a preference**: a generated player is 18-33 at season 1, so at season 13 every age above 30 is still the inflated generated cohort, i.e. the very population being corrected.
  - **The DECLINE side is damped and the GROWTH side is not (`GENERATION_DECLINE_SELECTION` 0.55), and the asymmetry is the interesting part.** The curve states the mean decline of everyone who ages, but a player still on a roster at 37 is a *survivor* — `retirementProbability` climbs every year, so the ones who fell off are gone. Undamped it generated a big-four 35-year-old ~15 below a peak-age team-mate against ~9 at equilibrium, and on **`"steady"`**, whose late decline is far steeper, it drove the physical base onto the **soft floor outright (1.00 at age 37)**: every veteran's legs identically dead, with the clamp erasing the differences between them. 0.55 is the measured equilibrium-to-curve ratio, not a chosen number. **No equivalent factor below the peak**, because selection there runs the *other* way — `AI_PROSPECT_SLOTS` keeps teenagers for their ceiling rather than their ability, so equilibrium's young band sits *below* an unselected draw.
  - **`GENERATION_AGE_WEIGHTS` is a realistic senior-squad distribution, deliberately NOT the equilibrium's.** It is load-bearing rather than cosmetic, because the offsets are zero-meaned **under it**: weighting the ends more heavily drags every peak-age player up to compensate, which is half of why copying the equilibrium overshot. Bottom of the range is `YOUTH_AGE` (closes the hole above).
  - **`GENERATION_EQUILIBRIUM_LIFT` is 0 and that is a decision.** The world's rostered mean climbs 54.7 → 57.6 over 25 seasons, so a ~3-point lift would make generation start where it ends and never drift. Not taken, twice over: the generated level is **calibrated against EA FC** (a big-four top flight at 61/75.5/92 against EA's ~62/76/91, and the EA converter rank-matches onto a freshly generated world, so moving it moves imports too); and the drift it would cancel is the **documented ladder erosion** (`GROWTH_DAMPING_START` is an absolute ovr, so leagues under it grow undamped and gaps compress ~40%), so pre-baking it means generating England already compressed toward Serbia and moving the very gaps `weakLeaguesAudit` gates. **The change is shape-only: same level, same ladder.**
  - **Opt-in at the call site (`generatePlayer`'s trailing `ageAdjusted`, default false), and the default is what makes it safe.** The one caller that must NOT take it is youth intake, which already drops its 16-year-olds by `YOUTH_BASE_OFFSET` — an age curve on top double-counts. World generation and roster-import filler pass true; God Mode, the importer's archetype and every fixture keep what they had. **It looks inconsistent with `YOUTH_BASE_OFFSET` (34 points) against the curve's ~18 and is not**: intake is a *population* `trimRosterSurplus`/`AI_PROSPECT_SLOTS` then keep the best of, while generation puts a player straight on a roster with no selection in front of him.
  - **Scales draws, never the draw COUNT** (`generationAgeCurve.test.ts` pins it), so the shape change cannot re-roll a world by itself. But **the age draw feeds `estimatePotential`, whose loop runs `age+1 .. POTENTIAL_SIM_MAX_AGE`** — so changing the age *distribution* does change total draws and every generated world differs. Expected for a generation change (existing saves are already generated and untouched); it rebases the `touchStats` scoreline hash and rebuilds every cached test world.
  - **WHAT IT FIXES IS THE OPENING TRANSIENT, NOT THE DYNASTY-LONG DRIFT, and the distinction is worth stating precisely because the first write-up of this entry over-claimed it.** Measured, seed 1, 14 seasons (`agingBaseline.ts`), before → after:
    - **Best OVR at season 5: 99 → 93.** Before, the world's best player hit the `RATING_MAX` ceiling by season 5 and sat at 95-99 thereafter; now he is 93 at generation, holds 91-94 through season 10 and reaches 96-97 by season 11-14. The *pinning* is gone; a slow climb is not.
    - **90+ population at season 5: 48 → 20** (generation 11 → 16). By season 14 it is ~58 either way, so what moved is the speed, not the destination.
    - **Top-30 mean age: 26.0 → 21.5 by season 3 becomes 27.8 → 25.0**, settling ~23-24.5 rather than ~22. About two years older throughout.
    - **NOT fixed: ratings pinned at `RATING_MAX` still climb 0.14% → 1.10% over 14 seasons** (baseline 0.10% → 1.08%, i.e. the same trajectory from a slightly higher start). That is progression pushing the best players into the ceiling over many seasons, which an initial condition cannot touch; the lever is `GROWTH_DAMPING_*` or `RATING_MAX`, not this.
    - **NOT fixed: the squad-mean drop, which has a DIFFERENT CAUSE — do not read a mean that still falls as this change failing.** Big-four squad mean still goes ~75 → 61, because at season 13 **19% of a big-four squad is aged 16-17 at OVR 42-44**: `AI_PROSPECT_SLOTS` parks five high-potential teenagers on the SENIOR roster, where they never play. The XI is unaffected (p90 holds 84-87 the whole way). Fixing it means holding AI prospects somewhere other than the senior roster — its own change, its own audit.
    - Residual on top-30 age: ~24 rather than football's 26-30, because the best players are whoever got lucky and luck only lands on players with growth years left. The lever there is the shipped `"steady"` model, not this.
  - **Dynasty-audited, `weakLeaguesAudit` 20 seasons x 4 seeds, treatment and baseline run per seed on identical seeds and POOLED BY HAND.** Every treatment rung passes the mean gate, and the two negative pooled rungs belong to the **baseline** (Turkey→Greece −0.28, Scotland→Serbia −0.25) while the treatment has none. Pooled means, baseline → treatment: BIG4→France **3.95 → 3.87**, France→Netherlands 2.60 → 1.57, Netherlands→Portugal 1.48 → 2.56, Portugal→Belgium 1.03 → 0.05, Belgium→Turkey 0.55 → 0.86, Turkey→Greece −0.28 → **+0.04**, Greece→Scotland 0.71 → 0.13, Scotland→Serbia −0.25 → **+0.15**. **Solvency is clean on BOTH sides: all 8 runs SOLVENT, 0 clubs in deficit at 0/42 sampled points each.** Note that contradicts this file's own "main is red on this gate" note — re-measure the base, as ever.
    - **Every per-seed run prints a confident `FAILURES ABOVE` and none of them means anything**, which is this file's documented misuse arriving in force: the script applies its *cross-seed mean* gate to whatever seeds it is handed, so a single-seed invocation gates one draw. It fired on a different converged rung each time (Portugal→Belgium on seed 1, Turkey→Greece on seed 2, Scotland→Serbia on seed 3) and **the BASELINE fires on seed 3 too, on the same rung**. All of them vanish pooled. Run `SEEDS=1,2,3,4` in one invocation, or pool by hand — never read a per-seed "BROKEN" as a verdict.
    - Split across two machines: seed 3's treatment ran on `testmac` under `--max-old-space-size=2200`. **Probe the other Mac's MEMORY, not just whether it is idle of soccer-gm work** — it had no vitest or tsx running and was still at 81MB unused with 3.1GB in the compressor on 8GB, i.e. ~2.9GB available against an audit that ratchets to 2-3GB and never gives pages back. That is one seed's worth of headroom, not two, and the heap ceiling is what makes a wrong guess fail loudly instead of taking the machine down.
  - **Two tests were passing on luck and both needed the statistic fixed rather than the band widened** (fifth and sixth instance of that lesson in this file). `eafcConvert`'s "lands in the game's OVR band" asserted `max(imported) <= max(generated)`, comparing the top of the converter's reference world (seed 12345) against the top of the test league (seed 7) — **two unrelated 500-player draws**. They duly swapped (before 90 vs 93, after 93 vs 91) on a change that moved the mean by 0.1. Across five seeds English D1 generates **p50 76 on every one** and p99 90-91 while the max swings 91-93, so it now compares p99 with a tolerance sized to that spread. And `progressionModel`'s "leaves generated ratings alone and moves only the forecast" rested on "ratings are rolled before any progression term is read", which this change makes false **on purpose**: generation reads the model's own curve, because generating a `"steady"` save against the shipped curve would hand it its own transient. The property that actually protects the mid-save switch is the draw COUNT, asserted separately three times.

- **The user's club is unmanaged by design** in headless audits — no AI free agency/renewals/buys touch it, so it rots and produces *all* extreme worst-case roster/points stats. **Exclude `userTid` from tail metrics** in any audit, or report it separately.

- **Composites bucket by SLOT, not natural position (`rollupComposites` takes `SlottedPlayer[]`, `engine/positionFit.ts`, 2026-08-12).** The team's shape comes from its formation, so every group and weight keys off the slot a player occupies; his own `pos` only decides what it *costs* him to be there (`familiarityPenalty`, in raw rating points: `POSITION_ADJACENT_PENALTY` 6 / `POSITION_FOREIGN_PENALTY` 16 / `POSITION_KEEPER_PENALTY` 35, all in `engine/constants.ts`). Before this, groups were built from `p.pos` and the slot was forgotten after selection, so **moving a defender up the pitch made your defense better** (he stayed in the defensive group at full strength and simply left the attacking one) and `control` had the same inverted sign. `MatchPlayer` now carries `slot`; a substitute **inherits the slot of the man he replaces** (via a *copy*, never mutation — `TeamMatchData` objects are shared across every match built from one `leagueMatchData` call, e.g. `season.ts` builds it once for all 380 fixtures, so mutating a slot would leak into unrelated matches). `slotPlayed` tracks the played slot for the box score, which is built from the *original* roster arrays where a sub still carries his bench slot. Attribution weights, `computeMatchRating`, and every "who's the keeper" lookup follow the slot too. **The load-bearing consumer is the substitution logic, not the XI** — measured, starters are 99.2% exact-fit and 0% foreign, but the bench was putting a player in a foreign slot on **37% of all subs** (a striker replacing a tired centre-back was the single most common swap) because `pickReplacement` was exact-pos-or-anyone. It now maximizes `benchValue - familiarityPenalty(slot, pos)`, and `worthSub` gates on the same penalized value; **those two must stay on one number**, or the sim makes swaps it then punishes. Result: foreign subs 37% → 0.2%, and ~19% fewer subs overall (holding a tired starter on beats wrecking the shape). Chase-the-game subs pass `reshape` to `commitSub` so the arriving attacker plays *his own* position (a genuine shape change, one fewer defender) rather than being stranded in a defensive slot. Also closes the documented `pickReplacement` GK gap: an outfielder forced into goal is now penalized instead of silently leaving `keeping` at a neutral 0.5 while counting as an outfielder. Pure function of attributes, **no shared-`rng` draw**, so stream order is untouched — but composite values change, hence results change, hence the `touchStats.test.ts` scoreline hash was rebased. Measured over 20 seeded seasons: champion pts 79.20 → 80.55, and *variance fell* (champion sd 5.24 → 3.77, bottom sd 6.49 → 3.99), since fewer matches are decided by a side dismantling its own shape late. **Dynasty-audited** (`scripts/slotChurnAudit.ts`, 15 seasons × 2 seeds) for the obvious risk — that punishing thin squads sharpens the strong/weak gap into a procession — and it went the *other* way: distinct champions per league 8.0/8.1 → 9.4/9.3, dominant club's title share 33.3%/31.7% → 28.3%/23.3%, champion pts flat (77.9/78.1 → 78.1/77.4), ovr drift still ~0 (anti-inflation intact), D2 ceiling unchanged within noise. - **Secondary positions are DERIVED, never stored (`core/players/positions.ts`, `COVERABLE` in `engine/positionFit.ts`, 2026-08-13).** A player also plays any slot he can cover where his OVR there beats his own by at least `SECONDARY_POSITION_CUTOFF[pos][slot]`. A secondary is an **exact fit** (`fitTier` returns 0), so it waives `familiarityPenalty` entirely *and* makes him a first-choice `selectXI` candidate for that slot — a 74 winger who really does play full-back now takes the slot off a 66 full-back, where before fit was strictly by listed position. Threaded onto `MatchPlayer.secondary` because the derivation needs core's per-position OVR model and the engine can't import core; `benchValueAt` is the single sub-side caller, so `worthSub`/`pickReplacement` stay on one number by construction.   - **`COVERABLE` is the REVERSE of `ADJACENCY`, and getting it backwards is silent.** `ADJACENCY[X]` lists who can cover *slot X*; "where else can this player play" is the transpose. The table is **not** symmetric, so a forward lookup is wrong for exactly the pairs that matter and right everywhere else: a DM can cover at full-back but a full-back cannot cover in defensive midfield, and a winger can play up front but a striker is not thereby an attacking mid. Derived from `ADJACENCY` at module load so the two can't drift; a test pins the transpose and a second test pins the asymmetric pairs, so it can't quietly degrade into "same thing twice".
  - **One shared OVR threshold cannot work at ANY value — measured, and it was the first design.** How close a player rates one position along is a property of the position PAIR: CM/DM/AM share most of their OVR weighting, a striker's overlaps almost nothing. At a 3-point gap that gives **100% of CMs and 6% of STs**; there is no value where both are sane. `SECONDARY_POSITION_CUTOFF` is therefore per-pair, measured to admit `SECONDARY_POSITION_RATE` (0.15) of each position's players. Ranking by his rating **at the slot he'd fill** restores it (finishing 0.4652) and is the only comparison that means anything. Same reasoning applies to any future ranking of a player for a slot he doesn't list.

Greedy-best-pair-first cannot do that: a player only loses a slot to someone worth more there.

It hung `clubSeason.test.ts` indefinitely (62 CPU-minutes before it was traced).   - **`placePanel` is pure and is where the rules live**: below the anchor, flipped above when it would run off the bottom, clamped inside the viewport, and still opening *downward* when the panel is taller than the screen (pinning it to a far edge is worse than starting it where the reader is looking). Pure so it is testable with no DOM env, which this repo does not have.
  - **A `fixed` panel does not travel with the page, so an open one is dismissed on scroll or resize.** Worth knowing when testing in a browser: `styles.css` sets `scroll-behavior: smooth`, so a `scrollIntoView()` before a synthetic hover lands its scroll events *after* the panel opens and closes it immediately — scroll with `behavior: "instant"` and settle first, or the panel reads as never having opened.
  - **SSR is safe because the panel only exists while hovered** (`visible` starts false, and `createPortal` is never reached during `renderToStaticMarkup`) — every existing render test passes untouched. The guard against a regression is a CSS one: a test asserts neither panel rule carries `position: absolute`, since restoring it puts the panel back inside the clipping ancestor and *nothing else fails* — it renders perfectly, cropped.
- **Remapping `--bs-primary` does NOT reach form controls, and every checkbox in the game was Bootstrap blue for it (2026-09-01).** `styles.css` maps `--bs-primary` to the pitch green up top, which covers buttons and links — but Bootstrap compiles the checked colour into `.form-check-input:checked` as a **literal `#0d6efd`** rather than reading a variable, so all 12 checkboxes and switches rendered in stock blue on a green-tinted dark surface. Themed explicitly in the `.form-check-input` block beside the other form overrides; **a new control needs no work, but if one ever comes out blue this is why.** Two related gotchas: the tick and the switch knob *are* variables in Bootstrap 5.3 (`--bs-form-check-bg-image`, `--bs-form-switch-bg`), so they are themed without restating the selectors' rules; and the **unchecked** switch knob ships at `rgba(255,255,255,.25)`, drawn for a light page, which on this one reads as an empty pill rather than an off switch — hence the lift to 0.55. **`form-switch` is the house control for a setting that takes effect the moment you flip it** (Manager's "Never sack me", the depth-chart toggles, the live viewer's "Every chance", the Transfers for-sale filter, a league's "link money", New League's three). A bare `form-check` is for the other two shapes: **picking items out of a list** (World setup's per-country include — a switch per row in a twelve-row list is heavier than the choice deserves) and **staging something that happens on submit** (God Mode's clear-injury / clear-suspension, which apply on Save).
- **Two more Bootstrap colours were never remapped, and a 2026-09-03 UI audit found both (2026-09-03).** Exactly the trap the entry above documents, one selector along each time. **(a) `.nav-pills .nav-link.active`** compiles against `--bs-nav-pills-link-active-bg`, which resolves to a literal `#0d6efd` rather than to `--bs-primary` — so the Value/OVR and League/Cup toggles on Player Profile and Players/Clubs on Frivolities rendered in stock blue *inches from a pitch-green `btn-primary` doing the same job*. Themed on `.nav-pills` itself, so a new pill strip is green without anyone knowing this. **(b) `--bs-info` was the one semantic colour left unmapped** (`--bs-success`/`danger`/`warning` are all pointed at tokens), so every `.bg-info` / `.text-bg-info` / `.border-info` was stock cyan `#0dcaf0`: the board-confidence meter's "settled" step, the club-season "In progress" badge, the Schedule's current-matchday marker. Now `--bs-info: var(--sg-cup)` — the cup teal is already this system's cool, *non-result* accent, which is exactly what an "info" colour needs. **The Schedule marker had a second fault worth knowing**: `border-info` sets the border *colour on all four sides*, so it repainted that row's existing cell borders and drew a box around the row rather than an edge on it. It uses `.row-current` (an inset box-shadow left edge, combined explicitly with the win/loss washes, since a later box-shadow rule replaces an earlier one rather than stacking) — the same technique `.team-highlight` and `.row-through` already use. **The general rule: if a control comes out blue or cyan, a Bootstrap variable is unmapped; grep `styles.css`'s `--bs-` block before styling the call site.**
- **Empty states are a shared component (`ui/components/EmptyState.tsx`), because nine pages rendered as a bare sentence on the page background and read as broken (2026-09-03).** Every one of them was a `<p className="text-muted">` with no container, which made them the only content in the app not sitting on a surface — and a page-by-page audit graded all nine of them worst, above every genuine defect, for exactly that reason. They were *correct*: those competitions really hadn't started. The copy was rarely the problem; the missing container was. `EmptyState` takes a `headline` (what this page is), `children` (**when it fills up and what it will hold** — the pages that already said this graded a full grade higher than the ones that only said "nothing yet") and an optional `action` (somewhere to go now, since an empty page that is also a dead end is the worst case). Applied to Continental Cup/Shield, Domestic Cup, Champions Cups, Promotion Playoffs, Academy, Watchlist and the National Teams shell. **Deliberately capped at 62ch and NOT stretched to fill the viewport** — the void is the problem, so a wider box makes it worse. Two follow-ups the audit named and this did not take: Promotion Playoffs and Continental Shield can both derive a *provisional field* from the live tables and show it instead of prose, which is the real fix for those two.
- **`NationalTeamsLayout` set its group name larger than its page name, on all eleven pages (2026-09-03).** `<h4>National Teams</h4>` above `<h5>{title}</h5>`, so the loudest thing on every screen in the section was the one word identical across the section. Now a `.page-eyebrow` (the sidebar's own `nav-section` treatment) above an `h4` page title. Worth knowing as a shape: any grouped section that adds a shell should put the *variable* at the top of the type scale, not the constant.
- **Seasons display as years, and the start year is per-save (`meta.startYear`, 2026-08-23).** A season is a 1-based counter everywhere in the sim; `ui/format.ts`'s `seasonYear` is the only thing that turns it into a year, and which year season 1 lands on is now the player's choice on the New League screen. **Cosmetic only** — nothing in core, the engine or persistence reads it, and the field is optional with absent meaning the 2026 old saves have always shown (so no `migrate.ts` change). The offset lives as **module state in `format.ts`**, set by `LeagueContext`'s `commitLeague` — the single funnel every league (loaded, created, imported, switched away) passes through — rather than threaded to the ~90 `seasonYear` call sites, half of which are render helpers with no league in scope. The consequence to know: **anything rendering a season for a save that is not the active one must use `seasonYearFrom(startYear, season)`**, not `seasonYear` (`/leagues` sidesteps this by listing raw season numbers).
- **Crash visibility (2026-07-25):** `ui/components/ErrorBoundary.tsx` wraps the `<Outlet />` in `Layout.tsx` **keyed by `location.key`** (a page crash keeps TopBar/Sidebar mounted so the user can navigate away, and moving route remounts a clean boundary) plus an outer one in `App.tsx` for the routes outside `Layout` (`/leagues`, `/new-league`). `posthog.init` sets **`capture_exceptions: true`** (`main.tsx`) and the boundary also calls `captureException` itself, because React swallows the error on its way to unmounting. Before this, *any* throw blanked the whole app with the reason only in the console, and error tracking had **zero** issues recorded ever — a crash report could never be more specific than "it crashed". Gotcha for testing: **server rendering does not run error boundaries** (React re-throws to the caller), and there's no DOM test env in this repo, so `test/ui/errorBoundary.test.tsx` pins our half of the contract (`getDerivedStateFromError` + the fallback render) rather than a live catch. `test/ui/transfersRender.test.tsx` is the render harness pattern for a page (mock `useLeague`, wrap in `MemoryRouter`, `renderToStaticMarkup`) — a throw there surfaces as a test failure.
