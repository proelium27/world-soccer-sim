# Save size, IndexedDB storage split, worker boundary, exports, free-agent cull

> Moved verbatim from CLAUDE.md on 2026-09-25 to keep session context small. This is the detailed ledger for this area: read it before touching the code it describes, and add new entries here, not to CLAUDE.md. References to "this file" below meant CLAUDE.md as a whole; the other sections now live alongside this one in `docs/ledger/`.

**The `/transfers` freeze — root cause (2026-07-25)** — *the actual fix for "the transfers tab freezes and I can't open it".*
- **`WINDOW_TRANSFER_LIMIT` (50, `constants.ts`) caps the "Completed This Window" list**, which was uncapped. A 240-club world moves thousands of players per summer window; a real user save (season **5**, so this is not an aged-save problem) rendered **2056 `<li>` rows, 2066 flag `<img>`s, 10684 DOM elements and ~1 MB of SVG flag art**. After the cap: **603 elements, 60 flags, 17 SVGs**.
- **Why every profiling pass missed it:** the JS render of that page is **147ms** even at 2056 rows. The cost is entirely **layout, image decode and paint** — invisible to Node and to jsdom (neither lays out or paints). Measuring core functions, `renderToStaticMarkup` timings and client mounts all came back fast while the page was unusable. **When a page is slow but every JS measurement is fast, count DOM nodes and image bytes, not milliseconds.**
- **Flag SVGs are the multiplier**: `src/ui/assets/flags/` holds coats of arms up to **240 KB** (`bo`), 217 KB (`ec`), 153 KB (`es`), 143 KB (`mx`) — all rendered at **13px tall** by `<Flag>`. Any surface listing many players pays this. Keep per-page flag counts bounded; `scripts/flagWeightProbe.ts` weighs a list.
- **The News Feed inherited this exact bug and is the worse case (`NEWS_FEED_SEASON_LIMIT` 150, 2026-09-03).** `/transfers` was capped and `/news` was not, and the feed is the one that cannot stop growing: `newsEvents` is append-only and persisted, so a season's rows never shrink. Measured on a real **3-season** save: **956 rows, 15,903 DOM elements, 1,932 flag images, 34,345px tall** — already half again past the 10,684 elements that froze `/transfers`, three seasons in. `capSeason` (exported from `NewsFeed.tsx`, tested in `test/ui/newsFeedCap.test.ts`) keeps **every** item involving the user's club and fills the remaining budget in timeline order, then re-sorts by original index so a capped season still reads chronologically rather than "yours first". Measured after: 150 rows, 2,344 elements, 252 flags, 5,636px. Two non-obvious cases the test pins: the user's news must survive even when it all falls at the *end* of the season (a naive "first N" drops it), and a season that is entirely the user's legitimately exceeds the cap, so the budget goes negative and `slice(0, <=0)` must take none of the rest. **The lesson to carry: when a list is capped for this reason, check its siblings — the cost is DOM weight per page, so any other unbounded list of players is the next freeze.** Power Rankings (626 rows, ~400 images) is the remaining one.
- The user's own deals are always shown; the remainder is the biggest-by-fee, with a count and a News Feed link. `test/ui/windowTransferCap.test.tsx` pins the row/element/flag ceilings.
- **`scripts/probeUserSave.ts`** times every Transfers derivation against a real exported save — the tool that finally located this. Point it at a `/leagues` → Export JSON.

**Split player storage — saves write only what changed (`src/db/`, 2026-08-10).** Plan and measurements: `docs/save-performance-plan.md`. **The reframe worth internalising: save *size* was never the real problem — single-record *atomicity* was.** Every prior fix here (the free-agent cull, `archiveCup`, `WINDOW_TRANSFER_LIMIT`, `RETIREE_ARCHIVE_LIMIT`) shrank the save, which only helped because we had made total size the thing touched on every action. BBGM's database is also large at 100 seasons; it stays fast by storing entities as separate records so cost tracks what changed. Shrinking buys a constant factor, splitting changes the exponent.
- **Schema v6 split `played` out, and it is the same bug as v2 and v3 with by far the biggest field (2026-09-09).** Every one of the entries above says the league record "is rewritten in full on every mutation" — and `played`, the season's box scores, was sitting in it. Nobody connected the two facts, because **`played` is invisible to every save-size probe in this repo**: they all sample after the offseason, which wipes it. That is the same blind spot `core/simArchive.ts` documents for the worker boundary, and `detachPlayed` closed it there while explicitly leaving IndexedDB alone. Measured on a **season-1** save on the 626-club world, what one lineup drag wrote:

  | matchday | bytes per click | `structuredClone` |
  | --- | --- | --- |
  | 1 | 6.4 MB | 32 ms |
  | 10 | 63.0 MB | 350 ms |
  | 19 | 113.1 MB | 1,091 ms |
  | 28 | 162.3 MB | 1,430 ms |
  | 38 | 216.6 MB | 2,653 ms |

  on a fast desktop, before IDB serialises a byte, against mobile's documented 5-10x. Real player saves agree (`soccer-gm-league-9`, season 47 mid-season: **166.7 MB, 944 ms**; the 100-season save in its offseason: 108.7 MB, all append-only history). Split out, that same record is **13.1 MB / 129 ms** and a mutation writes **no played rows at all**. `scripts/playedStoreProbe.ts` measures all of it, "before" being the same record with `played` still on it rather than a stale reading from another branch.
  - **The table is NOT a save-age curve, and that is why the symptom reads as "slow on certain devices".** `played` scales with world size and how far into the season you are, so it hits a season-2 player exactly as hard as a season-60 one, worsens every matchday and vanishes at the rollover. Every other entry in this section is about a save that degrades as it ages; this one degrades and recovers every year.
  - **The diff is an APPEND, not the identity comparison players and retirees need, and that is what gets the common case to zero work.** `players` is a pool where any row can change, so finding what moved costs a map and a per-row compare. `played` is a *log*: `simThrough` only ever does `[...league.played, ...newResults]` and the offseason only ever sets it to `[]`, so the answer is an index rather than a set. `playedToWrite` checks that claim rather than assuming it — a pointer compare per match, no allocation, ~10.5k at worst — and falls back to a full rewrite on anything unexpected, the same "cannot prove what is on disk, so rewrite it" rule the other two diffs open with.
  - **Rows are keyed by ARRAY POSITION (`[lid, matchIndex]`), not by an id, because the UI addresses matches by index** (`/box-score/:idx`, `/watch/:matchIndex`, Schedule's rows) — the array's order is itself load-bearing state. IDB compares array keys element-wise and numbers numerically, so `[lid, 2]` really does sort below `[lid, 10]` and a `getAll` comes back in index order (a string key would return 0,1,10,11,2… and silently renumber every match a link points at). Density is an invariant `saveLeague` maintains, which is why a full rewrite must **range-delete first**: a season that shrank would otherwise leave the tail of the old one behind and `loadLeague` would read a longer season than was played.
  - **An empty inline array still counts as "not split yet".** A save sitting in the offseason legitimately has no matches, so `loadLeague` uses `??` rather than a length test — a length test leaves that record in its old shape and rewrites it on every single load. Same rule the archive already documents, and it bites far more often here.
  - **Load is a wash, measured rather than assumed** (the one thing this could have made worse, since ~203 MB now arrives as 10.5k rows): reading the same data back is **1,610 ms** as one inline record against **86 + 1,356 ms** split, same order and marginally faster. Paid once a session either way, against once a click.
  - **Verified in Chrome, which the entries above could not claim** (`fake-indexeddb` is more forgiving about transaction auto-commit than Safari, and this adds a fifth store plus a delete-then-put to that one transaction). On a real 6,080-match save: the lazy split produced 6,080 rows with a **content hash identical** to the pre-split record and dense in-order keys, the box score page rendered the same match, a scouting-slider mutation persisted while `played` kept its hash (zero rows written), the rollover **range-deleted all 6,080**, and a simmed matchday **appended 160 rows while a deliberately tampered row 0 survived untouched**. No console errors.
  - Costs one `DB_VERSION` bump, so the documented one-way door widens again: a v5 build cannot open a database a v6 build has touched, and rollback is a total outage until you roll forward. It fixes **write** cost only — `played` is still fully resident after load, which is the `docs/lazy-career-plan.md` problem one field along.

**Match box scores are read back on demand, not held (`loadLeague`/`loadMatchBoxScore`, `BoxScore.detailElided`, `teamSeasonStatsFor`, 2026-09-17).** Schema v6 above stopped *writing* `played` on every mutation and says in its own last line that it fixes write cost only — this is that leftover. `loadLeague` now returns every match with its box score detail (the event timeline AND both teams' player lines) emptied and `detailElided: true` set, keeping only the score, possession and matchday that the standings, the schedule and every table read; `loadMatchBoxScore(lid, index)` fetches one match's back. **Measured on the shipped 898-club world at matchday 12 (`scripts/lazyMatchDetailProbe.ts`): the league object the app holds for the session goes 161.8 MB -> 61.1 MB, a 62.2% cut, `played` itself 101.6 MB -> 1.0 MB, at 21.2 KB of detail per match — extrapolated to a full season's 10,538 fixtures, ~223 MB that is never loaded. `loadLeague` time is unchanged (~1s).** It shipped in two steps (events first, then lines), which is why the helpers were renamed partway through.
  - **The one thing this can do is DESTROY DATA, and it is silent.** Once an in-memory box score can be a hollow copy of a real row, every write path has to know not to put it back. Two rules in `saveLeague`, both load-bearing: an elided row is **never written**, and the full-rewrite branch now deletes only the **tail** (`bound([lid, played.length], [lid, []])`) rather than clearing the range. Clearing used to be equivalent because every surviving index was rewritten immediately after; that stopped being true the moment rows could be skipped. `loadLeague` seeds no write cache, so the very next save takes the full branch — **verified, without the fix every timeline on disk reads 0 after one mutation**. `test/db/lazyMatchDetail.test.ts` is the gate and was run against the pre-fix code to confirm it fails.
  - **Skipping is exact rather than best-effort, and the argument is worth keeping**: an elided row can only have come from `loadLeague`, at that same index, and `played` is only ever appended to or cleared wholesale, so the row already at that key IS that match.
  - **The player lines have exactly ONE whole-season reader, `computeTeamSeasonStats`, and dropping them is only safe because of the fold (`TeamSeasonAcc` in `core/standings.ts`).** The lines are folded into a per-club accumulator as they are read (`readPlayedElided`) or written (`elideWrittenDetail`), then dropped; `teamSeasonStatsFor(league, teamIds)` answers from the fold plus any matches still held in full, and replaced `computeTeamSeasonStats` at every caller outside the sim — `useSimWorker`'s offseason hand-off (the precomputed `teamStats` that lets `detachPlayed` work), Leaders and the Club Database. `computeTeamSeasonStats` is now a wrapper over the same fold, and additions run in match order either way, so **the sums are bit-identical, not close** — `lazyMatchDetail.test.ts` pins `toEqual` on the floats against real simmed matchdays, after a load and across a session's saves, and was verified to fail with the load-time fold removed. Three rules hold it up: **(a)** the fold is keyed **by lid** (`seasonFolds`), not a single slot, because customising another save's teams loads a non-active league mid-session and a single slot would evict the active league's totals — `lastWritten` gets away with one slot only because losing it costs a full rewrite; **(b)** a read NEVER advances the shared fold, because a live match is simmed and shown before it is committed and abandoning it must not leave its goals in every total; **(c)** a stripped match with no fold covering it makes `teamSeasonStatsFor` THROW rather than return a total that silently omits it, since that state is a bookkeeping bug and a wrong table is worse than a loud one. The free-agent cull never touches `played`, which is what keeps the fold from going stale underneath it.
  - **The marker must never reach a FILE.** It claims "the real events are on disk at this key", which is a claim about *this* database and false anywhere else — imported, `saveLeague` would skip those rows for the life of the save and the dynasty would never have a timeline again. So `exportLeagueJSON` rehydrates through `withMatchDetail` first, and `importLeagueJSON` strips the marker defensively. **The strip is deliberately NOT in `migrateLeague`**, which every load also goes through: `loadLeague` elides *before* migrating, so stripping there would undo the elision on the spot.
  - **A match that genuinely recorded no events is left unmarked**, or every goalless, cardless match would be re-queried forever. `isDetailElided` therefore means "there are events on disk that are not here", never "there may be".
  - **A pre-v6 record carrying `played` inline is NOT elided**, because there its box scores are the only copy in existence and the split write-back is what first puts them in the store.
  - **The read is chunked (`PLAYED_READ_CHUNK` 512) and that is the point, not an optimisation.** A single `getAll` over the range materialises every event first, which lowers the steady-state floor and leaves the peak — and the peak is the half that runs a phone tab out of memory. Keys are dense, so the next key after N rows is exactly `[lid, N]`; ~20 round trips on a full season against ~10,500 cursor advances. It runs in **its own read-only transaction**, since it awaits between requests and an idle transaction is free to auto-commit.
  - **Two screens need a whole box score and both are single-match or single-matchday**: `/box-score/:idx` and `/watch/:matchIndex` (rewatch), through `ui/useMatchDetail.ts`. The box score page gates the WHOLE page on the fetch now, not just the timeline, since its player tables come from the fetched lines too and an empty table would say the match had no players. **The LIVE viewer never waits** — its candidates are built from the fresh sim result before it is committed. Rewatch fetches the whole matchday in parallel because the rail reconstructs the other games' scores minute by minute (`scoreAtMinute`). Both surfaces distinguish "loading" from "nothing happened", which are different claims about a match.
  - **Cup box scores are untouched** and still fully resident: they live on `league.cup`, not in the `played` store. `archiveCup` folds them at the rollover.
  - **Verified in real Chrome IndexedDB, not just `fake-indexeddb`** (2026-09-18, headless Chrome on a throwaway profile, fresh origin): 3 matchdays simmed in-session left all 1,198 stored rows with events and lines and **0 rows carrying the marker**; a reload followed by another matchday — the full-rewrite branch on top of a stripped league, the dangerous one — left all 1,635 rows intact with 0 marked; the box score page, rewatch pitch, Club Database and Leaders all rendered with zero console errors. **How that was driven is worth knowing:** the Chrome DevTools MCP refuses to launch when another session holds its profile, and the extension can lose its tab. Chrome itself can be run headless with `--remote-debugging-port` and a temp `--user-data-dir` and driven from a ~100-line Node script over the DevTools protocol (Node 24 has `WebSocket` built in; `Page.navigate` + `Runtime.evaluate` is all it needs), which is fully isolated from every real save and needs no package installed.
  - **Matches simmed DURING a session are elided too, after the save that wrote them (`elideWrittenDetail`, called in `LeagueContext`'s `commitLeague`).** The worker returns real box scores, so without this a season simmed in one sitting climbs straight back to holding every timeline. It elides only a `played` array it can PROVE is on disk — the exact reference the last `saveLeague` for that lid recorded in `lastWritten` — and returns anything else untouched, and it repoints `lastWritten` at the elided array so the next save still sees an unchanged prefix and stays on the append path. Measured with real engine output (`lazyMatchDetailProbe.ts`, 12 matchdays saved and elided one at a time): **101.3 MB held, 0 of 4,750 timelines in memory, all 4,750 on disk** — identical to a freshly reloaded save. `commitLeague` is the funnel for the same reason the season-year offset and the badges are set there: every committed league passes through it. The live viewer is unaffected because its candidates are built from the fresh sim result *before* commit.
  - **This is stage 1 of the worker-owns-the-data plan, and the ordering is deliberate.** Moving ownership to the worker does NOT reduce memory on its own — the worker would hold the same bytes on the same device — and a half-done inversion is a *regression*, because `saveLeague` currently runs on the main thread with no clone and moving it adds a full clone per mutation until views exist. The payoff is laziness; ownership is what makes laziness enforceable and kills the clone. Remaining stages: worker owns league + DB with mutations as commands, then page-shaped views so the UI stops reading `LeagueStore`, then worker-side paging of one season.
- **Schema v3 split `retiredPlayers` out too, and it is the same bug one field along (2026-08-22).** The split above stopped rewriting the *pool* on every mutation; the whole **non-player** record is still rewritten every time (`leagues.put({ ...rest })`), and the retiree archive was sitting in it. So the archive was re-serialised on every lineup change and signing. Measured at 2,204 bytes a row (`scripts/archiveWriteCost.ts`): **11ms per save at 2,000 rows, 46ms at 10,000, 91ms at 20,000**, before mobile's documented 5-10x — i.e. exactly the budget #210 existed to reclaim. **`RETIREE_ARCHIVE_LIMIT` was therefore bounding write latency, not disk**, which is why it could be raised **2,000 → 20,000** the moment the archive moved to its own `retirees` store (same out-of-line `[lid, pid]` key, same identity diff, same transaction). Sized against measurement, not a round number: `scripts/archiveGateProbe.ts` puts `isArchiveWorthy` at **~270 retirees/season at maturity** (5 in season 3, 184 by season 11 — careers must lengthen before anyone clears 200 appearances, so a short probe badly under-reads it), so 20,000 is ~75 mature seasons of full coverage against ~7 before, at 44 MB on disk. Three gotchas. **(a)** `loadLeague` splits a v1/v2 record lazily and keys off the field being **present**, not non-empty — an empty inline array must still count as unsplit, or a save with a legitimately empty archive rewrites itself on every load. **(b)** `remove` matters here in a way it rarely does for players, because the cap genuinely prunes rows. **(c) The `DB_VERSION` one-way door is now wider**: a v3 build opening the database locks every *older* build out of **all** saves (`VersionError`), so a deploy rollback is a total outage until you roll forward. Export JSON is the escape hatch.
- **Schema v2** (`database.ts`): a second store, `players`, one record per player keyed **out-of-line as `[lid, pid]`**. The compound key makes a league's pool a single range query (`IDBKeyRange.bound([lid], [lid, []])` — arrays sort after numbers, so `[lid, []]` is an upper bound), so **no index is needed**. `StoredLeague` = `LeagueStore` minus `players`, plus optional `players` (v1 records) and `writeSeq`.
- **`loadLeague` reassembles** the two halves into an ordinary `LeagueStore`, which is why `migrate.ts`, `exportImport.ts`, `src/worker/*` and every reader of `league.players` are **untouched**. Containment is what made this a one-file change.
- **The dirty set is a reference-identity diff**, valid only because the core is purely functional — it maps over players and passes unchanged ones through *by reference* (the sole `players.push` in the repo is a test fixture). **`test/db/playerIdentity.test.ts` is the gate, not a nicety**: if anything ever mutates a player in place, the diff calls it clean and the edit is silently never persisted — no type error, no crash, and nothing else in the suite would notice.
- **The last-written pool lives in the db layer**, keyed by lid, *not* in `LeagueContext` (the plan assumed the latter). No call site can forget it. Cross-tab staleness is caught by **`writeSeq`** on the league record: if disk doesn't match what we last wrote, the save degrades to a full rewrite rather than merging two states that never coexisted. `loadLeague` deliberately does *not* seed the cache — migration rebuilds player objects, so a loaded pool can't be assumed to match disk; first save of a session is therefore full.
- **One transaction over both stores is a correctness requirement**, not tidiness: `teams[].roster` holds pids, so a crash between the two writes leaves rosters pointing at players that don't exist.
- **Migration is lazy, in `loadLeague`, not in `upgrade()`** — testable, and a large save can't stall a versionchange transaction at startup. Interrupted = save left in its old shape, retried next load.
- **Lazy careers (`docs/lazy-career-plan.md`, 2026-08-24).** The splits above all fixed *write* cost and deliberately left `loadLeague` reassembling one ordinary `LeagueStore`; that containment is why the pool is still **fully resident**, which is the separate problem this plan attacks. Measured on the reported season-60 save: 275.8 MB of live JS objects (~1.52x its 181.6 MB serialized form), of which a player's identity is 4.5 MB across the whole world and his career records are **45.2 MB** — ten to one, worsening every season. Survey finding that makes it tractable: the hot pages (Roster, Dashboard, Leaders, awards) all do `p.stats.find(s => s.season === season)` — **one season, not a career**.
  - **`Player.career` is the whole trick, and it is what dissolved both open questions.** A `CareerSummary` (totals + best-single-season + a line per season) costs **13.5 MB against the 45.2 MB of per-season history it stands in for**, and *every* consumer that used to walk a career reads it instead: the all-time boards (so Frivolities loads nothing and no board loses a filter or a sort), `archivePlayer` and its worthiness gate, `playerGoalTotals`' milestone check, and the retiree farewell notice. The plan's fallback designs — pre-filter and load the top 500 for Frivolities, splice a retiree's final snapshot back on the main thread for the archive — turned out to be unnecessary and were never built. **Measure before designing here; both were sized by guess and both guesses were wrong by ~2x.**
  - **The contract: a stored summary covers seasons the player has FINISHED.** The one in progress is not in it, so a live number is the summary plus the current row — which is exactly what the resident window keeps. Folded once per offseason (in the progression map, step 2, which is *before* retirement at step 3, so a retiree's final season is already in it) rather than maintained per matchday, because one call site is testable and twenty are not.
  - **`peakOvr`/`peakOvrSeason` are authoritative once present, and that is an invariant with teeth.** `careerPeakOvr` and `peakOf` skip the history scan when the field is set, so anything building a `Player` with a `hist` must set it to match — `generatePlayer`, `createCustomPlayer` and the roster importer all do. A stale one makes a player read as worse than he ever was and the scan will *not* save you.
  - **Careers cross the worker as a window** (`detachCareer`, the last `POSITION_CHANGE_SEASONS` snapshots and 2 stats rows), sized from the code: the position-change spell walk reads the last `POSITION_CHANGE_SEASONS - 1` snapshots *with their full ratings*, and `ovrDuringSeason` wants the one stamped season − 1, a step further back once progression has appended. **Reading the constants cannot prove a window is wide enough** — running a season *and* an offseason on it and demanding the same league out can, and that gate caught two silent under-counts a narrower test would have missed (a 100-goal milestone firing twice, and a retiree's permanent farewell line).
  - **Cumulative worker payload on the real season-60 save, with the news and transfer detaches below: end of season 235.3 MB → 46.3 MB (80%), and flat across the season.**
  - **Still resident, still to do:** the main thread holds all 275.8 MB either way — everything above changes what *crosses*, not what is *held*. Making careers non-resident is the rename (`stats` → `recentStats`), which breaks all 113 call sites at compile time. That churn is the point: a truncated array read as a career returns a wrong number rather than an error, and in this branch alone that failure mode fired four times.
- **Splitting a store changes what "changed" means, and that nearly shipped a 2.2x regression (v4, phase 2).** Diffing by object identity is correct while both halves live in one record. Once they are apart it is not: a simmed matchday replaces `stats` on every player, so everyone arrives as a *new object* with identical ratings/contract/ovr, and the identity diff then rewrote ~11k rows byte-for-byte identical to disk **on top of** the career rows it genuinely had to write. Two puts per player instead of one: matchday save 622ms → **1459ms**. `rowsToWrite` now asks the halves separately — career by reference compare (`stats`/`hist` are never mutated in place), identity by *field* compare (sound for the same functional-core reason: nested values are replaced, not edited) — and most saves touch one or the other, never both. Back to ~660ms. **If you split another field off a record, re-ask what the diff is comparing.**
- **The one-way door is wider than it looks, and this was verified rather than assumed.** Once a `DB_VERSION` 2 build opens the database *once*, a version-1 build's `openDB` fails with **`VersionError`** — IDB refuses to open below the stored version. So an older build loses access to **every save in that browser profile, migrated or not**, not just the one that was upgraded. **Deploy rollback is therefore a total outage** for anyone who loaded the new build (no data loss — rolling forward restores it). Matters doubly here: whichever branch or worktree is on the older build hits it too, and several are normally open at once. Export JSON is the escape hatch.
- **Measured** (`scripts/savePerfProbe.ts`): single-player actions **1 dirty player, 0.01% of the save**; lineup/scouting/release write **zero** players. 8-season save: routine action **281ms → ~118ms** (3-season: 99 → 35). **Phase 1 alone was a regression** (99 → 335ms writing every row individually) — it must never ship without the dirty set. **Sims are barely helped** (a matchday dirties 8076 of 8076 by identity, 5992 genuinely) and their real cost is the worker `structuredClone`, which this doesn't touch.
- **Two live follow-ups.** (a) The remaining floor is the non-player fields, and **the figure this entry used to quote here was badly wrong in an instructive way**: "~7.8 MB at 8 seasons" was measured *after* an offseason, so it missed `played` entirely — the largest of them by 25x (see schema v6 above, which took it). What is left really is small and almost all append-only (`powerRankingHistory`, `transfers`, `newsEvents`, `seasonHistory`, `cupHistory`), so splitting those is the next win and is *easier* than this was, but measure mid-season before sizing it. (b) **Making `simThrough`'s blanket player copy lazy was measured and rejected**: 26% ceiling on the one action users already accept as a pause, against touching the hot path in a repo with a history of RNG-order accidents. Don't revisit without new numbers.
- **Unverified in a real browser:** the save now reads and writes inside one IDB transaction, and `fake-indexeddb` is more forgiving about transaction auto-commit than Safari. Every await is on a request in that transaction, which should hold, but confirm by playing a save before trusting it.

**`league.played`'s box scores are the biggest single thing in a mid-season save, and half the cause of the reported crash (`detachPlayed`, `core/simArchive.ts`, 2026-08-24).** Measured on the **real reporter save** (`soccer-gm-league-4`, season 60, 59 completed seasons, the **shipped** 16-competition / 320-club world — not a custom one).
- **`played` is invisible to every save-size probe in this repo**, including `leagueSizeTiming.ts`, because it is wiped every offseason and rebuilt every season and they all sample *after* the offseason. It is driven by **world size × how far into the season you are**, not by season count. On the real save it is 60.5 MB at matchday 23 and ~99 MB at matchday 38 (6,080 league matches × ~16.4 KB a box score: 25 player lines ~6.6 KB, **181 events ~10.8 KB**).
- **Real-save totals, at end of season:** 221.7 MB, `structuredClone` **4788 ms** on a fast desktop. Composition at matchday 23: `played` 60.5 (33.3%), `players` 49.7 (27.3%), `powerRankingHistory` 18.9 (10.4%), `transfers` 14.8, `newsEvents` 11.6, `seasonHistory` 5.6, then the cup histories at 4-5 each.
- **A long-lived save does NOT match a simulated one of the same age, and this bit me.** A simulated 56-season world put `domesticCupHistory` at 42.9 MB and called it the dominant history; the real 60-season save has **4.3 MB**, because domestic cups only shipped recently and the save predates them. **Simulated projections over-weight every recently-added feature** — measure a real save before naming the biggest field.
- **Cumulative effect of everything in this change, on the real save: 221.7 MB → 99.3 MB (55%), clone 4788 ms → 1209 ms**, and the payload is **flat across the season** (~99 MB at matchdays 26/30/34/38) where it used to climb 189.8 → 221.7. What is left is dominated by `players` (49.7 MB), which must cross.
- **The sim does not read them.** `applyInjuries`, `applySuspensions` and `detectMatchdayNewsEvents` all take *the matchday's own* results, which the worker just generated; the markets, `computeStandings` and `computeTeamForm` read scores only. The **single** exception is `computeTeamSeasonStats` at `offseason.ts`, so `simOffseason` gained an **optional third param** for a precomputed aggregate — optional precisely because the function has ~60 call sites across tests and scripts and none of them should have to care.
- **`detachPlayed` swaps each box score for a `{home:[],away:[],events:[],stub:true}` marker.** Scores, possession and matchday survive because the sim genuinely reads those. `reattachPlayed` counts the **leading run of stubs** rather than matching positions: `simThrough` only appends and the offseason only clears, so the stubs come back as a prefix, and a result with no leading stub means the array was wiped and is the worker's own. **`jump` is deliberately exempt** (it crosses offseasons, so the leading-stub rule does not hold) — one slow deliberate action against every matchday advance.
- **Effect of `detachPlayed` alone**, measured on a 32-competition custom world: matchday 38 payload 216.1 MB → 27.4 MB. On the real shipped-world save it is the largest of the three held-back fields (~99 MB of the 122 MB held back at matchday 38).
- **Still open, and it is a product call:** this keeps box scores out of the worker, and schema v6 (above) later kept them out of the *per-mutation write*, but neither shrinks them on disk. The lever if that matters is the **181 events per match (62% of a box score)** — thinning event timelines for matches that are not the user's would cut most of it, at the cost of the timeline on other clubs' old matches.

**The worker boundary is the other half of the save-size problem, and it is the one that CRASHES rather than freezes (`core/simArchive.ts`, 2026-08-24).** Splitting storage fixed what a *mutation* costs; it does nothing for what a *sim* costs, because `postMessage` structured-clones the whole `LeagueStore` to the worker and the whole result back. Reported as "my save is crashing at season 56 on mobile", and it is real: PostHog carries production `$exception` rows reading `DataCloneError: Failed to execute 'postMessage' on 'DedicatedWorkerGlobalScope': Data cannot be cloned, out of memory` — on **desktop**, on `/dashboard`. A phone tab that gets OOM-killed reports nothing at all, so absence of mobile events is not evidence against.
- **Measured, on the current 16-competition world** (probe shape in the commit; ~20s/season, so chunk it): a season-56 save is **165.6 MB** serialized and ~150 MB as live objects, and a sim round trip holds **≥4 copies ≈ 560 MB** before the sim's own working set, React and the DOM. Growth is ~2.2 MB/season and does **not** plateau: `players` flattens at ~46 MB by season 16, and everything after that is append-only history. Composition at s56: players 46.3, `domesticCupHistory` 42.9, `retiredPlayers` 22.4, `transfers` 14.5, `newsEvents` 12.3, `powerRankingHistory` 9.0, `seasonHistory` 5.9, `cupHistory` 4.3, `international`/`shieldHistory` 2.9 each. **Users really do go this deep** — the top saves have 326/199/118 offseasons, and mobile users reach 73.
- **`detachArchive`/`reattachArchive` hold back the history the sim writes but never reads.** Wired into `useSimWorker.ts`'s `post()`, which is the single choke point every command *and* every result passes through, so no call site can forget it (same containment argument as `loadLeague` and `CrestArtProvider`). The payload carries **empty arrays, not missing keys**, so the sim needs no branch and whatever comes back in those fields is exactly this run's delta — appending to `[]` yields the delta for free. Currently `powerRankingHistory` + `retiredPlayers`: **30.8 MB off each direction at s56 (19%), clone 1699ms → 1130ms.**
- **The invariant, and it is silent when broken:** a held-back field must be append-only across the *entire* worker-side call graph. A read sees `[]` — no type error, no crash, just wrong output. `test/core/simArchive.test.ts` is the gate, and it is an end-to-end deep-equality check (a detached offseason, and a detached season+offseason, must land on exactly the league an undetached run does), not a unit test of the split.
- **`detachNews` took the news feed and the three cup histories (~23 MB), and they needed more than an empty array.** They look append-only from outside, but two offseason steps genuinely read them: `cullFreeAgentPool` scrubs culled players' rows out of them, and `extendPlayerNames` walks the cup `statLines` to decide which of this offseason's retirees are still referenced. Each got its own answer — the culled pid set is **reported back** out of `simOffseason` and the main thread applies the identical scrub through the very same exported function (`scrubHistoryForCull`, so the two cannot drift), and the referenced set is **precomputed here and handed in**. Getting a value out of `simOffseason` went through a **reporting variant beside it** (`simOffseasonReporting`), **not** a changed return type, which has ~60 call sites across tests and scripts; `cullFreeAgentPoolReporting` is the same shape. **Do not "simplify" by dropping the scrub:** culled players' rows would survive and render as "Player 4821", the exact bug `playerNames` exists to fix.
  - **A precomputed `referencedPids` must be UNIONED with the live walk, never substituted for it** — this was got wrong first and the deep-equality gate did not catch it, because the fixture had no case. The caller measures the league *before* the offseason, and the offseason then adds references of its own: this season's cup is archived into `cupHistory` by the same run, so a one-club retiree whose only surviving mention is a cup line from his final season is referenced by the finished league and not by the one the caller measured — he would silently lose his name forever. The union cannot over-name: the extra pids it carries belong to players the cull has since deleted, and a retiree is never one of those (retirement is step 3, the cull is the last thing that happens).
- **`detachTransfers` is a WINDOW, not an empty array, and it is the only held-back field the sim genuinely reads.** 14.8 MB / 186k rows on the real save. The read is `joinedSeasons` feeding `settledMultiplier` in `runAITransferMarket`, and it has a horizon: `settledMultiplier` **returns 1 for a player who arrived `PLAYER_SETTLED_SEASONS` ago and 1 for a player with no record at all**, so a row older than that is not merely unlikely to matter, it is provably inert. The log is written in season order, so the window is a suffix and the retained rows are the prefix ahead of it — concatenating them back needs no merge. Cut at `season - PLAYER_SETTLED_SEASONS`: one season wider than the winter market needs, two wider than the summer one. Measured on the real save: **166,394 of 186,032 rows held back, 13.2 MB, and the end-of-season payload 59.5 → 46.3 MB.** The retained rows take the same `culledPids` scrub the news history does. `jump` is exempt with the rest — each of its offseasons culls and only the last one's pids come back. **If anything else ever reads the transfer log inside the sim this stops being safe**, and it fails as a plausible wrong answer ("he has always been here") rather than a crash.
- **`seasonHistory` (5.9 MB) is the one that can never move.** It is read for real sim decisions (`academyForm`, `protectedStars`) and, unlike the transfer log, nothing bounds how far back those look — so there is no window to cut and no answer to precompute.
- **`POWER_SNAPSHOT_INTERVAL` is a save-size constant, not a UI one** (5 → **10** in the same change, so four snapshots a season counting the finale). A snapshot is a row per club for the whole world and is never pruned, so the cadence is a permanent per-season tax; at 5 it reached 448 snapshots / 143,360 club-rows / 18.2 MB by season 56. Price any increase in MB per 50 seasons. Pure and rng-free, and nothing in the sim reads the history back, so scorelines are unaffected (`touchStats.test.ts` hash unchanged).

**Exported saves are compact JSON + gzip (`db/exportImport.ts`, 2026-08-15).** `Export Save` writes `soccer-gm-league-<lid>.json.gz`. Two independent wins, both lossless: dropping the `JSON.stringify(league, null, 2)` indentation is **half the file on its own** (nothing ever read the export as formatted text), and gzip takes the rest — measured 8 seasons **83.6 MB → 43.3 MB → 5.2 MB (16.2x)**, 3 seasons 42.4 → 2.76 MB (15.3x, `scripts/exportRoundTrip.ts`, which also asserts the decoded bytes are identical to what was encoded). **This is emphatically *not* open design decision 6** — no history is pruned, the round trip is byte-for-byte, and the in-browser IndexedDB save is untouched (this is the export *file* only, so it does nothing for clone/save latency). Three things to know: **(a)** `readLeagueFileText` is the **single reader** for every file the game accepts (`importLeagueJSON`, the Leagues import router, the NewLeague roster picker) and it **sniffs the gzip magic bytes `1f 8b` rather than the extension**, so back-compat with old `.json` exports and with never-compressed roster files is free and a renamed file still works. Add a reader without going through it and gzipped saves read as garbage on that surface alone. **(b)** `exportLeagueJSON` is now **async** (`CompressionStream` is a stream) — its two call sites await it. **(c)** Browsers can only *compress* gzip/deflate via `CompressionStream`; **brotli would be 4.66 MB but is decompress-only in browsers**, so don't reach for it. `scripts/probeUserSave.ts` reads user exports through the same helper, so it takes either form.

**Save size & the free-agent cull** (`core/players/freeAgentCull.ts`, 2026-07-25) — *the fix for the "transfers page freezes the whole game" reports; see resolved design decision 6 for the measurements.*
- **Two separate problems shared one symptom. The `/transfers` freeze is fixed by `WINDOW_TRANSFER_LIMIT` (below), NOT by the save-size work here** — that was a real but distinct problem, and attributing the freeze to it was wrong. That page's own *derivations* are flat ~40-100ms even on a 24-season save. The cost is **total save size**: every mutation writes the *whole* league to IndexedDB and every sim `structuredClone`s it to the worker, both on the main thread, both scaling with size. `/dashboard` was nearly as bad. Baseline at 14 seasons: **88 MB, clone 4230ms, save 2756ms** (superlinear; mobile is 5-10× slower, matching production INP p75 31.5s / worst 539s).
- **Two bloat sources, both now fixed.** (1) **`archiveCup`** (`core/cup/archive.ts`) folds a finished cup's box scores into one `CupPlayerLine` per player (`CupState.statLines`) and drops them, at the offseason archive point and in `migrate.ts` — **18 MB of an aged save down to 431 KB across 13 cups (~8×)**. Everything the UI draws is stored separately and survives (scorelines, aggregates, `legs`, winners, the LP table, the bracket); the box scores' only reader was `cupStatsForPlayer`, which now prefers `statLines` and falls back to summing box scores for the *live* cup. Verified on real simmed cups (`scripts/cupBoxScoreCheck.ts`): all three stages → 0 box scores, ~369 stat lines kept, scorelines/winners intact, idempotent. **`CupTie.boxScore` is now `BoxScore | null`** — note **international tournaments reuse `CupTie`**, so `simIntl.ts`/`tournament.ts` needed null guards. Every list read in the archive path is defaulted (`?? []`) because it runs inside `migrate` on every archived cup, where a throw would stop the save loading at all (verified: `cupStatsForPlayer` iterates only `cup.ties`; `Cup.tsx` has no `boxScore` reference, its table comes from `leaguePhaseTable`; `clubHistory` only keys cups by season). (2) `cullFreeAgentPool` deletes unsigned free agents who are `age ≥ FREE_AGENT_CULL_MIN_AGE` (24) **and** career-peak ovr ≤ 65 **and** potential ≤ 65. Result: **88 → 54.7 MB, clone 4230 → 370ms (11×), save 2756 → 736ms**, and the pool plateaus (~5.3k, increments decelerating) instead of growing forever.
- **Aggregating fixed a long-standing cup-stat under-count.** The cup's three stages live in three places (`leaguePhase.matches`, `playoff.ties`, top-level `ties`) and `cupStatsForPlayer` read **only the last**, so league-phase and playoff appearances never reached a profile: a club that played 6 group games and lost the playoff showed **0** cup appearances for every player, and even a quarter-finalist lost his group games. Measured on one real season: **1857 appearances played, 199 counted** (253 of 374 players showed nothing). `aggregateCupStats` now sums all stages, so cup appearances/goals jump for anyone who played group games — that's a correction, not inflation, and it's player-visible (Manual + Changelog both say so). `scripts/cupUndercountDemo.ts` reproduces the old behavior.
- **Retirement already deletes players outright** (offseason step 3), so a save holds **no retired players** — every off-roster player is an unsigned free agent, and nothing ever culled them (9245 unsigned vs 5996 rostered at 14 seasons, 96% never past ovr 55). Don't repeat the mistake of reading that bucket as "retired".
- **The age+potential gates are load-bearing, not caution.** A 17-year-old at ovr 45 with potential 80 has a career *peak* of 45, so culling on peak alone deletes the youth pipeline before the user sees it on `/incoming-talent`. Award winners are protected too (`awardedPids`), so no honours board can point at a deleted player.
- **`LeagueStore.nextPid` is a persisted monotonic pid allocator, and this is a correctness fix, not bookkeeping.** Pids used to be `max(players.pid) + 1` at each use (`offseason.ts`, `godMode.ts`), which silently reuses a pid whenever the highest-pid player is removed — and removal already happened via retirement. The reused pid then inherits that player's transfers/newsEvents/cup lines, since a pid is the only link. Backfilled as `max(pid)+1` so no save changes behavior on upgrade. Both call sites guard a missing cursor (`Number.isFinite`) because `Math.max(undefined, n)` is `NaN`, which would land straight in a player's pid — a test fixture casting `as LeagueStore` hit exactly this.
- **The cull necessarily shifts the RNG stream** (offseason step 2 progresses *every* player in the array with a draw each, so a shorter array = fewer draws = different downstream league). That's inherent to deleting players, not a slip, but it means the pre-cull dynasty baseline no longer applies. `scripts/cullDynastyAudit.ts` re-checks the invariants; **the only trustworthy way to read it is against the same script run on `main`** (copy it into a `git worktree add` of `origin/main`), because several metrics drift on main too. Measured 25 seasons, main → cull: inflation drift **+4.17 → +4.26** (seed 1), **+4.24 → +4.23** (seed 2); AI tier-2 players over the 70 ceiling **579 → 581** (seed 2); champion pts mean **83.8 → 84.1** / **85.3 → 87.0**; worst AI budget **+7.9M → −0.8M** (seed 1) but **+10.6M → +11.1M** (seed 2), so that lone small deficit is stream-shift noise, not a systematic effect. Free agents at season 25: **13961 (still climbing) → 5689 (plateaued)**; prospects **6157 → 5534**, so the pipeline is intact.
- **Two pre-existing findings this audit surfaced, neither caused by the cull** (both identical on main, both left alone): league-wide mean ovr drifts **~+4 over 25 seasons**, and `enforceDivisionCeilings` leaks **~23 over-threshold AI tier-2 players per season**. If either matters, they're separate work. **The leak figure is stale and the leak is now closed (2026-08-13).** Re-measured over 12 seasons excluding `userTid` (`scripts/loanCeilingProbe.ts`) it was **0-3 per season**, not ~23 — it shrank with the 2026-08-08 market fix, which also cut the sweep's own workload 61→18 — and **100% of what remained arrived by loan**, through a missing tier-2 guard in `runAILoanMarket` (see the loans entry below). With that guard added the count is **0 in every season**: the sweep handles owned players exactly.
- **Exclude `userTid` from D2-ceiling metrics**: a relegated user squad keeps 70+ players in tier 2 by design (`enforceDivisionCeilings` never sweeps it), which otherwise reads as a breach every single season. Comparing the best D2 player against the tier-1 *full-roster* mean (~57) is likewise a miscalibrated check — it "fails" on main too.
- **`awardedPids` protects honours-board pids, and getting this wrong is silent.** `SeasonAwards` stores **bare numbers** under `playerOfSeasonPid` / `goldenBootPid` / `teamOfSeason[]` — there is no `pid` key — so an earlier version that walked for objects with a `pid` property returned an **empty set for every save**, i.e. the protection did nothing and nothing failed. It now matches `*Pid` keys plus `teamOfSeason`, tolerates all three historical award container shapes (single / `[D1,D2]` tuple / `Record<compId,…>`), and covers `international.history[].topScorer.pid` (its `name` fallback saves the label but the profile *link* still uses the pid). Reachable, not theoretical: tier-2 squads are capped below `DIVISION_2_REFUSAL_OVR_THRESHOLD`, so a second-division Golden Boot / Team-of-the-Season pick can sit at peak ovr ≤ 65. **`scripts/freeAgentPoolAudit.ts` shared the same bug**, which is why it reported zero award references — don't read that as evidence.
- **The load-time cull is gated on pool size** (`cullOnLoad`, `FREE_AGENT_CULL_LOAD_THRESHOLD` 7000). Culling on *every* load makes mid-season deletion immediate — release a player by mistake, reload, and he's gone instead of re-signable from `/free-agents`. Only a genuinely bloated pool (the frozen-save case, 9245 in the save that prompted this; a maintained pool plateaus ~5.3k) is drained at load; everything else waits for the offseason cull.
- **`loadLeague` writes the shrunk record back** when migration removed players or collapsed a cup. Without it the on-disk save stays full size and every startup re-reads it and re-runs `aggregateCupStats` over every archived cup before first paint — the exact main-thread cost this set out to remove. The check is deliberately cheap (player count + `statLines` identity), since serializing twice to compare sizes is itself the cost being avoided.
- **There are THREE pid allocators, all now on the cursor:** `offseason.ts` (youth intake), `godMode.ts` (`createCustomPlayer`), and **`rosterImport.ts` (`applyRosterFile`)** — the last one was missed initially. It matters most there because **retirement deletes players without scrubbing** their transfers/newsEvents/cup lines, so a reissued pid inherits real history.
- Dangling references are scrubbed with the player (transfers, newsEvents, negotiations, inboundOffers, loan listings/rejections, `scoutingObserved`, **every cup stage's box-score lines and the archived `statLines`** — `scrubCupLines` covers `leaguePhase`/`playoff`/`playIn`/`ties`, not just `ties`, because `cupStatsForPlayer` reads them all, **and the live international campaign's `NationSquad.pids` + `stageInjuries`** — squad selection reads end-of-season club rosters and a weak nation can genuinely name a sub-65 player, so a culled player really can be sitting in one; archived campaigns already discard squads, and `IntlTournamentSummary.topScorer` carries a `name` fallback, so neither needs it) — not a crash if left (every reader guards the lookup) but it renders as "Player 4821" in history.
